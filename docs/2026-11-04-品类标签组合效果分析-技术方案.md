# 品类、标签、组合效果分析技术方案

> 日期：2026-11-04 ｜ 状态：技术方案讨论稿
> 对应需求：《2026-11-04-品类标签组合效果分析-需求文档》
> 依据：代码级静态调研 + 印尼生产库真实字段逐表确认（不含猜测字段）

---

## 一、实现目标

1. 建立**组合维度全指标**数据底座（发送/送达/已读/点击/注册/授信/放款，含 T1/T3/T7 三归因窗口）；
2. 支持按**业务场景 → 品类 → 标签 → 组合**分层下钻，指标列由业务场景决定；
3. 复用现有数据源，**不改动质效大盘现有统计表（`qe_*`）的写入来源**；
4. 品类/标签字段等一期上线生产后，通过映射回填，无需重建表。

## 二、数据现状与关键事实（生产实测确认）

### 2.1 数据源盘点

| 数据源 | 类型 | 关键维度 | 关键指标 |
|---|---|---|---|
| `message_template_statistic` | MySQL 日表 | **`material_combination_id`**、`material_group_id`、`agent_template_id`、`dt` | sent/delivered/read/url_clicked/unique_url_clicked |
| `qe_task_lane_template_message_statistic` | MySQL 日表 | `template_name`、`lane_type`、`window_type`、`task_id`、`send_dt` | 全套含 register/apply_credit/loan |
| `qe_task_lane_material_message_statistic` | MySQL 日表 | `material_type`、`material_id`、`lane_type`、`window_type` | 全套含 register/apply_credit/loan |
| `qe_task_message_statistic` | MySQL 日表 | `task_id`、`window_type` | 全套含 register/apply_credit/loan |
| `whatsapp_task_metrics` | Mongo 明细 | `templateId`、`materialGroupId`、`header/body/footer/buttonMaterial` | sent/delivered/read/click + buttonA~F |
| `message_record` | Mongo 明细 | `template.combinationId`、`template.name`、`relate_extra` | msg_status + 各状态时间 |

### 2.2 关键事实（决定方案走向）

1. **`qe_*` 表内部没有"组合"维度**，最细只到 `template_name`（模板）或 `material_id`（素材）。组合维度靠反查补键。
2. **`message_template_statistic` 是唯一带 `material_combination_id` 的统计表**，上段指标（到点击）现成；其 `material_combination_id` 由本仓库 `MessageTemplateStatisticJobService` 直接从 `message_template.material_combination_id` 取值写入。
3. **`template_name` 唯一映射组合**：代码层保证唯一、实测唯一，`template_name → material_combination_id` 反查成立。
4. **组合维度覆盖率约 85%**：`material_combination_id IS NULL` 属"渠道直建模板"，语义剔除，非缺陷。
5. **品类/标签字段生产未上线**：`category.code/category_type/source_type`、`tag.source_type`、`tag_relation.source_type/binding_status`、`message_material_combination.material_category_code`、Mongo `message_material.material_category_code` 均缺失，需等一期上线补。

6. **`qe_*` 表由外部写入**：三张 `qe_task_*` 表的 Mapper 仅有查询方法、无任何 insert/update，全仓库无对 `qe_*` 表的写入 DML——`qe_*` 的写入方不在本仓库（应为质效大盘/数据团队独立链路）。因此 `register_count / apply_credit_count / loan_count` 的「去重人数 vs 事件次数」口径，本仓库代码无法确认，需向数据团队核实（见 §7.2）。

7. **仓库已有 `material_combination_send_statistic` 表**（组合上段发送统计，含 `send_dt / material_combination_id / request_count / sent_count / delivered_count / read_count`，由 `MaterialCombinationSendStatisticJob` 每日全量重刷）。**本方案忽略此表，按 §四 重新新建 3 张表**，不从该表扩展。

### 2.3 业务场景维度的数据现状（本次新增确认）

- `qe_task_lane_template_message_statistic.lane_type` 线上实际取值（抽样）：`CUSTOMER_NEW`、`COLLECTION_MESSAGE`、`UTILITY`、`MARKETING_CHAT`、`DISCORD` 等。完整旧泳道定义见枚举 `SourceLaneEnum`：`AUTHENTICATION / UTILITY / CUSTOMER_NEW / CUSTOMER_OLD / MARKETING_DEFAULT / MARKETING_CHAT / COLLECTION_CHAT / MARKETING_FLOW / COLLECTION_MESSAGE`（其中 `DISCORD` 为另一维度字段值，非该枚举）。
- **通知类（UTILITY）模板有 loan 转化**：如 `credit_approve_notify`（授信通过通知）loan=215、`disburse_successful`（放款成功通知）loan 有值——证实通知类会促授信/放款。
- **OTP 无统计**：`lane_type='OTP'` 查询为空，OTP 走独立 otp 服务，不进营销统计表。**OTP 不纳入本方案**。
- 业务场景的锚定：以 `TaskTagEnum` 的 SCENARIO 场景为主（`TaskTagCategoryEnum.SCENARIO`，任务必填单选）；过渡期按 `lane_type` 兜底归类。

## 三、下钻链路设计

### 3.1 到品类（两条路，一期上线后可用）

- 路 A（组合快照）：`combination → message_material_combination.material_category_code`；
- 路 B（成员素材）：组合 → 成员素材 → `message_material.material_category_code`；
- 历史缺品类素材读作 `UNCATEGORIZED`，单独成桶。

### 3.2 到标签（按标签类型独立下钻，一期上线后可用）

```
组合/模板 → message_material_template（或 whatsapp_task_metrics.*Material）
        → material_id（素材 Mongo _id）
        → tag_relation(entity_type='MATERIAL', entity_id=material_id, binding_status=1)
        → tag(source_type 区分 AI=0 / 运营=2)
```

标签分三类，来源与用途不同，**各自独立作为筛选维度、不跨体系比较**：
- **运营标签**：运营人工打，业务意图类（`source_type=2`）；
- **AI 标签**：AI 按内容分析（`source_type=0`）；
- **编码规则标签**：规则/程序判定，结构化特征（如"3段""2个emoji""头图为男孩"），**生成来源与存储方式待补充（见需求文档 TODO）**。

### 3.3 业务场景维度的接入

- **来源**：`qe_task_lane_template_message_statistic.lane_type`（现成）与 TaskTag 场景（逐步接入）。
- **场景 → 关注指标映射**：在应用层/配置维护一张映射（见 §六），前端按场景渲染对应指标列；数据层全量落库，不因场景裁列。
- 过渡期：未挂 TaskTag 的旧素材包按 `lane_type` 归类到场景大类。

## 四、表结构变更（新增 3 张表）

采用**多表、分层**：明细层照搬源表原生粒度，汇总层按"组合 × 日期"聚合。单表细粒度会导致笛卡尔爆炸与大量零值，不采用。

### 4.1 明细表① `material_combination_sent_effect_detail`（组合上段明细）

粒度：`combination_id × stat_date × agent_template_id`

```sql
CREATE TABLE `material_combination_sent_effect_detail` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT 'Primary key',
  `stat_date` varchar(10) NOT NULL DEFAULT '' COMMENT 'Statistics date yyyy-MM-dd',
  `material_combination_id` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Material combination ID',
  `material_group_id` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Material group ID',
  `message_template_id` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Message template ID',
  `agent_template_id` varchar(50) NOT NULL DEFAULT '' COMMENT 'Agent (channel) template ID',
  `agent` varchar(20) NOT NULL DEFAULT '' COMMENT 'Third party agent',
  `sent_count` int(11) NOT NULL DEFAULT '0' COMMENT 'Sent count',
  `delivered_count` int(11) NOT NULL DEFAULT '0' COMMENT 'Delivered count',
  `read_count` int(11) NOT NULL DEFAULT '0' COMMENT 'Read count',
  `url_clicked_count` int(11) NOT NULL DEFAULT '0' COMMENT 'URL clicked count',
  `unique_url_clicked_count` int(11) NOT NULL DEFAULT '0' COMMENT 'Unique URL clicked count',
  `create_time` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Creation time',
  `update_time` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Update time',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_comb_date_agent` (`material_combination_id`,`stat_date`,`agent_template_id`),
  KEY `idx_stat_date` (`stat_date`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Material combination sent/read/click effect detail';
```

### 4.2 明细表② `material_combination_conversion_effect_detail`（组合下段明细）

粒度：`combination_id × stat_date × lane_type × window_type`


## 五、数据流转与 Job 时序

```text
[message_template_statistic]                [qe_task_lane_template_message_statistic]
        │ 直传 mapping                              │ template_name 反查 combination_id
        ▼                                           ▼
  明细① sent_effect_detail                     明细② conversion_effect_detail
        └──────────────────┬────────────────────────┘
                           │ group by (combination_id, stat_date) sum
                           ▼
                  汇总 material_combination_effect_summary
```

**Job 时序（T+1 批处理，增量）：**

1. **上段 Job**：读 `message_template_statistic` 昨日 `dt`（增量），过滤 `material_combination_id IS NULL`，写明细①（`insertOrUpdate`）。
2. **下段 Job**：读 `qe_task_lane_template_message_statistic` 昨日 `send_dt`（增量），批量反查 `template_name → material_combination_id`：
   - 反查成功写明细②（`insertOrUpdate`，保留 lane_type + window_type）；
   - 反查失败（模板已删/无组合）直接丢弃。
3. **汇总 Job**：明细① + 明细② join，按 `(combination_id, stat_date)` 聚合，下段指标按 `window_type` 转置 T1/T3/T7 三组列，写汇总表。
4. **品类/标签回填 Job**（一期上线后追加）：组合 → 素材包 → 品类、组合 → 成员素材 → 标签，回填汇总表品类/标签列。

## 六、场景 → 关注指标（应用层实现）

数据层**全量落库**（不因场景裁列），「场景 → 关注指标」由应用层/前端按映射渲染：

| 场景（TaskTag 场景值） | 关注指标列 |
|---|---|
| 营销-未注册 / 营销-新客聊天 | 发送·送达·已读·点击·注册·授信·放款 |
| 营销-已注册 / 在贷 / 结清 / 默认 / 老客聊天 | 发送·送达·已读·点击·授信·放款（无注册） |
| 通知-在贷提额 / 结清提额 / 已注册提额 | 发送·送达·已读·点击·授信·放款 |
| 通知-工具类（放款成功/授信通过等） | 发送·送达·已读·点击·授信·放款 |
| 通知-逾前提醒 / 逾后催收 | 发送·送达·已读·点击（无转化列） |

**过渡期旧泳道兜底（`SourceLaneEnum` → 关注指标列）**：

| 旧泳道 code | 关注指标列 |
|---|---|
| `CUSTOMER_NEW` | 发送·送达·已读·点击·**注册·授信·放款** |
| `CUSTOMER_OLD` | 发送·送达·已读·点击·**授信·放款**（无注册） |
| `MARKETING_DEFAULT` | 发送·送达·已读·点击·**授信·放款** |
| `MARKETING_CHAT` | 发送·送达·已读·点击·**授信·放款** |
| `MARKETING_FLOW` | 发送·送达·已读·点击·**授信·放款** |
| `COLLECTION_MESSAGE` | 发送·送达·已读·点击（无转化列） |
| `COLLECTION_CHAT` | 发送·送达·已读·点击（无转化列） |
| `UTILITY` | 发送·送达·已读·点击·**授信·放款** |
| `AUTHENTICATION` | —（OTP，不纳入） |

- 实现方式：映射作为**配置/枚举**维护（参考 `TaskTagEnum`），前端按场景加载对应指标列。

## 七、关键口径（已决策 + 待确认）

### 7.1 已决策
1. 归因窗口 T1/T3/T7 全保留：明细②存全窗口，汇总表拆 `*_t1/t3/t7`。
2. 反查失败丢弃：`template_name` 反查不到组合的下段行直接丢弃。
3. 写入时序增量：各 Job 增量处理，非全量重刷。
4. 无组合桶：`material_combination_id IS NULL` 源行不进入明细（约14.9%）。
5. 渠道多副本合并：上段同一组合多渠道副本汇总时 sum。
6. 品类/标签后置：一期上线后新增列映射回填，不重建表。
7. OTP 不纳入。
8. 催收类只看触达（送达·已读·点击），loan 对催收语义不匹配（loan=新放款非回款）。
9. 上段统计来源 `message_template_statistic`（含 url_clicked/unique_url_clicked），不采用已有的 `material_combination_send_statistic`（该表缺点击指标、粒度粗）；新建明细① 直取 `message_template_statistic`。
10. 标签计量口径 = 方案 A（粗）：按"使用含该标签素材的消息整体效果"统计（不做跨体系比较，AI/运营/编码规则三类标签独立下钻）；后续必要时再引入组件位精确归因（方案 B）。
11. 已读率分母 = read / delivered（与 `combination/page` 接口 `readRate`、质效大盘一致）；全漏斗转化率统一以 delivered 作分母：送达率=delivered/sent，已读率=read/delivered，注册率/授信率/放款率=对应转化/delivered。
12. 后链路指标口径 = 事件次数：register/apply_credit/loan 按事件次数统计（非去重人数）；`qe_*` 由外部写入、无用户维度回溯能力，去重人数暂不可行，后续有需求再评估。

## 八、风险与备注

1. `whatsapp_task_metrics` 无后链路字段，注册/授信/放款只能走 `qe_task_*` 反查上卷，跨表 join 成本与准确性需评估。
2. 组合维度覆盖约 85%，空值为渠道直建模板（语义剔除），非缺陷。
3. 历史消息对应素材多落 `UNCATEGORIZED`，早期品类/标签效果样本可能不足。
4. 品类/标签字段生产未上线，§四品类/标签列需一期上线后补。
5. `message_template.name` 无 DB 层 UNIQUE 约束，反查前建议先做 `GROUP BY name HAVING count>1` 校验兜底。
6. 业务场景锚定处于"TaskTag 细化逐步替代 lane_type"的过渡期，需兼容新旧并存。
