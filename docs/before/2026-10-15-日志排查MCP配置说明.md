## 1.2 核心逻辑

### （1）日志排查：不做业务表映射，纯日志两段式

业务表里**不存 traceId**，所以拿到「手机号 / 任务ID / 模板名」这类业务标识时，流程是：

```text
第 1 跳：用关键词去 test_log 表做 LIKE 模糊匹配
        ↓ 从命中的日志正文里用正则 traceId:\[([^\]]*)\] 提取 traceId
        ↓ 按出现次数排序，返回 top 20 个 matchedTraceIds
第 2 跳：挑一个 traceId，再查一次，拿到该请求的完整日志链路
```

这样做的好处：**完全不需要维护「业务表 → 日志」的映射关系**，因此也没有映射过期、缺字段之类的维护成本。

### （2）服务与别名

固定 4 个服务，支持简称，**不指定就全部查**：

| 简称 | 实际 `service_name` |
| --- | --- |
| `api` | `whatsapp-crm-api` |
| `job` | `whatsapp-crm-job` |
| `mq` | `whatsapp-crm-mq` |
| `otp` | `whatsapp-crm-otp` |

### （3）时间与数据量

- **不传时间 → 默认查最近 20 分钟**；日志表 `test_log` 只保留**约 2 小时**数据。
- 查询必须带 `service_name`（走 `idx_service_time(service_name, log_time)` 索引），所以即使是「4 个服务全查」，也是 4 条带索引的查询。
- 默认返回 200 行，最大 1000 行。

### （4）Apollo 配置读取

用 **apollo-client SDK**（`com.ctrip.framework.apollo:apollo-client:1.4.0`）读取，对齐业务代码里 `TestLogServiceImpl#getAllApolloConfigs` 的实现，因此拿到的值和线上服务实际看到的一致。

- namespace 按环境在 `profiles.json` 的 `logDiagnostic.environments.<name>.apollo.namespaces` 里声明（idn-test 当前 14 个）。
- 返回结果里带 `sources` 字段（`REMOTE` / 其他）。**只要不是 `REMOTE`，说明没真正连上 Apollo 服务端**，会同时写入 `warnings`，避免把「本地兜底值」误当成「远端配置」。
- 结果里 `comment` 恒为空：运行时客户端不暴露配置注释。

### （5）安全设计

| 措施 | 说明 |
| --- | --- |
| 只读会话 | JDBC 连接显式设置为只读 |
| 不接受原始 SQL | 只执行由 `SqlBuilder` / `MongoBuilder` 生成的 `SELECT` / `COUNT` / `EXPLAIN`，所有值走参数绑定 |
| 白名单 | 表 / 集合必须显式列在 `allowedTables` / `allowedCollections` 里 |
| 批量化 | MySQL `IN` 每批 500 个值；Mongo `$in` / `$nin` 上限 500 |
| **仅测试环境** | 见下 |

**仅测试环境（三层硬约束，无任何绕过开关）**：

1. **加载层**：`ProfileStore` 在读配置时，**根本不会加载**名字里含 `prod` 的环境，只把它记进 `blockedEnvironments`（这样整个 MCP 不会因为配了生产环境就起不来）；
2. **调用层**：`LogConfig.requireEnvironment` 对生产环境名无条件抛错 `Production environment is not allowed: xxx ...`；
3. **Skill 层**：`log-diagnostics` 与 `business-data-diagnostics` 两个技能的描述里都写明「test environment only」，正文有 `## Environment scope (test only)` 段落，用户提到「线上 / 生产 / prod」时 AI 会直接说明并停止。

> 曾有 `allowProduction` 开关的设计，被安全复核否决后已彻底移除。

## 1.4 用法

### 触发方式：**只有你显式要求才会用**

三层省 token 设计：

1. `.mcp.json` 的 `enabled_tools` 白名单（Mongo 工具不加载）；
2. 两个 Skill 的 `description` 都写了「Use ONLY when the user explicitly asks…」，不会被主动调用；
3. `SKILL.md` 正文有 `When to use / When NOT to use` 段落。

### 典型对话

| 你说 | 实际发生什么 |
| --- | --- |
| `查下日志，traceId 是 xxxx` | 直接按 traceId 查，返回完整链路 |
| `看下 138xxxx 这个手机号今天的报错` | 关键词搜（默认跨 4 个服务）→ 返回 `matchedTraceIds` → 再按 traceId 追链路 |
| `这个模板名有没有报错` | 同上，按模板名搜 |
| `查下 mq 服务最近 10 分钟的错误日志` | 限定服务 + 时间窗 + 日志级别 |
| `看下 xxljob.yml 里的开关配置` | 读 Apollo 配置，可用关键词过滤避免刷屏 |
| `列出日志环境` | 确认配置是否加载成功 |

### `query_logs` 参数默认值

| 参数 | 默认 |
| --- | --- |
| `service` | 不传 → 4 个服务全查 |
| `env` | 不传 → 用 `defaultEnvironment`（`idn-test`） |
| `timeStart` / `timeEnd` | 不传 → `timeEnd` = 现在，`timeStart` = 20 分钟前 |
| `limit` | 200（最大 1000） |
| `order` | `asc` |

> `traceId` 和 `keyword` **至少给一个**，否则报 `Either traceId or keyword is required`。

## 1.6 关键实现细节（容易踩的坑）

- **`log_time` 边界必须传格式化字符串** `yyyy-MM-dd HH:mm:ss.SSS`。`SqlBuilder` 的 `gte/lte` 只接受标量，若传数字，MySQL 的 DATETIME 比较会被隐式转成 `YYYYMMDDHHMMSS` 而查错。
- **`test_log` 表结构**：`id, service_name, pod, log_time, trace_id, log_level, content, ctime, utime`，索引 `idx_service_time(service_name, log_time)`。
- **traceId 正则**：`traceId:\[([^\]]*)\]`。
- **run.sh 的提示信息只能写 stderr**：stdout 是 MCP 的 JSON-RPC 通道，往 stdout 打任何东西都会破坏协议。
- **内网限制**：Apollo meta（`http://10.99.1.187:8080`）和 MySQL 都是内网地址，必须连内网 / VPN。

## 2.6 常见问题

**Q1：报 `Missing password environment variable: LOG_DIAGNOSTIC_IDN_TEST_MYSQL_PASSWORD`**
→ `env.sh` 没被读到。依次检查：① 文件路径是否为 `~/.business-diagnostic/env.sh`；② 是否忘记 `Command + Q` 重启；③ 权限是否 600；④ 变量名是否写错（要和 `profiles.json` 里的 `passwordEnv` 完全一致）。

**Q2：我在终端里 `export` 了密码，为什么还是 `Missing password`？**
→ Codex 是图形程序，从 Dock 启动时不读 `~/.zshrc`。用 `~/.business-diagnostic/env.sh` 这一招就不受影响。

**Q3：为什么密码不直接写在 `profiles.json` 里？**
→ 当前代码强制要求用环境变量（`passwordEnv` 只能填变量名，明文 `password` 字段不被识别）。这样设计是为了：分享配置时不顺手泄露密码；即使文件被误提交也没有明文密码。

**Q4：日志查不到数据？**
→ 依次检查：① 是否连了 VPN；② 关键词是否是**精确子串**（手机号建议带国家码的完整形式都试一下）；③ 时间窗是否在最近 **2 小时**内（超过就物理上不存在了）；④ 放开服务限制 / 扩大时间窗再试。

**Q5：Apollo 读出来是空的？**
→ 看返回里的 `warnings` 和 `sources`。如果 `sources` 不是 `REMOTE`，说明没真正连上 Apollo 服务端（多半是 VPN / meta 地址不通），此时读到的是本地兜底值，不能当作真实配置。

**Q6：会在线上误用吗？**
→ 不会。生产环境名在配置加载阶段就被丢弃，`query_logs` 会直接报 `Production environment is not allowed`，**没有任何开关可以绕过**。

# 三、分享给其他人使用流程

## 3.1 分享什么

分享整个 `mcp-servers` 目录（或把它推到内网 Git 仓库后给地址）：

```text
/Users/opay-20260271/code-temp/mcp-servers
├── .agents/plugins/marketplace.json      # 插件货架清单（必需）
└── business-diagnostic-mcp/              # 插件本体（必需）
```

**绝对不要分享**（也分享不了，都不在仓库里）：

- `profiles.json`（已 gitignore，里面有你本地的库地址和用户名）
- `~/.business-diagnostic/env.sh`（密码）

## 3.2 接收方操作步骤

### 第 1 步：拿到代码

把 `mcp-servers` 目录拷到自己电脑（例如 `/Users/<你的用户名>/mcp-servers`），或者 `git clone` 内网仓库。

### 第 2 步：加入货架并安装插件

```bash
codex plugin marketplace add /Users/<你的用户名>/mcp-servers
codex plugin add business-diagnostic-mcp@whatsapp-crm-mcp
```

安装成功会输出 `Installed plugin root: .../plugins/cache/whatsapp-crm-mcp/business-diagnostic-mcp/0.2.0`。

### 第 3 步：确认插件已启用

检查 `~/.codex/config.toml` 里是否有：

```toml
[marketplaces.whatsapp-crm-mcp]
source_type = "local"
source = "/Users/<你的用户名>/mcp-servers"

[plugins."business-diagnostic-mcp@whatsapp-crm-mcp"]
enabled = true
```

也可以执行 `codex mcp list`，应能看到 `business_diagnostic` 且 `status = enabled`。

### 第 4 步：各自配置自己的凭据

**这一步每个人都要做，且各配各的：**

1. 复制配置模板：

   ```bash
   cd /Users/<你的用户名>/mcp-servers/business-diagnostic-mcp
   cp profiles.example.json profiles.json
   ```

2. 编辑 `profiles.json`：填入自己的库地址（`host`）和只读用户名（`user`）。
3. 建密钥文件：

   ```bash
   mkdir -p ~/.business-diagnostic
   cp ~/.business-diagnostic/env.sh.example ~/.business-diagnostic/env.sh   # 若模板不存在，手工创建
   chmod 600 ~/.business-diagnostic/env.sh
   open -e ~/.business-diagnostic/env.sh
   ```

   填入自己的数据库密码。

4. `Command + Q` 重启 Codex，然后说「列出日志环境」验证。

## 3.3 为什么凭据不会跟着一起泄露

| 文件 | 是否随插件分发 | 是否进 Git | 是否含密码 |
| --- | --- | --- | --- |
| `business-diagnostic-mcp/`（代码、Skill、脚本） | ✅ 分发 | ✅ 进 Git | ❌ 不含 |
| `.agents/plugins/marketplace.json` | ✅ 分发 | ✅ 进 Git | ❌ 不含 |
| `profiles.json` | ❌ 不分发 | ❌ gitignore | ❌ 只含变量名 |
| `~/.business-diagnostic/env.sh` | ❌ 每个人自己建 | ❌ 在仓库外 | ✅ **只在这** |

也就是说：**代码和配置模板可以随便传，密码永远只待在自己电脑上。**

## 3.4 后续更新怎么同步

| 上游改了什么 | 接收方要做什么 |
| --- | --- |
| 只改了 Java 代码 | 拉最新代码 → 在 `business-diagnostic-mcp` 下 `mvn -q -DskipTests package` → `Command + Q` 重启 Codex |
| 改了插件元数据（`.mcp.json` / `plugin.json` / `SKILL.md`） | 拉最新代码 → `codex plugin add business-diagnostic-mcp@whatsapp-crm-mcp` → 重启 Codex |
| 改了 `profiles.example.json` | 拉最新代码，对照自己的 `profiles.json` 手工同步（不要直接覆盖，会丢自己的地址） |

## 3.5 注意事项

- 所有使用者都**必须连内网 / VPN**；
- 所有使用者都只能用**只读账号**，不要图方便用写账号；
- 这套工具**只能查测试环境**，线上问题请走运维/监控体系；
- 如果谁把 `profiles.json` 或 `env.sh` 误提交了，立刻改密码 —— 这两个文件本身设计上就不该进版本库。
