# 日志排查 MCP 设计方案

- 日期：2026-10-13
- 范围：`mcp-servers/business-diagnostic-mcp` 扩展，新增「日志查询」与「Apollo 配置读取」能力
- 状态：设计已确认，待编写实现计划

## 1. 背景与目标

排查线上/测试问题时，代码与数据都已在手，但**日志需要人工去表里翻**：日志统一落在 MySQL `test_log` 表，只保留约 2 小时，查询必须带 `service_name`（最左索引列）。目标是把这件事变成「对 Codex 说一句『帮我查下日志』就能自动完成」，并支持顺带读取 Apollo 配置辅助判断（如某开关是否打开）。

关键事实（来自代码核实）：

- 日志写入方：`TestLogDbAppender`（Log4j2 Appender，异步 INSERT 到 `test_log`），非 prod 环境 + Apollo 开关 `test.log.db.enabled` 命中才注册到 root logger。
- 表结构：`id, service_name, pod, log_time, trace_id, log_level, content, ctime, utime`。
- `content` 是整行文本，pattern 为：
  `%d{yyyy-MM-dd HH:mm:ss.SSS} [%t] %-5level - traceId:[%X{traceId}] %c{36} -- %m%ex%n`
  → **traceId 前缀为 `traceId:[`，可正则提取**。
- traceId 来源：HTTP 请求由 `TraceIdFilter` 取请求头 `X-Trace-Id` 或生成 UUID；job/MQ 由 `MDCUtil.start()` 生成（MQ 消费直接用 `msgId` 当 traceId）。
- **业务表不存 traceId**（所有 PO/SQL 均无该字段），因此「业务标识 → traceId」只能靠日志内容检索完成，不做业务表映射。
- 保留策略：xxl-job `testLogCleanupJob` 平时滚动删 2h 前数据、每天 02:00 整表 TRUNCATE → 只能排查最近约 2 小时。
- 索引：`idx_service_time(service_name, log_time)`、`idx_trace`、`idx_log_time`、`idx_content`(FULLTEXT)。

## 2. 总体形态

在现有 `business-diagnostic-mcp` **内部扩展**（不新建独立项目），以 Codex plugin 形式交付：

```
business-diagnostic-mcp/
├── .codex-plugin/plugin.json
├── .mcp.json
├── profiles.example.json
├── skills/
│   ├── business-data-diagnostics/SKILL.md   （现有）
│   └── log-diagnostics/SKILL.md             （新增，显式入口）
└── src/main/java/.../
```

理由：复用现有 stdio 传输层、`ProfileStore`、`SqlBuilder` 只读安全机制与 `Audit`；避免复制约 250 行通用件。

Skill 作为**显式入口**：description 限定「仅在用户明确要求排查/查询日志时使用」，避免被隐式触发。

## 5. 工具定义

新增 3 个工具（工具总数 8 → 11）；为省 token，MCP 配置用 `enabled_tools` 只暴露日志相关工具（见第 9 节）。

### 5.1 `list_log_environments`

无参数或仅用于发现。返回：`defaultEnvironment`、环境列表、服务别名 → `service_name` 映射。避免模型瞎猜服务名。

### 5.2 `query_logs`

统一日志查询入口。

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `env` | 否 | 环境名，默认 `defaultEnvironment` |
| `service` | 否 | `api/job/mq/otp` 或全名；**不传 → 4 个服务一起查**；模型能判断则自动选，判断不了则全查 |
| `traceId` | 否 | 与 `keyword` 至少给一个 |
| `keyword` | 否 | `content LIKE %kw%`，如模板名 / 手机号 / 任务ID |
| `logLevel` | 否 | 精确匹配 `DEBUG/INFO/WARN/ERROR` |
| `timeStart` / `timeEnd` | 否 | 毫秒时间戳；**都不传 → 默认近 20 分钟** |
| `limit` | 否 | 默认 200，上限 1000 |
| `order` | 否 | 默认按 `logTime` 升序 |

返回：

- `rows`：`id, serviceName, pod, logTime, traceId, logLevel, content`
- `matchedTraceIds`：从命中行 content 提取的 traceId，按命中次数排序去重
- `serviceHits`：各服务命中数
- `hasMore`：是否还有更多

**两段式编排（内建）**：

1. 给了 `traceId` → 直接按 traceId 查询（可跨服务），时间窗默认近 20 分钟（可显式放宽）。
2. 只给 `keyword` → 在时间窗内做 `content LIKE` 检索，同时返回 `matchedTraceIds`；模型可据此二次调用（`traceId` 模式）拉出完整链路。
3. 两个都不给 → 直接报错（防止大表全扫）。

### 5.3 `get_apollo_configs`

完全对齐 `TestLogServiceImpl#getAllApolloConfigs` 的实现方式。

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `env` | 否 | 环境名，默认 `defaultEnvironment` |
| `namespace` | 否 | 不传 → 该环境配置的全部 namespace |
| `keyKeyword` | 否 | 按 key 模糊过滤 |

返回：`namespace / key / value` 列表；`comment` 恒为空（apollo-client 运行态不暴露注释，与接口一致）。

实现要点：

- 用 apollo-client SDK：通过系统属性注入 `app.id`、`apollo.meta`（若配了 `accessKeyEnv` 且环境变量存在，则同时注入 `apollo.accesskey.secret`）后，`ConfigService.getConfig(namespace)` → `getPropertyNames()` → `getProperty(key, "")`。apollo-client 也支持 `META-INF/app.properties`，本项目统一走系统属性/环境变量。
- 逐 namespace try/catch：单个 namespace 失败记 warning 并跳过，不影响其它。

## 6. 查询编排与默认值（汇总）

- 默认时间窗：**近 20 分钟**（未显式给时间时），保证走 `idx_service_time`。
- `service` 未指定：4 个服务全查（用 `service_name IN (...)`，仍走索引最左列）；4 个值远小于 500，无需分批，但复用 `SqlBuilder` 的 IN 分批能力作为兜底。
- `keyword` 检索依赖 `service_name` + `log_time` 先收窄，再做 content 过滤（与接口注释里的策略一致）。
- 排序默认 `log_time` 升序，便于按时间线阅读。

## 7. 安全与只读性

- 不接收任何原始 SQL；只由 `SqlBuilder` 生成 `SELECT / COUNT / EXPLAIN`。
- 表名/列名/排序字段：正则 `^[A-Za-z_][A-Za-z0-9_]*$` 校验 + 反引号包裹。
- 操作符白名单：`eq/ne/gt/gte/lt/lte/like/in/notIn/isNull/isNotNull`。
- 值全部 JDBC 参数绑定（`?`），无字符串拼接。
- 连接层：`SET SESSION TRANSACTION READ ONLY` + `connection.setReadOnly(true)`；单查询超时 5s；`limit ≤ 1000`；`offset ≤ 10000`。
- 表白名单：`test_log`（+ 现有表）；拒绝未授权表。
- 不提供任何写工具。
- **脱敏：本期不做**（`content` 里手机号等为排查关键信息，保留原文）；`Masking` 现有字段级掩码对新增日志工具不启用。

## 8. 错误处理

- 服务别名无法解析 → 报错并列出可用别名。
- `traceId` 与 `keyword` 都未提供 → 明确报错。
- Apollo 不可达 / 单 namespace 失败 → warning + 跳过，不整体失败。
- MySQL 连接失败（含 mock 配置）→ 返回清晰错误信息，不崩溃。

## 9. Token 控制（显式调用 + 省 token）

原则：**两类能力（日志排查、业务数据查询）都只在用户明确要求时才使用**，且默认不把全部工具塞进工具目录。

### 9.1 Skill 层：显式触发

- Skill 走渐进式披露：平时只加载 `name + description`，`SKILL.md` 正文仅在被选中时读取。
- 两个 skill 的 description 都写死「仅当用户明确要求 … 时使用」：
  - `log-diagnostics`：仅在用户明确要求**排查/查询日志**时使用。
  - `business-data-diagnostics`（现有）：**同样只在用户明确要求时才使用**。需要改两处：
  1. frontmatter `description` 改成 `Use ONLY when ...` 的措辞（去掉现在这种"可用于检查业务数据"的宽泛描述）；
  2. 正文最前面加一段 `When to use / When NOT to use`：只有在用户明确说"查一下业务数据 / 看下某张表 / 诊断这条记录 / 看下表结构"时才调用；
     用户没提到数据/表/记录时**不要**主动调用，也不要为了"先看一眼"而调用；日志排查走 `log-diagnostics`，不走这个 skill。
  3. 正文里的 MySQL/Mongo 示例保留，但定位为"被明确要求后按需查阅"，不作为默认动作。
- 注意：Codex 没有强制的"仅显式调用"开关，触发可靠性靠 description + 正文约束；真正的兜底是第 9.2 节的工具白名单。

### 9.2 MCP 层：enabled_tools 收敛工具目录

MCP 工具 schema 会常驻工具目录，因此用 `enabled_tools` 只暴露必要工具：

- 暴露（8 个）：日志 3 个（`list_log_environments`、`query_logs`、`get_apollo_configs`）+ 业务查询 5 个（`list_profiles`、`get_schema`、`query_mysql`、`count_mysql`、`explain_mysql`）。
- 默认不暴露（3 个，本项目暂无用例，需要时一行配置加回）：`query_mongo`、`count_mongo`、`explain_mongo`。

```jsonc
// .mcp.json（示意）
{
  "mcpServers": {
    "business_diagnostic": {
      "command": "bash",
      "args": ["scripts/run.sh"],
      "enabled": true,
      "enabled_tools": [
        "list_log_environments", "query_logs", "get_apollo_configs",
        "list_profiles", "get_schema", "query_mysql", "count_mysql", "explain_mysql"
      ]
    }
  }
}
```

### 9.3 环境范围：仅测试环境（硬约束）

线上问题**不使用**本 MCP，两个层面同时约束：

1. **Skill 层**：两个 skill 的 description 与正文都写明「仅测试环境」；用户提到线上/生产/prod 问题时，
   模型应直接说明「本工具只覆盖测试环境」并停止，不调用 `query_logs` / `get_apollo_configs` / 业务查询工具。
2. **代码层（无绕过开关）**：
   - `ProfileStore` 解析 `logDiagnostic.environments` 时，**不加载**名字含 `prod` 的条目，
     只把它们记进 `blockedEnvironments`（避免因为配置里混入生产条目导致整个 MCP 起不来）；
   - `LogConfig.requireEnvironment` 对 blocked 环境名以及任何含 `prod` 的环境名，无条件抛
     `IllegalArgumentException`（"Production environment is not allowed"），
     因此即使有人手工传 `env: "idn-prod"` 也拿不到数据；
   - `list_log_environments` 会返回 `blockedEnvironments` 与对应 warning，说明为什么该环境不可用；
   - 实现时曾考虑加 `allowProduction` 开关，因与「仅测试环境」冲突而**明确不做**，且刻意不提供任何绕过入口；
   - 注意 `prod` 判定基于环境名子串；后续新增环境请沿用测试环境命名（如 `idn-test` / `ng-em-test`）。

### 9.4 极端场景

如需把常驻 token 压到接近 0，可平时 `enabled: false`，使用时再开（代价：skill 单独无法工作）。

## 10. 测试

  - 服务别名解析（含全名直传、无法解析报错、多服务展开）。

## 11. 分享给同事

1. MCP 项目提交到 `mcp-servers` git 仓库；同事 clone 后 `mvn -DskipTests package` 生成 jar。
2. Skill 随 plugin 分发；团队级 skill 也可放仓库 `.agents/skills/`。
3. 同事装 plugin 即自动挂载 MCP（可用 `plugins.<plugin>.mcp_servers.enabled` 本地覆盖）。
4. 每人自配 `profiles.json`（DB 凭证、Apollo meta/appId）；凭证不入库。
5. 提醒：Apollo meta 为内网地址，需在内网/VPN 使用。

## 13. 决策记录

| 议题 | 决策 | 理由 |
| --- | --- | --- |
| 数据获取路径 | 直连（MCP 自连 MySQL + Apollo SDK） | 不依赖 CRM 部署、无 SSO 鉴权、能力不受接口限制 |
| 交付形态 | 扩展现有 business-diagnostic-mcp | 复用传输层与只读安全设施，一个 MCP 打通 |
| 业务标识 → traceId | 纯日志两段式（content 检索 → 提取 traceId → 按 traceId 查） | 业务表不存 traceId |
| 服务名 | 4 个服务；未指定则全查；支持 api/job/mq/otp 别名 | 沟通习惯 |
| Apollo 读取 | apollo-client SDK，对齐 `getAllApolloConfigs` | 忠实复刻运行态 |
| Apollo namespace | 按各环境 bootstrap 声明 | 与运行态一致（接口硬编码列表与实际不符） |
| 环境范围 | 本期仅 idn-test，留 TODO | 先跑通一个环境 |
| MySQL 配置 | 先 mock | 暂无只读账号 |
| 默认时间窗 | 近 20 分钟 | 保证走索引 |
| 脱敏 | 不脱敏 | 排查优先 |
| 环境范围 | 仅测试环境；线上问题不使用；代码层无条件硬拦生产环境（无绕过开关） |
| Token 控制 | 两个 skill（日志 + 业务数据）均限定"仅显式要求时使用" + enabled_tools 只暴露必要工具
（日志 3 + 业务 MySQL 5；Mongo 3 个默认不暴露） | 省 token，且按需使用 |
