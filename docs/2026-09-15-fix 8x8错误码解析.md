## 1. 背景与问题

### 1.1 现象

- 收到打点告警（指标 `whatsapp_crm_message_status_receive`，告警按 `task_id / agentName / code` 聚合统计成功率），例如任务 31、线路 EIGHTX802 维度下成功率=0。
- 从 MongoDB `message_record` 查到的失败消息，8x8 原始回调（`third_status_extra`）中带明确错误码：
  - `status.errorCode = 1018`（8x8 层：Message undeliverable）
  - `whatsapp.providerErrorCode = 131026`（Meta/WhatsApp 层）
  - `status.detail = rejected_by_operator`
- 但告警规则已排除 `code="131026"`，告警仍然命中。

### 1.2 根因

告警指标 `whatsapp_crm_message_status_receive` 的 `code` 标签由 `OpayMessageService.getErrorCode(opayMessage)` 生成：

```java
"code", opayMessageService.getErrorCode(opayMessage) == null
        ? "empty" : String.valueOf(opayMessageService.getErrorCode(opayMessage))
```

而 `getErrorCode()` 最终调用 `getErrorCodeFromThirdStatusExtra(agent, messageId, thirdStatusExtra)`，该方法**目前只实现了 NXCLOUD / ADA / YCLOUD / GPI 四个渠道的分支，没有 EIGHTX8 分支**，8x8 渠道恒返回 null：

```java
if (AgentEnum.NXCLOUD.getName().equals(agent)) { ... }
else if (AgentEnum.ADA.getName().equals(agent)) { ... }
else if (AgentEnum.YCLOUD.getName().equals(agent)) { ... }
else if (AgentEnum.GPI.getName().equals(agent)) { ... }
// EIGHTX8：无分支 → 返回 null → 打点 code="empty"
```

结论：

- 8x8 渠道的所有状态回调（无论发送失败还是投递失败）在 `whatsapp_crm_message_status_receive` 指标上的 `code` 标签**恒为 `empty`**；
- 告警排除 `code="131026"` 无效，因为该值根本不会出现在此指标的 `code` 标签中；
- 现有告警无法按 8x8/Meta 错误码区分失败类型（如"用户不可达"vs"模板/线路问题"）。

## 3. 方案 A：给 getErrorCodeFromThirdStatusExtra 增加 EIGHTX8 分支

### 3.1 目标

1. 让 `whatsapp_crm_message_status_receive` 指标的 `code` 标签带上 8x8/Meta 错误码，不再恒为 empty；
2. 使告警排除条件（如 `code!="131026"`）真实生效；
3. 支持按错误码维度统计失败构成、区分失败类型。

### 3.2 修改点

文件：`whatsapp-crm-data/src/main/java/com/opay/occ/whatsapp/data/agent/opay/impl/OpayMessageServiceImpl.java`

方法：`getErrorCodeFromThirdStatusExtra(String agent, String messageId, JSONObject thirdStatusExtra)`

在现有 GPI 分支后增加 EIGHTX8 分支，解析 `third_status_extra`（即 8x8 原始回调 JSON）：

- **解析路径（优先级从高到低，已确认）**：
  1. `payload.whatsapp.providerErrorCode`（Meta 层，如 131026）——**优先取此值**
  2. `payload.status.errorCode`（8x8 层，如 1018）
  3. `payload.error.code`（8x8 legacy 格式）
  4. 都为空 → 返回 null（打点保持 empty）
- **返回类型**：与现有方法一致，返回 `Integer`。
  - `whatsapp.providerErrorCode` 是字符串（"131026"），需 `Integer.valueOf` 安全转换（捕获 NumberFormatException，失败则跳过）；
  - `status.errorCode` 本身就是数字（1018），直接取值；
  - 遗留 `error.code` 可能是字符串，同样做安全转换。

### 3.3 为什么取 providerErrorCode（131026）优先——参考其他通道

`getErrorCodeFromThirdStatusExtra` 现有各渠道均取 **status 回调中最具体的第三方业务错误码**（而非通道通用码）：

| 渠道 | 取值字段 | 说明 |
|---|---|---|
| NXCLOUD | `status.errors[0].code` | 配置 `nxFailedMetaCodeList` 时，命中则改用 `error.meta_code`（更具体） |
| ADA | `data.failedReasonCode` | 直接取失败原因码 |
| YCLOUD | `whatsappMessage.errorCode` | 直接取错误码 |
| GPI | `status.errors[0].code` | 取第一条 error 的 code |

8x8 同一条失败会同时带两个码：

- `status.errorCode = 1018`：8x8 层通用码（Message undeliverable），粒度粗；
- `whatsapp.providerErrorCode = 131026`：Meta/WhatsApp 提供商标识码，粒度细（如用户不可达/被运营商拒），**与告警排除目标一致**。

因此 EIGHTX8 分支按"最具体的第三方业务错误码"的原则取 `whatsapp.providerErrorCode` 优先，与 NXCLOUD 优先 meta_code 的做法一致。**已与需求确认：取 131026（providerErrorCode 优先）**，用户现有告警排除 `code!="131026"` 即可生效。

### 3.4 需要注意的兼容性

- 只新增 EIGHTX8 分支，不改变 NXCLOUD / ADA / YCLOUD / GPI 现有逻辑，风险低；
- 该方法同时被两处使用：
  1. `executeUpdateReplyStatus()`：写 Mongo 字段 `msg_error_code`（8x8 之前一直为空，补齐后该字段开始有值）；
  2. `getErrorCode()`：MQ 消费打点 `whatsapp_crm_message_status_receive.code`（本方案核心收益）。
- 补充后 8x8 的 `msg_error_code` 字段也会被填充（此前为空），查询 `message_record` 时可通过 `msg_error_code` 直接筛错误码；
- `third_status_extra` 为 null 或解析异常时保持返回 null，打点不变为 empty，不影响其他逻辑。

## 4. 验证计划（实施后执行）

1. **单元/集成验证**：
   - 构造 8x8 v9 失败回执（`whatsapp.providerErrorCode=131026` + `status.errorCode=1018`），验证 `getErrorCodeFromThirdStatusExtra("EIGHTX8", ...)` 返回 **131026**；
   - 构造仅有 `status.errorCode=1018`（无 providerErrorCode）的失败回执，验证返回 1018；

   - 验证 NXCLOUD/ADA/YCLOUD/GPI 分支无回归。
2. **Mongo 验证**：新失败消息 `msg_error_code` 为 131026，与 `third_status_extra.whatsapp.providerErrorCode` 一致；旧数据不受影响（不追溯）。

4. **告警验证**：确认现有排除 `code!="131026"` 后，131026 类失败不再拉低成功率；其他失败（如 1018 无 provider 码、empty）仍可告警。
