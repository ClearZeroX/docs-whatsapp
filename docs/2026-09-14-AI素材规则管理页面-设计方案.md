# AI 素材规则管理页面 设计方案

- 日期：2026-09-14
- 模块：AI 素材建议规则（`ai_material_suggestion_rule`）管理
- 范围：后端接口 + 数据模型 + 前端原型（本次不做代码实现，代码实现另有实现计划）

## 1. 背景与目标

当前 AI 素材建议规则存放在 Apollo 配置 JSON 中，由 XXL-Job `AiMaterialSuggestionRuleImportJob`
定期 upsert 到数据库表 `ai_material_suggestion_rule`（按 `rule_code` 覆盖）。
规则维护只能改配置 JSON，缺少可视化 CRUD、启停、历史追溯能力。

本次目标：

1. 规则数据源改为 **DB 为准**，提供管理页面对规则进行增删改查（删除=停用）。
2. job 保留作**兜底**，改为手动触发，保留导入逻辑并新增 **enable / disable** 两个动作。
3. 增加**操作日志表**，支持“规则列表 → 历史记录 → 历史明细（字段级 before/after 对比展示）”。

## 2. 需求定稿（决策清单）

| 项 | 决策 |
|---|---|
| 数据源 | DB 为准，页面直接改库 |
| 版本管理 | 不加 `version` 字段，规则原位修改，`rule_code` 保持唯一 |
| 是否可用 | 复用现有 `enabled` 字段（1=可用 / 0=不可用），不新增 `status` 列 |
| 删除语义 | 不物理删除，统一为“停用（disable，置 enabled=0）” |
| 操作日志 | 增加日志表，`change_detail` 存字段级 before/after |
| 历史明细 | 只做对比展示，不做回滚 |
| job | 手动执行；IMPORT（现有 upsert）+ ENABLE + DISABLE |
| job/页面批量过滤 | `rule_code`、`suggest_type`、`source_lane`，均为 list |
| 页面导入/导出 | 支持 JSON 导入、导出 |

## 4. 数据模型

### 4.1 规则表 `ai_material_suggestion_rule`

保持现有结构不变，关键点：

- `enabled` 复用作“是否可用”；
- 保留唯一键 `uk_rule_code(rule_code)`；
- 不新增 `version`、`status`、`deleted` 字段。

### 4.2 新增操作日志表 `ai_material_suggestion_rule_log`

```sql
CREATE TABLE `ai_material_suggestion_rule_log` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT 'primary key',
  `rule_id` bigint(20) NOT NULL DEFAULT 0 COMMENT 'rule id',
  `rule_code` varchar(64) NOT NULL DEFAULT '' COMMENT 'rule code',
  `action` varchar(16) NOT NULL DEFAULT '' COMMENT 'CREATE/UPDATE/ENABLE/DISABLE',
  `source` varchar(16) NOT NULL DEFAULT '' COMMENT 'PAGE/JOB',
  `operator` varchar(64) NOT NULL DEFAULT '' COMMENT 'operator',
  `change_detail` text COMMENT 'field-level changes JSON array [{"field","from","to"}]',
  `create_time` bigint(20) NOT NULL DEFAULT '0' COMMENT 'create time',
  `update_time` bigint(20) NOT NULL DEFAULT '0' COMMENT 'update time',
  PRIMARY KEY (`id`),
  KEY `idx_rule_id` (`rule_id`),
  KEY `idx_rule_code` (`rule_code`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='AI material suggestion rule operation log';
```

`change_detail` 约定：

- `CREATE`：记录初始值，`from=null`，`to=初值`；
- `UPDATE`：只记录发生变化字段的 `from/to`；`ruleContent` 的 `from/to` 存完整正文 JSON，便于前后对比；
- `ENABLE` / `DISABLE`：记录 `{"field":"enabled","from":0,"to":1}` 或反向。

`action` 取值：`CREATE / UPDATE / ENABLE / DISABLE`。
`source` 取值：`PAGE`（页面操作）/ `JOB`（job 兜底操作）。

## 5. 服务层设计（AiMaterialSuggestionRuleService）

保留现有 `querySnapshot / page / importFromConfig`，新增：

| 方法 | 说明 |
|---|---|
| `detail(id)` | 查询完整详情（含 ruleContent、全部字段），用于编辑回显 |
| `queryEnums()` | 返回枚举字典（sourceLane/materialType/suggestType/ruleSource/ruleType） |
| `createRule(saveDTO, operator, source)` | 校验 code 唯一、枚举/JSON 合法；插入规则 + 写日志(CREATE) |
| `updateRule(saveDTO, operator, source)` | 读旧值 → 计算字段 diff → 更新 + 写日志(UPDATE) |
| `enableRules(filterDTO, operator, source)` | 批量置 enabled=1 + 逐条写日志(ENABLE) |
| `disableRules(filterDTO, operator, source)` | 批量置 enabled=0 + 逐条写日志(DISABLE) |
| `deleteRules(filterDTO, operator, source)` | 按条件物理删除规则 + 逐条写 DELETE 日志（job 使用） |
| `importFromConfig(json, operator, source)` | JSON 数组 upsert + 写日志（job 与页面导入共用）；页面导入时 rule.operator 设置为当前操作人 |
| `exportRules(filterDTO)` | 按条件导出 JSON 数组 |
| `historyPage(...)` | 历史记录分页查询 |
| `historyDetail(logId)` | 历史明细（返回解析后的 change_detail） |

字段 diff 规则：对以下可编辑字段比较 `ruleName / sourceLane / materialType / suggestType / ruleSource / ruleType / ruleContent / priority / enabled / operator`，只记录有变化的字段。`ruleContent` 以整体字符串比较。

关键约束：

- 主表写操作与日志写入**同一事务**，保证历史不丢；日志按 `rule_id` 关联查询。
- `ruleCode` 由 `uk_rule_code` 保证唯一，创建时重复则返回业务错误。

## 6. 接口设计

修改 `AiMaterialSuggestionController`（前缀 `/dev/api/ai-suggestion` 不变）。

| 接口 | 说明 |
|---|---|
| `POST /rule/page` | 规则分页查询（扩展查询条件） |
| `GET /rule/enums/dict` | 枚举字典（materialType/suggestType/ruleSource/ruleType），供筛选下拉与表单使用 |
| `GET /rule/detail` | 规则详情 |
| `POST /rule/create` | 新增规则 |
| `POST /rule/update` | 编辑规则 |
| `POST /rule/enable` | 批量启用 |
| `POST /rule/disable` | 批量停用 |
| `POST /rule/import` | JSON 导入 |
| `POST /rule/export` | JSON 导出 |
| `POST /rule/history/page` | 历史列表 |
| `POST /rule/history/detail` | 历史明细（含 change_detail） |

### 6.1 规则分页查询

新增/扩展 `AiSuggestionRulePageReqDTO`：

- `id`（可选精确）
- `ruleCode`（模糊）、`ruleName`（模糊）
- `sourceLane`、`materialType`、`suggestType`、`ruleSource`、`ruleType`（可选精确）
- `enabled`（可选 1/0）
- `pageNo`、`pageSize`

响应 `AiSuggestionRuleRespDTO` 扩展返回：`id、ruleCode、ruleName、sourceLane、materialType、suggestType、ruleSource、ruleType、priority、enabled、operator、createTime、updateTime、ruleContent`（列表同样返回 ruleContent 完整正文）。

排序：按 `updateTime` 倒序。

### 6.2 规则保存

`AiSuggestionRuleSaveReqDTO`：

- `id`（编辑时必填）
- `ruleCode`（创建必填，编辑只读）
- `ruleName`（必填）
- `sourceLane`、`materialType`、`suggestType`、`ruleSource`、`ruleType`（必填，枚举校验）
- `ruleContent`（必填，合法 JSON 对象字符串）
- `priority`（整数，默认 0）
- `enabled`（Integer，1/0；响应 DTO 中转为 Boolean）

### 6.3 批量启用/停用

`AiSuggestionRuleBatchReqDTO`：

- `ids`（页面勾选行，List<Long>）
- `ruleCodes`（List<String>）
- `suggestTypes`（List<String>）
- `sourceLanes`（List<String>）

约定：

- 页面批量操作：至少传 `ids` 或过滤条件之一，不允许“空=全量”造成误操作。
- job 动作：过滤 list 为空 = 全量。

### 6.4 历史

`history/page` 请求：`ruleId`（必填）、`action`（可选）、`source`（可选）、`pageNo`、`pageSize`。
`history/detail` 请求：`logId`。

`history/detail` 响应包含：`id、ruleCode、action、source、operator、createTime、changeDetail`（JSON 数组对象，前端用于渲染对比表）。

### 6.5 枚举字典

`GET /rule/enums/dict`，无入参，返回规则相关枚举，供前端筛选区和新增/编辑弹窗下拉使用。

响应示例：

```json

    { "code": "MARKETING_CHAT", "desc": "MARKETING_CHAT" },
    { "code": "UTILITY", "desc": "UTILITY" },
    { "code": "ALL", "desc": "ALL" }
  ],
  "materialTypes": [
    { "code": "BODY", "desc": "Body" }
  ],
  "suggestTypes": [
    { "code": "GENERAL", "desc": "General suggestion" },
    { "code": "COST_FIRST", "desc": "Cost first suggestion" },
    { "code": "AI_BACKUP_MATERIAL_GROUP", "desc": "AI backup material group" }

  "ruleSources": [
    { "code": "BUSINESS", "desc": "Business-sourced rule" },
```

## 7. Job 设计

`AiMaterialSuggestionRuleImportJob` 保留单 handler，通过 param 传 JSON 区分动作：

```json
{"action":"IMPORT"}
{"action":"ENABLE","ruleCodes":["..."],"suggestTypes":["..."],"sourceLanes":["..."]}
{"action":"DISABLE","ruleCodes":["..."],"suggestTypes":["..."],"sourceLanes":["..."]}
{"action":"DELETE","ruleCodes":["..."],"suggestTypes":["..."],"sourceLanes":["..."]}
```

规则：

- `action` 缺省为 `IMPORT`（向后兼容，现有行为不变）。
- `IMPORT`：读取 `BusinessConfig.aiSuggestionRuleImportJson`，按 `rule_code` 有则更新、无则新增，并逐条写日志（`source=JOB`，action=CREATE/UPDATE）。
- `ENABLE` / `DISABLE`：复用服务的 `enableRules/disableRules`，写日志（`source=JOB`）；过滤 list 为空 = 全量。
- `DELETE`：物理删除，删除前写 `DELETE` 日志（`source=JOB`）；过滤 list 为空 = 全量。
- MySQL `in` 批量查询按 AGENTS 要求分批执行，避免超大 in。

## 8. 前端原型设计

### 8.1 规则管理页

顶部筛选区（查询条件）：

- `ruleCode`（模糊）、`ruleName`（模糊）
- `sourceLane`、`materialType`、`suggestType`、`ruleSource`、`ruleType`（下拉）
- `enabled`（可用/不可用）
- 查询、重置按钮

工具区：`新增规则`、`批量导入 JSON`、`导出 JSON`、`批量启用`、`批量停用`

表格列：

`勾选`、`ruleCode`、`ruleName`、`sourceLane`、`materialType`、`suggestType`、`ruleSource`、`ruleType`、`priority`、`enabled（开关）`、`operator`、`updateTime`、`操作`

操作列：

- `编辑`（打开编辑弹窗）
- `历史`（打开历史面板）
- `启用/停用`（单条开关）

### 8.2 新增/编辑弹窗

字段：

- `ruleCode`：创建可填（唯一校验），编辑只读
- `ruleName`
- `sourceLane`、`materialType`、`suggestType`、`ruleSource`、`ruleType`（下拉）
- `priority`（数字）
- `enabled`（开关）
- `ruleContent`（三语 Tab 编辑，见 8.4）

### 8.3 历史面板

- 规则列表点【历史】→ 弹出该规则变更记录列表：
  - 列：`action`、`source`、`operator`、`createTime`、`涉及字段数`
- 点某条记录 → 历史明细页：

  - 顶部：ruleCode、action、source、operator、createTime
  - 中部：字段级 before/after 左右对比表（字段名 | 改前 | 改后）
  - `ruleContent` 字段：展示“旧正文 vs 新正文”两侧对比（各语言 Tab 分组）

### 8.4 ruleContent 三语 Tab（按环境）

前端根据运行环境决定展示三语 Tab：

| 环境 | 三语 Tab |
|---|---|
| 印尼（Indonesia） | `zh_CN` / `en_US` / `id` |
| 尼日利亚（Nigeria） | `zh_CN` / `en_US` / `en_GB` |

说明：

- `ruleContent` 在后端存合法 JSON 对象字符串，语言键集合为 `{zh_CN, en_US, id, en_GB}` 的子集；
- 前端按环境用三个输入框（Tab）编辑对应语言字段，保存时组装为 JSON 对象提交；
- 后端仅校验其为合法 JSON 对象，语言键是否齐全由前端按环境约束。

- 列表列：action、source、operator、createTime、涉及字段数、操作（查看明细）。
- 点击【查看明细】→ 当前弹窗切换为「历史明细对比」视图，可返回。

## 9. 错误处理

- `ruleCode` 重复：创建时返回业务错误，前端提示。
- 枚举值非法：保存前校验拦截。
- `ruleContent` 非法 JSON / 非对象：保存前校验拦截。
- 批量启用/停用：页面场景不允许“空条件=全量”，防止误操作。
- 导入部分失败：返回“成功 N 条 / 跳过 M 条”及跳过原因。
- 主表操作与日志写入同一事务；日志失败则主操作回滚。
