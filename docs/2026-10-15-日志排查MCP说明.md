# 日志排查 MCP 说明

> **这是什么**：一个挂在 Codex 上的日志排查能力。在 Codex 里说一句「帮我查下日志」，它就会自动去测试环境的 `test_log` 表里检索日志、按 traceId 还原完整请求链路，必要时再读 Apollo 配置辅助判断。
>
> **本文档分三部分**：
> 一、[项目说明](#一项目说明)（做什么 / 怎么做 / 怎么改）
> 二、[本地使用说明](#二本地使用说明)（要配置什么、配置流程）
> 三、[分享给其他人使用](#三分享给其他人使用)

---

# 一、项目说明

## 1.1 能力概览

| 能力 | 说明 |
| --- | --- |
| 按 traceId 查日志 | 直接拉出某次请求的完整日志链路 |
| 按关键词查日志 | 用手机号、任务ID、模板名、报错文本等模糊检索日志正文 |
| **无关键词自动排查** | 用户只描述现象（如「素材生成图片一直失败」）时，**自动读业务代码推导出关键词和服务名**再查 |
| 按服务/级别/时间过滤 | 支持 api/job/mq/otp 四个服务、DEBUG~ERROR 级别、自定义时间窗 |
| 读 Apollo 配置 | 读取运行态 Apollo 配置（开关、阈值等），与业务服务看到的完全一致 |
| 附带业务数据查询 | 只读查 MySQL 表结构 / SELECT / COUNT / EXPLAIN（同一套只读安全机制） |

**只做测试环境。** 线上 / 生产问题会被拒绝，且没有任何绕过开关（见 1.7）。

## 1.2 术语与组成

| 名词 | 一句话解释 |
| --- | --- |
| **MCP** | Model Context Protocol，Codex（客户端）与外部程序（服务端）之间的通话协议 |
| **MCP Server** | 真正干活的后台进程 `business-diagnostic-mcp`，通过标准输入输出收发 JSON-RPC |
| **Tool（工具）** | MCP Server 对外暴露的可调用能力，例如 `query_logs` |
| **Skill（技能）** | 一段**给 AI 看的操作手册**（`SKILL.md`，纯文字，无可执行代码），规定「什么时候用、按什么顺序用、什么不能做」 |
| **Plugin（插件）** | 打包分发单位 = MCP Server 声明（`.mcp.json`）+ Skill + 元数据（`.codex-plugin/plugin.json`） |
| **Marketplace** | 插件货架清单，告诉 Codex 去哪里安装插件 |

组成与串联关系：

```text
marketplace.json ──codex plugin add──▶ 插件
                                        │
                          config.toml ──┤ enabled = true
                                        ▼
   plugin.json ──声明──▶ .mcp.json ──启动──▶ run.sh ──▶ java -jar ──▶ MCP Server（11 个工具）
                └─声明──▶ skills/  ──装进会话──▶ AI 看到的操作手册（Skill）

AI 在会话里同时拿到：① 能调什么工具 + ② 该怎么调
```

## 1.3 工作原理

### 1.3.1 日志数据源

- 日志落在 MySQL 表 **`test_log`**，字段：
  `id, service_name, pod, log_time, trace_id, log_level, content, ctime, utime`
- 索引：`idx_service_time(service_name, log_time)`、`idx_trace`、`idx_log_time`、`idx_content`（FULLTEXT）
- **只保留约 2 小时**（xxl-job 平时删 2 小时前数据，每天 02:00 整表清空），所以只能排查最近 2 小时。
- 查询必须带 `service_name`（最左索引列），因此即使「4 个服务全查」，也是 4 条带索引的查询。
- 是否写入该表由 Apollo 开关 `test.log.db.enabled` 控制（非 prod 环境 + 开关打开才有数据）。

### 1.3.2 日志行格式

`content` 是整行文本，格式与代码里的 log4j2 配置一致：

```text
%{yyyy-MM-dd HH:mm:ss.SSS} [%t] %-5level - traceId:[%X{traceId}] %c{36} -- %m%n
```

实际长这样：

```text
2026-10-15 10:12:33.482 [http-nio-8080-exec-3] INFO  - traceId:[a1b2c3d4e5f6] c.o.o.w.api...TaskDataController -- PROCESS_CANVAS_API_IMPORT taskData taskId: 1001, phoneNumber: 8613800138000
```

由此得到两条稳定的解析规则（工具内建，无需人工处理）：

- **traceId**：永远位于 `traceId:[...]` 中，正则 `traceId:\[([^\]]*)\]`
- **业务消息**：位于 ` -- ` 之后

### 1.3.3 三种排查入口

业务表**不存 traceId**，所以「业务标识 → traceId」只能靠日志正文检索完成，不做业务表映射。据此有三种入口：

**入口 A：用户给了 traceId** → 直接按 traceId 查（可跨服务），拿到完整链路。

**入口 B：用户给了关键词**（手机号 / 任务ID / 模板名 / 报错文本）

```text
第 1 跳：用关键词在 test_log 里做正文模糊匹配（先按 service_name + log_time 收窄，再过滤正文）
        ↓ 从命中行的 content 中用正则提取 traceId
        ↓ 按命中次数排序去重，返回 top 20 个 matchedTraceIds
第 2 跳：挑一个 traceId 再查一次，拿到该请求的完整日志链路
```

**入口 C：用户没给关键词**（只描述现象）——见下一节。

`traceId` 与 `keyword` 至少要给一个；两者都不给会直接报错（防止大表全扫）。

### 1.3.4 无关键词场景：自动读代码推导关键词与服务名

用户可能只说现象，例如「素材生成图片一直失败」「这个任务没发出去」。此时 **AI 主动去读业务代码，自行推导出服务名和关键词**，不反问用户、不盲目乱搜。

流程：

```text
① 在本地代码仓库里定位与现象相关的类（按业务词 / 控制器名 / 报错文本检索）
        ↓
② 由代码所在模块确定服务名（判不了就 4 个服务全查）
        ↓
③ 从这些类的日志语句里提取「消息模板中的稳定字面片段」作为关键词
        ↓
④ 用推导出的关键词调 query_logs → 拿 matchedTraceIds → 再按 traceId 追完整链路
        ↓
⑤ 简要说明推理过程：查了哪个模块、推出什么关键词、扫了哪些服务
```

**② 服务名判定表**（按模块目录）：

| 代码模块目录 | 服务简名 | `service_name` |
| --- | --- | --- |
| `whatsapp-crm-api` | api | `whatsapp-crm-api` |
| `whatsapp-crm-job` / `whatsapp-crm-job2-1-1` | job | `whatsapp-crm-job` |
| `whatsapp-crm-mq` | mq | `whatsapp-crm-mq` |
| `whatsapp-crm-otp` | otp | `whatsapp-crm-otp` |

> 不能用 `spring.application.name` 判断：多个模块的这个值都是 `whatsapp-crm-api`。
> 权威映射以 `profiles.json` 的 `logDiagnostic.services` 为准。

**③ 关键词提取规则**：代码里的日志都是

```java
log.info("MaterialRAGController.getAsyncGeneratePictureResult taskId={}, cost={}ms", taskId, cost);
```

因此取**模板中不含 `{}` 占位符的连续字面片段**作为关键词：

| 规则 | 说明 |
| --- | --- |
| 优先类名/方法名前缀 | 如 `MaterialRAGController.getAsyncGeneratePictureResult`，最稳定、最不易误命中 |
| 其次业务动作短语 | 如 `PROCESS_CANVAS_API_IMPORT taskData` |
| 避免泛化词 | `failed` / `error` / `success` / `start` / `end` / `null` 之类会命中海量无关日志 |
| 长度适中 | 要能作为渲染后整行的子串，同时足够独特 |
| 多候选时逐个试 | 直到有结果为止 |

**举例**：用户说「素材生成图片失败」→ 在 `whatsapp-crm-api` 里找到 `MaterialRAGController`，其中
`log.info("MaterialRAGController.getAsyncGeneratePictureResult taskId={}, cost={}ms", ...)`
→ 关键词取 `MaterialRAGController.getAsyncGeneratePictureResult`，服务取 `api`（不确定就全查）
→ 用关键词查近 20 分钟日志 → 拿到 traceId → 追完整链路。

### 1.3.5 服务与别名

固定 4 个服务，支持简称，**不指定就全部查**：

| 简名 | `service_name` |
| --- | --- |
| `api` | `whatsapp-crm-api` |
| `job` | `whatsapp-crm-job` |
| `mq` | `whatsapp-crm-mq` |
| `otp` | `whatsapp-crm-otp` |

也支持直接传全名。别名解析不了会报错并列出可用别名。

### 1.3.6 时间窗与默认值

| 项 | 默认值 |
| --- | --- |
| 时间窗 | **最近 20 分钟**（`timeEnd` = 现在，`timeStart` = 20 分钟前） |
| 返回行数 | 200（上限 1000） |
| 排序 | `log_time` 升序（按时间线阅读） |
| 服务 | 不指定 → 4 个服务全查 |

### 1.3.7 Apollo 配置读取

- 使用 **apollo-client SDK**（`com.ctrip.framework.apollo:apollo-client:1.4.0`），对齐业务代码 `TestLogServiceImpl#getAllApolloConfigs` 的读取方式，因此拿到的值和运行中的服务看到的一致。
- 通过系统属性注入 `app.id` / `apollo.meta`；若配置了访问密钥且对应环境变量存在，同时注入 `apollo.accesskey.secret`。
- namespace 按环境在 `profiles.json` 里声明（idn-test 当前 14 个），与 bootstrap 声明保持一致。
- 逐个 namespace 独立 try/catch：单个失败只记 warning 并跳过，不影响其他 namespace。
- 返回结果带 `sources` 字段（`REMOTE` / 其他）。**只要不是 `REMOTE`，说明没真正连上 Apollo 服务端**，同时会写入 `warnings`，避免把本地兜底值误当成远端配置。
- `comment` 字段恒为空：运行时客户端不暴露配置注释。

## 1.4 工具清单

共 11 个工具，Codex 里实际启用 8 个（`enabled_tools` 白名单），Mongo 3 个注册但未暴露，用于省 token。

| 工具 | 用途 | 暴露 |
| --- | --- | --- |
| `list_log_environments` | 列环境、默认环境、服务别名、被拦截的生产环境 | ✅ |
| `query_logs` | 查 `test_log`，支持 traceId / keyword | ✅ |
| `get_apollo_configs` | 读 Apollo 配置 | ✅ |
| `list_profiles` | 列出已配置的数据源 profile | ✅ |
| `get_schema` | 查 MySQL 表结构 | ✅ |
| `query_mysql` | 只读 SELECT 查询 | ✅ |
| `count_mysql` | COUNT 统计 | ✅ |
| `explain_mysql` | EXPLAIN 执行计划 | ✅ |
| `query_mongo` / `count_mongo` / `explain_mongo` | Mongo 查询 | ❌ 未暴露 |

### `query_logs` 参数

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `env` | 否 | 环境名，默认 `defaultEnvironment` |
| `service` | 否 | `api/job/mq/otp` 或全名；**不传 → 4 个服务一起查** |
| `traceId` | 否 | 与 `keyword` 至少给一个 |
| `keyword` | 否 | 日志正文模糊匹配（子串），如模板名 / 手机号 / 任务ID / 类方法名 |
| `logLevel` | 否 | 精确匹配 `DEBUG` / `INFO` / `WARN` / `ERROR` |
| `timeStart` / `timeEnd` | 否 | 毫秒时间戳；都不传 → 近 20 分钟 |
| `limit` | 否 | 默认 200，上限 1000 |
| `order` | 否 | `asc`（默认）或 `desc` |

返回：`rows`（`id/serviceName/pod/logTime/traceId/logLevel/content`）、`matchedTraceIds`（按命中次数排序去重，最多 20 个）、`serviceHits`（各服务命中数）、`hasMore`。

### `get_apollo_configs` 参数

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `env` | 否 | 环境名，默认 `defaultEnvironment` |
| `namespace` | 否 | 不传 → 该环境配置的全部 namespace |
| `keyKeyword` | 否 | 按 key 模糊过滤 |

返回：`namespace / key / value` 列表，以及 `sources` 与 `warnings`。

## 1.5 用法

### 触发方式：仅在你明确要求时使用

三层省 token 设计：

1. `.mcp.json` 的 `enabled_tools` 白名单（Mongo 工具不加载）；
2. 两个 Skill 的 `description` 都写了 `Use ONLY when the user explicitly asks…`，不会被主动触发；
3. `SKILL.md` 正文有 `When to use / When NOT to use` 段落。

平时不会占用你的上下文，只有你开口了才用。

### 典型对话

| 你说 | 会发生什么 |
| --- | --- |
| `查下日志，traceId 是 xxxx` | 直接按 traceId 查，返回完整链路 |
| `看下 138xxxx 这个手机号今天的报错` | 关键词搜（默认跨 4 个服务）→ 返回 matchedTraceIds → 按 traceId 追链路 |
| `这个模板名有没有报错` | 同上，按模板名搜 |
| `查下 mq 服务最近 10 分钟的错误日志` | 限定服务 + 时间窗 + 级别 |
| **`素材生成图片一直失败，帮我看看`** | **不给关键词也行：自动读代码定位模块 → 推出关键词 → 查日志** |
| **`这个任务没发出去，排查下`** | 同上，自动推导服务与关键词 |
| `看下 xxljob.yml 里的开关配置` | 读 Apollo 配置（可用关键词过滤避免刷屏） |
| `列出日志环境` | 确认配置是否加载成功 |

## 1.6 安全设计

| 措施 | 说明 |
| --- | --- |
| 只读连接 | JDBC 会话显式设为只读（`SET SESSION TRANSACTION READ ONLY` + `setReadOnly(true)`） |
| 不接受原始 SQL | 只执行由 `SqlBuilder` / `MongoBuilder` 生成的 `SELECT` / `COUNT` / `EXPLAIN`，所有值走 JDBC 参数绑定 |
| 标识符校验 | 表名/列名/排序字段正则 `^[A-Za-z_][A-Za-z0-9_]*$` 校验 + 反引号包裹 |
| 操作符白名单 | `eq / ne / gt / gte / lt / lte / like / in / notIn / isNull / isNotNull` |
| 表白名单 | 表与集合必须显式列在 `allowedTables` / `allowedCollections` 中 |
| 批量化 | MySQL `IN` 每批 500 个值；Mongo `$in` / `$nin` 上限 500 |
| 查询限流 | 单查询超时 5 秒；`limit ≤ 1000`；`offset ≤ 10000` |
| 无写工具 | 不提供任何写库能力 |
| 审计 | 每次工具调用写一条审计记录 |

## 1.7 约束与限制

| 约束 | 说明 |
| --- | --- |
| **仅测试环境** | 线上 / 生产问题不适用，见下方三层硬约束 |
| 日志只留约 2 小时 | 更早的日志物理上不存在，查不到不是工具的问题 |
| 日志正文不脱敏 | `content` 原样返回（手机号等是排查关键信息）。业务数据表的字段级脱敏仍然生效，仅日志不脱敏 |
| Apollo 单环境 | apollo-client 的 `meta` / `appId` 是**进程级全局配置**，同一进程一次只能连一个环境的 Apollo。多环境并行读取需要为每个环境创建独立 client 实例 |
| 查询必须收敛 | 不支持整表扫描；至少给 `traceId` 或 `keyword` |

**仅测试环境的三层硬约束（无任何绕过开关）**：

1. **配置加载层**：`ProfileStore` 读取 `logDiagnostic.environments` 时，**根本不加载**名字里含 `prod` 的条目，只把它记进 `blockedEnvironments`（这样即使配置里混入生产条目，整个 MCP 也不会起不来）；
2. **调用层**：`LogConfig.requireEnvironment` 对生产环境名无条件抛错 `Production environment is not allowed: xxx ...`，即使手工传 `env: "idn-prod"` 也拿不到数据；
3. **Skill 层**：两个 Skill 的 description 与正文都写明 test-only，用户提到「线上 / 生产 / prod」时 AI 会说明并停止。

`list_log_environments` 会返回 `blockedEnvironments` 和对应 warning，明确告知某环境为什么不可用。

## 1.8 配置模型

`profiles.json` 分两部分：`profiles`（通用数据源）与 `logDiagnostic`（日志排查专用）。**凭证不写在这里**，只写变量名。

```jsonc
{
  "profiles": {
    // 通用只读数据源，供 query_mysql / get_schema 等使用
    "test-mysql": {
      "type": "mysql",
      "host": "127.0.0.1",
      "port": 3306,
      "database": "whatsapp_crm",
      "user": "readonly_user",
      "passwordEnv": "BUSINESS_DIAGNOSTIC_TEST_MYSQL_PASSWORD",
      "allowedTables": ["message_template", "message_material_group", "message_material_combination", "message_material", "task", "task_sub"],
      "sensitiveFields": ["password", "secret", "token", "phone", "mobile", "email", "id_card", "bank_card"]
    },
    "test-mongo": { "type": "mongo", "uriEnv": "...", "database": "...", "allowedCollections": ["..."] }
  },
  "logDiagnostic": {
    "defaultEnvironment": "idn-test",
    "logTable": "test_log",
    "services": {                       // 别名 → service_name
      "api": "whatsapp-crm-api",
      "job": "whatsapp-crm-job",
      "mq":  "whatsapp-crm-mq",
      "otp": "whatsapp-crm-otp"
    },
    "environments": {
      "idn-test": {
        "mysql": {
          "host": "MOCK_IDN_TEST_HOST",     // 待替换为真实地址
          "port": 3306,
          "database": "whatsapp_crm",
          "user": "MOCK_READONLY_USER",     // 待替换为真实只读账号
          "passwordEnv": "LOG_DIAGNOSTIC_IDN_TEST_MYSQL_PASSWORD"
        },
        "apollo": {
          "appId": "whatsapp-crm",
          "meta": "http://10.99.1.187:8080",
          "namespaces": [
            "application", "datasource.yml", "rocketmq.yml", "xxljob.yml",
            "obs.yml", "agent.yml", "logging.properties", "freemarker.properties",
            "aviatorscript.properties", "source.yml", "rabbitmq.yml", "okhttp",
            "llm.yml", "prompt.properties"
          ],
          "accessKeyEnv": "LOG_DIAGNOSTIC_IDN_TEST_APOLLO_ACCESS_KEY"   // 可选
        }
      }
    }
  }
}
```

字段速查：

| 字段 | 作用 |
| --- | --- |
| `defaultEnvironment` | 不指定 `env` 时使用哪个环境 |
| `logTable` | 日志表名 |
| `services` | 服务别名的权威映射；新增服务只需在这里加一行 |
| `environments.<名>.mysql` | 该环境日志库连接；`passwordEnv` 是密码所在的环境变量名 |
| `environments.<名>.apollo` | 该环境 Apollo 坐标与 namespace 列表；`accessKeyEnv` 可选 |
| `allowedTables` / `allowedCollections` | 表白名单，未列出的表一律拒绝 |
| `sensitiveFields` | 业务数据字段级脱敏字段名 |

**已支持的环境（Apollo 坐标参考）**：

| 环境 | app.id | apollo.meta |
| --- | --- | --- |
| `idn-test`（当前配置） | whatsapp-crm | http://10.99.1.187:8080 |
| ng-opay-test | whatsapp-crm-api-opay | http://172.16.22.173:8077/ |
| ng-em-test | whatsapp-crm-api-em | http://10.220.0.156:8080 |
| ng-ok-test | whatsapp-crm-api | http://10.220.2.207:8080 |
| idn-prod / ng-*-prod | — | 生产环境，**本工具不支持** |

> 除生产环境的 easemoni 域名外，其余均为内网地址，需在对应内网 / VPN 内运行。

## 1.9 如何改动

### 代码结构

```text
business-diagnostic-mcp/
├── .codex-plugin/plugin.json      # 插件元数据：声明 skills 与 mcpServers
├── .mcp.json                      # MCP 服务声明：启动命令、工具白名单、环境变量透传

├── scripts/run.sh                 # 启动脚本：加载密钥文件 → 启动 JVM
```

### 改代码

**加一个新工具**：

1. 在 `ToolRegistry.listTools()` 加工具定义（名称、描述、参数 schema）；

4. 同步 `skills/*/SKILL.md` 的说明，以及 `.mcp.json` 的 `enabled_tools`；
5. 补单元测试，跑 `mvn test`。

**调整默认值**：`LogTools` 里的 `DEFAULT_WINDOW_MINUTES`、`DEFAULT_LIMIT`、`MAX_LIMIT`、`MAX_TRACE_IDS`。

**改完怎么生效**：

```bash

mvn -q -DskipTests package
```

- 只改 Java 代码 → 打包后 `Command + Q` 重启 Codex 即可；
- 改了插件元数据（`.mcp.json` / `plugin.json` / `SKILL.md`）→ 还要重新安装插件
  `codex plugin add business-diagnostic-mcp@whatsapp-crm-mcp`，再重启 Codex。

### 开发约束

- Java 8；代码注释一律英文；
- 改动不提交 git；
- MySQL `IN` 批量查询必须分批（每批 500）；
- 新建表需符合项目规范（字段 `not null` 必须有默认值，必须有 `create_time` / `update_time`，`create_time` 加索引）。

### 已知的坑

- **`log_time` 边界必须传格式化字符串** `yyyy-MM-dd HH:mm:ss.SSS`。若传数字，MySQL 的 DATETIME 比较会被隐式转成 `YYYYMMDDHHMMSS`，导致查错时间范围。
- **`run.sh` 的输出只能写 stderr**：stdout 是 MCP 的 JSON-RPC 通道，往 stdout 打任何内容都会破坏协议。
- **日志表写入依赖 Apollo 开关** `test.log.db.enabled`；关掉后表中不再有新数据。
- **`spring.application.name` 不能用来判断服务**：api / job / otp 等多个模块的值都是 `whatsapp-crm-api`。

# 二、本地使用说明

> 面向不熟悉命令行的同学，照着做即可。

## 2.1 前置条件

1. **必须连内网 / VPN**，否则数据库和 Apollo 都连不上。
2. 有 **idn-test 环境 MySQL 的只读账号**（用户名 + 密码）。
3. 已安装本插件（安装步骤见第三部分）。

## 2.2 需要配置什么

| 要配的东西 | 位置 | 内容 | 是否进 Git |
| --- | --- | --- | --- |
| 数据源与日志环境 | `business-diagnostic-mcp/profiles.json` | 库地址、用户名、Apollo 坐标与 namespace | ❌（已 gitignore） |

| 插件开关 | `~/.codex/config.toml` | 安装插件时自动写入 | — |

## 2.3 第一步：配置 `profiles.json`

### 文件位置

```text
/Users/opay-20260271/code-temp/mcp-servers/business-diagnostic-mcp/profiles.json
```

> 查找顺序：① 环境变量 `BUSINESS_DIAGNOSTIC_CONFIG` 指定的路径 → ② 程序工作目录下的 `profiles.json` → ③ `~/.business-diagnostic/profiles.json`。当前生效的是第 ② 条。

### 打开

```bash
open -e /Users/opay-20260271/code-temp/mcp-servers/business-diagnostic-mcp/profiles.json
```

或用 VS Code / 任意文本编辑器打开。

### 要改哪几行

找到 `logDiagnostic.environments.idn-test.mysql`：

```json
"mysql": {
  "host": "MOCK_IDN_TEST_HOST",
  "port": 3306,
  "database": "whatsapp_crm",
  "user": "MOCK_READONLY_USER",
```

## 2.4 第二步：把密码写进密钥文件

### 文件位置

```text
/Users/opay-20260271/.business-diagnostic/env.sh
```

这个文件在**你自己的主目录**下，**不在任何 Git 仓库里**，永远不会被提交，也不会随插件分享给别人。权限为 `600`（只有你自己能读写）。

### 怎么改

**方式一：命令行（推荐）**

1. 打开「终端」：启动台搜索 `终端` / `Terminal`。
2. 执行下面这行，会用「文本编辑」打开文件：

   ```bash
   open -e ~/.business-diagnostic/env.sh
   ```

3. 找到这一行：

   ```bash
   export LOG_DIAGNOSTIC_IDN_TEST_MYSQL_PASSWORD=''
   ```

4. 在**两个单引号中间**填上真实密码：

   ```bash
   export LOG_DIAGNOSTIC_IDN_TEST_MYSQL_PASSWORD='你的密码'
   ```

   > - 不要删引号，不要加多余空格；
   > - 密码里若含单引号 `'`，写成 `'\''`；嫌麻烦就换一个不含单引号的密码。

5. `Command + S` 存盘并关闭编辑器。

**方式二：Finder 图形界面**

1. Finder 中按 `Command + Shift + G`，粘贴 `~/.business-diagnostic`，回车。
2. 右键 `env.sh` → 打开方式 → 文本编辑。
3. 填好密码存盘。

> 看不到该文件夹时，在 Finder 里按 `Command + Shift + .`（句点）可显示隐藏文件。

### Apollo 访问密钥

同文件里还有一行（默认被注释）：

```bash
# export LOG_DIAGNOSTIC_IDN_TEST_APOLLO_ACCESS_KEY=''
```

- idn-test 的 Apollo **未开鉴权** → **什么都不用做**；
- 若确认开了鉴权 → 把行首 `# ` 删掉，再填密钥。

### 确认权限

```bash
ls -l ~/.business-diagnostic/env.sh
```

看到 `-rw-------` 就对；若是 `-rw-r--r--`，执行：

```bash
chmod 600 ~/.business-diagnostic/env.sh
```

## 2.5 第三步：完全退出并重启 Codex

1. 按 `Command + Q` **彻底退出** Codex（只关窗口不算）；
2. 重新打开 Codex；
3. 开一个新会话。

> **为什么**：配置和密钥只在服务启动时读一次。另外 Codex 是图形界面程序，Mac 上图形程序继承的是系统 `launchd` 环境，**不会读** `~/.zshrc` / `~/.bash_profile`——所以在终端里 `export` 对它没用。这里改成了由 `run.sh` 自己去读 `~/.business-diagnostic/env.sh`，彻底绕开这个问题，**你不需要往 `~/.zshrc` 写任何东西**。

## 2.6 第四步：验证

**验证 1：配置是否加载** —— 新会话里说：

```text
列出日志环境
```

预期看到：`defaultEnvironment` = `idn-test`、4 个服务（api/job/mq/otp）、14 个 Apollo namespace。

**验证 2：数据库密码是否正确** —— 再说：

```text
帮我查下日志，关键词是 13800138000，服务 api
```

> `list_log_environments` **只验证配置读到了，不验证数据库密码**。真正的验证是验证 2：
> 密码错 → 数据库认证失败；连不上 → 连接超时（检查 VPN）。

**验证 3：无关键词场景** —— 说：

```text
素材生成图片一直失败，帮我看看
```

预期：AI 会先去看代码定位到 `whatsapp-crm-api` 的 `MaterialRAGController`，用推导出的关键词查日志，并说明它的推理过程。

## 2.7 常见问题

**Q1：报 `Missing password environment variable: LOG_DIAGNOSTIC_IDN_TEST_MYSQL_PASSWORD`**
→ 密钥文件没被读到。依次检查：① 路径是否为 `~/.business-diagnostic/env.sh`；② 是否忘记 `Command + Q` 重启；③ 权限是否 600；④ 变量名是否与 `profiles.json` 里的 `passwordEnv` 完全一致。

**Q2：我在终端里 `export` 了密码，为什么还是 `Missing password`？**
→ Codex 是图形程序，从 Dock 启动时不读 `~/.zshrc`。用 `~/.business-diagnostic/env.sh` 就绕开了。

**Q3：为什么密码不直接写在 `profiles.json` 里？**
→ 工具只识别 `passwordEnv`（变量名），不识别明文密码字段。这样设计是为了：分享配置时不顺手泄露密码；即使文件被误提交也没有明文密码。

**Q4：日志查不到数据？**
→ 依次检查：① 是否连了 VPN；② 关键词是否是精确子串；③ 时间窗是否在最近 **2 小时**内；④ 放开服务限制、扩大时间窗再试；⑤ 该服务是否在写 `test_log`（依赖 Apollo 开关 `test.log.db.enabled`）。

**Q5：Apollo 读出来是空的？**
→ 看返回的 `warnings` 与 `sources`。若 `sources` 不是 `REMOTE`，说明没真正连上 Apollo 服务端（多为 VPN / meta 地址不通），此时读到的是本地兜底值。

**Q6：不给关键词时，AI 怎么知道该搜什么？**
→ 它会去本地代码仓库里读相关类的日志语句，取消息模板中的稳定片段（一般是类名/方法名前缀）作为关键词，并按代码所在模块判断服务。它会在回复里说明推理过程，你可以据此纠正。

**Q7：会在线上误用吗？**
→ 不会。生产环境名在配置加载阶段就被丢弃，`query_logs` 会直接报 `Production environment is not allowed`，没有绕过开关。

# 三、分享给其他人使用

## 3.1 分享什么

分享整个 `mcp-servers` 目录（或推到内网 Git 仓库后给地址）：

```text
mcp-servers/
├── .agents/plugins/marketplace.json      # 插件货架清单（必需）
└── business-diagnostic-mcp/              # 插件本体（必需）
```

**不需要也不能分享**：`profiles.json`（含本地库地址与用户名）、`~/.business-diagnostic/env.sh`（密码）——两者都不在仓库里。

## 3.2 接收方操作步骤

### 第 1 步：拿到代码

把 `mcp-servers` 目录拷到自己电脑（例如 `/Users/<用户名>/mcp-servers`），或 `git clone` 内网仓库。

### 第 2 步：加入货架并安装插件

```bash
codex plugin marketplace add /Users/<用户名>/mcp-servers
codex plugin add business-diagnostic-mcp@whatsapp-crm-mcp
```

成功会输出 `Installed plugin root: .../plugins/cache/whatsapp-crm-mcp/business-diagnostic-mcp/0.2.0`。

### 第 3 步：确认插件启用

检查 `~/.codex/config.toml`：

```toml
[marketplaces.whatsapp-crm-mcp]
source_type = "local"
source = "/Users/<用户名>/mcp-servers"

[plugins."business-diagnostic-mcp@whatsapp-crm-mcp"]
enabled = true
```

也可执行 `codex mcp list`，应看到 `business_diagnostic` 且 `status = enabled`。

### 第 4 步：各自配置自己的凭据

**每个人各配各的，互不影响：**

```bash
cd /Users/<用户名>/mcp-servers/business-diagnostic-mcp
cp profiles.example.json profiles.json          # 然后编辑 host / user
mkdir -p ~/.business-diagnostic
open -e ~/.business-diagnostic/env.sh           # 填入自己的密码
chmod 600 ~/.business-diagnostic/env.sh
```

最后 `Command + Q` 重启 Codex，说「列出日志环境」验证。

## 3.3 凭据为什么不跟着一起泄露

| 文件 | 随插件分发 | 进 Git | 含密码 |
| --- | --- | --- | --- |
| `business-diagnostic-mcp/`（代码、Skill、脚本） | ✅ | ✅ | ❌ |
| `.agents/plugins/marketplace.json` | ✅ | ✅ | ❌ |
| `profiles.json` | ❌ | ❌（gitignore） | ❌ 只有变量名 |
| `~/.business-diagnostic/env.sh` | ❌ 每人自建 | ❌（仓库外） | ✅ **只在这里** |

一句话：**代码和配置模板可以随便传，密码永远只待在自己电脑上。**

## 3.4 后续更新怎么同步

| 上游改了什么 | 接收方要做什么 |

| Java 代码 | 拉最新代码 → 在 `business-diagnostic-mcp` 下 `mvn -q -DskipTests package` → `Command + Q` 重启 Codex |
