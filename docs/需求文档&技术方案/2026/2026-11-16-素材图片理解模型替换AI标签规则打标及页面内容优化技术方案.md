# 图片理解模型替换、AI标签、规则打标及页面内容优化技术方案

> 首次写入工具：Codex
> 最近写入工具：Codex
> 日期：2026-11-16
> 文档状态：技术方案初稿

## 一、背景与目标

当前素材标签有三类来源：

| 来源 | 产生方式 | 关系来源字段 |
| --- | --- | --- |
| 运营打标 | 运营创建素材时绑定标签 | `material_category_tag_relation.source_type=2` |
| AI 打标 | AI 根据素材内容生成品类和业务标签 | `material_category_tag_relation.source_type=0` |
| 规则打标 | AI 根据 `material_tag_rule` 中的规则判断素材是否命中，再生成标签关系 | `material_category_tag_relation.source_type=3` |

当前图片素材的 AI 标签流程先调用 Stable Diffusion Interrogate，将图片转换成一段 caption，再拼接为 `image_content_info`，最后交给标签模型生成业务标签。当前实现存在以下问题：

1. `getImageInfo` 依赖的图片识别模型可能返回 `null`，下游只能得到无效的图片内容描述；
2. 图片识别结果只有一段 caption，不能稳定表达人物、年龄阶段、性别外观呈现、可见肤色外观、人物类型、图片文字、金额、利率、期限、品牌、按钮、场景和构图；
3. 图片理解模型和标签生成模型的模型配置、Prompt 配置及响应解析边界不够清晰；
4. 已有 `material_tag_rule` 目前主要作为普通 AI 标签 Prompt 的业务判断参考，还没有独立的规则打标阶段；
5. 页面上部分品类展示、标签校验和筛选能力还没有与新的品类/标签模型完全对齐。

本方案目标如下：

- 使用 `glm-5.3-flash` 替换当前图片识别模型，并输出结构化图片理解 JSON；
- 保持普通标签模型不直接接收原始图片，继续通过 `image_content_info` 生成普通 AI 标签；
- 复用普通 AI 标签阶段当前的模型配置和 Ark Responses 接入方式，新增独立规则 Prompt，增加规则 AI 判定阶段；
- `scope=RULE` 的规则只进入规则打标流程，且 `material_category_code` 必须为空；
- 规则命中后的标签 code/name 直接维护在 `material_tag_rule.prompt_desc` 的 JSON 中，不新增规则表或规则标签关联表；
- 明确 `material_tag.source_type` 与 `material_category_tag_relation.source_type` 的不同含义；
- 优化素材包、组合模板、历史素材、标签管理、素材品类管理和任务分流页面展示与校验。

## 二、当前公共流程与数据模型

当前公共流程为：

```text
素材包保存
  → 保存素材及运营选择的 materialCategoryCode、运营标签关系
  → 发送现有素材标签 MQ 消息
  → 标签消费者加载可提取素材
  → 图片素材生成 image_content_info
  → 普通 AI 标签和规则 AI 判定
  → 分别写入 material_category_tag_relation
  → 记录 tag_extract_log
  → 刷新素材品类和标签查询结果
```

三张核心表职责如下：

| 表 | 职责 |
| --- | --- |
| `material_tag` | 标签定义，包括标签 code、中文名称及标签定义本身的创建来源 |
| `material_category_tag_relation` | 素材与标签的绑定关系，同时记录该关系由运营、AI 还是规则产生 |
| `material_tag_rule` | 普通 AI 标签阶段和规则 AI 判定阶段使用的规则配置 |

两个 `source_type` 的含义必须分开：

```text
material_tag.source_type
  → 标签定义的创建来源，保持现有含义

material_category_tag_relation.source_type
  → 素材标签关系的产生来源
  → 0=AI，1=admin，2=operator，3=rule
```

本次只在 `MaterialCategoryTagRelation` 中增加 `SOURCE_RULE=3` 的语义，不改变 `material_tag.source_type`。

`material_category_tag_relation.material_category_code` 表示这条素材标签关系所属的素材品类：

| 关系来源 | 品类取值 |
| --- | --- |
| 运营打标 | 运营创建素材时保存的 `MessageMaterial.materialCategoryCode` |
| 普通 AI 打标 | 普通 AI 结果中的品类，按当前流程处理；必要时回退到素材保存的品类 |
| 规则打标 | 运营创建素材时保存的 `MessageMaterial.materialCategoryCode` |

规则打标阶段不重新判断素材品类。规则配置中的 `material_category_code` 只用于规则配置校验，不作为规则关系的品类值。

## 三、图片理解与生成标签流程调整

**当前图片链路**

```text
图片素材
  → getImageInfo
  → Stable Diffusion interrogateImage
  → caption
  → image_content_info
  → MaterialContent.content
  → 普通 AI 标签模型
  → material_category_tag_relation
```

当前问题包括图片识别返回 `null`、不同图片格式统一声明为 PNG、caption 信息维度不足。改造后：

```text
图片原图
  → glm-5.3-flash 多模态图片理解
  → 结构化图片理解 JSON
  → image_content_info
  → MaterialContent.content
  → 普通 AI 标签模型
```

图片理解输入为图片理解 Prompt 和原始图片，至少支持 JPEG、PNG、WEBP，并根据图片响应头或文件头识别真实 MIME 类型。图片理解 Prompt 使用独立 key：

```text
material.ai.image.understanding.prompt
```

图片理解输出应覆盖：

- 图片整体主题、营销目的和视觉风格；
- 图片中的可见文字、语言、金额、币种、利率、期限、日期、按钮、CTA、品牌和合规文案；
- 人物数量、成人/儿童等年龄阶段、性别外观呈现、可见肤色外观、真人/插画/3D 卡通/平面卡通类型；
- 人物服饰、姿态、动作和位置；
- 手机、App 截图、二维码、金币、日历、扩音器和应用商店按钮；
- 品牌、场景、颜色、构图、版式和营销利益点。

图片理解输出示例：

```json
{
  "image_summary": "借款营销海报，突出展示借款额度和申请按钮",
  "visual_style": "realistic",
  "visible_text": [
    {
      "text": "Limit hingga Rp 200.000.000",
      "language": "id",
      "text_type": "amount"
    }
  ],
  "people": [
    {
      "age_stage": "adult",
      "gender_presentation": "female",
      "visible_skin_tone": "medium",
      "appearance_type": "real_person",
      "clothing": "浅色上衣",
      "pose": "手持手机",
      "position": "画面中央"
    }
  ],
  "objects": ["手机", "贷款应用页面", "二维码"],
  "brands": ["RupiahCepat"],
  "marketing_elements": ["低利率", "立即申请按钮"],
  "scene": "借款产品营销海报",
  "colors": ["蓝色", "白色"],
  "layout": "人物居中，文字位于上方，按钮位于下方",
  "visual_keywords": ["借款", "额度", "手机申请"]
}
```

人物的性别和肤色字段只描述图片中可见的外观呈现，用于素材内容差异和标签判断，不扩展为人物真实身份信息。无法观察或无法确认的信息返回空字符串、空数组或 `unknown`，不能编造。

图片理解 JSON 不单独新增落库表，作为 `image_content_info` 进入现有标签输入；图片理解失败、返回空值或字符串 `null` 时，不能把 `null` 当成有效内容传给下游。

普通 AI 标签输入和输出调整如下：

```json
{
  "materialId": "当前素材 ID",
  "type": "IMAGE",
  "materialCategoryCode": "当前素材保存的品类",
  "content": {
    "image_content_info": {
      "image_summary": "图片整体内容摘要",
      "visible_text": [],
      "people": [],
      "objects": [],
      "marketing_elements": []
    }
  }
}
```

普通 AI 标签模型收到的是文本 Prompt，不直接收到原始图片。文本素材继续传入原始文本。普通 AI 标签仍返回当前 `materials` JSON，并写入 `source_type=0` 的关系。

模型和 Prompt 配置分开：

```text
图片理解模型：glm-5.3-flash
普通 AI 标签模型：沿用当前标签模型配置，后续可独立替换
图片理解 Prompt：material.ai.image.understanding.prompt
普通 AI 标签 Prompt：material.ai.tag.system.prompt
```

普通 AI 标签 Prompt 的当前测试环境 Apollo 原值和改造后值如下。

**当前值：`material.ai.tag.system.prompt`**

```text
你是专业营销文案标签与素材品类分析师，请根据提供的素材内容完成素材品类判断和业务特征标签提取。

请严格按照以下规则处理：

1、对每个素材独立分析其实际内容，判断素材所属的素材品类，并提取能够体现业务含义和素材差异的标签。

2、素材品类选择顺序：
   a. 优先判断素材中的 materialCategoryCode，也就是运营绑定的素材品类是否符合当前素材内容；如果符合，继续使用该品类。
   b. 如果运营绑定的素材品类不符合，从 materialCategoryList 中选择最匹配的已有素材品类。
   c. 只有 materialCategoryList 中没有任何合适品类时，才允许新建素材品类。
   d. 当 materialCategoryCode 为 UNCATEGORIZED 时，不使用该值作为最终品类，直接从 materialCategoryList 中选择；只有没有合适已有品类时才新建品类。
   e. 已有素材品类能够匹配时，必须优先复用已有品类，不能随意新建品类。

3、新建素材品类时，materialCategoryCode 必须满足以下规则：
   - 以小写英文字母开头；
   - 只包含小写英文字母、数字和横线；
   - 长度不超过 64 个字符；
   - 不包含下划线、冒号、大写字母、空格、中文或其他特殊字符；
   - 不能使用 UNCATEGORIZED；
   - 必须使用能够表达业务含义的英文名称，例如 limit-offer、repay-1-day。

4、标签不依赖外部标签候选列表。标签必须直接根据素材内容生成，不要因为没有已有标签列表而返回空标签，也不要等待已有标签进行复用。

5、标签必须体现素材明确的业务含义或素材之间的差异，不要提取没有明确业务含义的普通词语、语气词、表情或普通语法词。

6、即使只有一个素材，也要根据该素材内容独立提取标签，不要求必须与其他素材进行比较。

7、对于内容可读且包含明确业务特征的素材，每个素材返回 1 到 5 个有业务含义的标签。标签数量根据实际内容决定，不要为了凑数量生成无意义标签。

8、对于素材内容为空、无法读取或图片识别结果为空的素材：
   - 不要编造素材品类；
   - 不要编造标签；
   - tags 可以返回空数组。

9、标签不归属于某个品类，标签应根据素材内容独立生成。materialCategoryCode 仅表示素材所属的素材品类。

10、每个标签必须包含以下字段：
   - tagCode：表达标签业务含义的英文 code；
   - tagName：简洁准确的中文名称；
   - confidence：0 到 1 之间的置信度。

11、tagCode 必须满足以下规则：
   - 以小写英文字母开头；
   - 只允许小写英文字母、数字、横线和冒号；
   - 长度不超过 64 个字符；
   - 不允许下划线、大写字母、空格、中文或其他特殊字符；
   - 必须符合正则：^[a-z][a-z0-9:-]{0,63}$；
   - 示例：disguise-system:notice、realistic-credit-limit、ojk-licensed-platform。

12、tagName 必须是简洁明确的中文展示名称，不要返回英文解释、长句或额外说明。

13、tag Rule 中的规则是业务判断参考。只有素材内容符合规则的适用条件时，才执行对应规则；不符合时跳过该规则，不要将规则强行应用到所有素材。

14、category item 中的 exampleTags 字段仅作为预留字段，必须保持为空数组。

15、每个输入素材都应在 materials 中返回对应结果，material_id 必须使用输入素材的 materialId。

16、必须严格返回纯 JSON：
   - 不要返回 Markdown；
   - 不要返回 ```json 代码块；
   - 不要返回解释文字；
   - 不要返回注释；
   - 返回内容必须能够直接被 JSON 解析。

17、返回格式必须为：

{
  "materials": [
    {
      "material_id": "Material ID",
      "materialCategoryCode": "repay-1-day",
      "materialCategoryName": "1天内还款",
      "tags": [
        {
          "tagCode": "disguise-system:notice",
          "tagName": "系统通知伪装",
          "confidence": 0.95
        }
      ]
    }
  ]
}
```

【图片理解结果兼容规则】
18、当输入素材的 type=IMAGE 时，content 中的 image_content_info 是上游图片理解模型输出的结构化 JSON，不是无意义的普通字符串。你需要读取其中的 image_summary、visual_style、visible_text、people、objects、brands、marketing_elements、scene、colors、layout 和 visual_keywords 字段。

19、图片中的 visible_text 是图片可见文字的识别结果。应结合文字原文、语言、金额、币种、利率、期限、日期、按钮、CTA、品牌和合规文案提取有明确业务含义的标签。

20、图片中的 people 只用于描述图片中可见的人物外观和画面差异，包括人物数量、成人或儿童等年龄阶段、性别外观呈现、可见肤色外观、真人/插画/3D 卡通/平面卡通类型、服饰、姿态、动作和位置。不要把无法从图片直接确认的信息当作事实，不要编造人物身份属性。

21、图片中的 objects、brands、marketing_elements、scene、colors、layout 和 visual_keywords 可以参与素材品类和业务标签判断。只有字段内容明确支持时才生成对应标签；字段为空、unknown 或图片理解结果为空时，不要猜测或补充信息。

22、对于图片素材，优先使用 image_content_info 中已经识别出的内容完成标签判断，不要要求标签模型重新读取原始图片。图片理解结果为空或不可读时，遵守第 8 条规则，不要编造素材品类和标签。
```

追加规则的核心内容是：`type=IMAGE` 时解析结构化 `image_content_info`；结合 `visible_text`、`people`、`objects`、`brands`、`marketing_elements`、`scene`、`colors`、`layout` 和 `visual_keywords` 生成标签；图片理解结果为空时不编造品类和标签；人物年龄阶段、性别外观和可见肤色外观仅作为可见内容和素材差异信息使用。

## 四、规则打标流程调整

规则打标不实现本地关键词、正则或规则执行引擎，由 AI 根据规则描述判断是否命中，以支持“是否存在问候语”等需要语义理解的规则。

普通 AI 标签和规则 AI 判定复用同一个模型配置和当前 Ark Responses 接入方式，但使用不同 Prompt、输入规则集合、输出结构和关系来源：

```text
普通 AI 标签阶段
  → scope=CATEGORY 规则
  → material.ai.tag.system.prompt
  → 输出普通业务标签
  → source_type=AI

规则 AI 判定阶段
  → scope=RULE 规则
  → material.ai.tag.rule.system.prompt
  → 输出命中的 ruleId
  → 服务端解析 prompt_desc 中的 tags
  → source_type=RULE
```

`scope=RULE` 只用于规则打标流程，不传给普通 AI 标签阶段。`scope=CATEGORY` 继续用于原有品类规则。

规则维护仍使用现有 `material_tag_rule` 表和接口：

```text
/material/ai/tagRule/page
/material/ai/tagRule/create
/material/ai/tagRule/update
/material/ai/tagRule/delete
```

规则配置约定：

| `scope` | 用途 | `material_category_code` |
| --- | --- | --- |
| `CATEGORY` | 原有品类规则 | 必须有值，并校验为有效素材品类 |
| `RULE` | 新的规则打标规则 | 必须为空字符串 |

`scope=RULE` 时不能填写具体品类；数据库字段当前为 `NOT NULL DEFAULT ''`，应用层用空字符串表示为空。

`scope=RULE` 的规则和命中标签列表直接保存在 `prompt_desc` JSON 中，不新增 `material_tag_code` 字段、不新增规则标签关联表：

```json
{
  "rule": "判断素材中是否存在问候、打招呼或开场寒暄语义。只有素材内容明确包含问候语时才判定命中。",
  "tags": [
    {
      "tagCode": "contains-greeting",
      "tagName": "包含问候语"
    }
  ]
}
```

一条规则对应多个标签时扩展 `tags` 数组。服务端在请求前校验规则描述、标签 code/name 格式、标签定义存在性和重复 code。

规则 AI Prompt 使用独立 key：

```text
material.ai.tag.rule.system.prompt
```

模型配置复用普通 AI 标签模型配置。规则 Prompt 固定角色、判断边界和 JSON 输出格式，具体规则由运行时从数据库查询启用的 `scope=RULE` 记录组成 `ruleList`。

规则 AI 输入：

```text
规则 Prompt
  + ruleList
  + 与普通 AI 标签阶段相同的 MaterialContent
    - 文本素材使用原始文本
    - 图片素材使用 image_content_info
```

规则 AI 输出只返回命中的输入规则，不返回新的素材品类或自由生成的标签 code/name：

```json
{
  "materials": [
    {
      "materialId": "当前素材 ID",
      "ruleMatches": [
        {
          "ruleId": "1001",
          "matched": true,
          "confidence": 0.95,
          "evidence": "Selamat pagi"
        }
      ]
    }
  ]
}
```

每个输入素材都必须返回结果；没有命中时 `ruleMatches` 为空。服务端根据命中的 `ruleId` 找到 `prompt_desc.tags`，生成一个或多个规则标签关系：

```text
material_id              = 当前素材 ID
material_category_code   = 当前素材保存的素材品类
material_tag_code        = prompt_desc.tags[].tagCode
source_type              = 3（RULE）
binding_status           = 1（FORMAL）
accuracy_score           = 5
extract_log_id           = 规则阶段的 tag_extract_log.id
```

规则关系的 `material_category_code` 使用运营创建素材时保存的品类，不取规则配置品类，也不取规则 AI 重新判断的品类。首期不增加 `rule_id` 字段；规则命中通过 `source_type=3`、`extract_log_id`、`tag_extract_log.rule_ids`、`request_prompt` 和 `response_body` 追踪。

## 五、公共编排和异常处理

三个阶段按以下顺序执行：

```text
加载素材
  → 图片素材生成 image_content_info
  → 普通 AI 标签阶段
  → 规则 AI 判定阶段
  → 分别重建 AI 和 RULE 来源关系
  → 刷新素材品类和标签查询结果
```

图片理解结果只生成一次，普通 AI 标签和规则 AI 判定复用同一份结果。三个阶段可以共用 Ark SDK、鉴权、超时、重试和基础日志工具，但模型输入、Prompt、输出解析和关系来源保持独立。

来源隔离规则：

- 普通 AI 重跑只删除 `source_type=AI` 关系；
- 规则 AI 重跑只删除 `source_type=RULE` 关系；
- 运营标签关系不参与自动阶段删除；
- 没有启用 `scope=RULE` 规则时跳过规则阶段，普通 AI 仍继续执行；
- 规则 AI 请求失败时记录失败日志并保留已有 RULE 关系，成功重跑后再删除和重建；
- 图片理解失败、空结果或字符串 `null` 时，两个标签阶段都不得编造图片内容；
- 规则 `prompt_desc` JSON 非法、标签定义不存在或素材没有运营保存的品类时，不写入不完整的规则关系。

日志继续复用 `tag_extract_log`，分别记录普通 AI 和规则 AI 阶段的请求 Prompt、规则 ID、原始响应、处理数量、耗时和错误信息。图片理解结果不单独新增落库表，必要的输入内容随标签阶段日志保留。

## 八、验证和上线方案

验证重点：

- 图片理解模型使用 `glm-5.3-flash`，并能处理 PNG、JPEG、WEBP；
- 图片理解结果覆盖人物数量、成人/儿童、性别外观呈现、可见肤色外观、人物类型、服饰、动作、图片文字、金额、利率、期限、品牌、按钮、场景和构图；
- 图片理解结果能够作为 `image_content_info` 进入普通 AI 标签和规则 AI 判定输入；
- 普通 AI 标签继续返回完整 `materials`，关系来源为 `source_type=0`；
- `scope=RULE` 只进入规则 AI 判定，且 `material_category_code` 非空时创建/更新失败；
- `scope=CATEGORY` 继续进入普通 AI 标签，且 `material_category_code` 为空时创建/更新失败；
- 一条 RULE 规则可以维护多个标签，多个规则可以同时命中；
- 规则 AI 关系的 `material_category_code` 等于运营创建素材时保存的品类；
- 普通 AI 重跑不删除运营和 RULE 关系，规则 AI 重跑不删除运营和 AI 关系；
- 规则 AI 复用普通 AI 标签模型配置，只使用独立规则 Prompt；
- 页面英文显示 code、中文显示 name；
- 标签 name 首字符中文、特殊符号仅允许英文冒号、长度不超过 64；
- 品类管理页支持 code、来源、状态筛选；
- 任务按权重分流组合列表展示品类和组合稳定性，文案改为“素材包内容分流”。

上线前准备：

1. 配置 `material.ai.image.understanding.model=glm-5.3-flash` 和图片理解 Prompt；
2. 配置 `material.ai.tag.rule.system.prompt`；
3. 保留并备份现有 `material.ai.tag.system.prompt`，发布原值加图片理解兼容规则的目标配置；
4. 清理或校验 `scope` 和 `prompt_desc` JSON 数据；
5. 完成图片、文本、普通 AI、规则 AI 和页面回归测试；
6. 检查 `tag_extract_log`、`material_category_tag_relation` 和相关页面展示。

回滚时按能力独立处理：

- 图片理解异常时回滚图片理解模型或 Prompt；
- 普通 AI 标签异常时回滚普通 AI 模型或 `material.ai.tag.system.prompt`；
- 规则 AI 异常时回滚 `material.ai.tag.rule.system.prompt` 或规则配置；
- 页面展示异常时回滚对应页面字段和文案；
- 各阶段只重建自己的来源关系，不删除运营标签关系。
