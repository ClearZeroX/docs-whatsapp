## 1. 当前架构与核心问题

### 1.1 当前三层口径

统一口径如下：

| 对象 | 表 | 含义 |
|---|---|---|
| 素材模板 | `message_material_group` | 一组素材模板配置，包含语言、类型、组合模式、状态、泳道配置等 |
| 素材组合 | `message_material_combination` | 可发送的组合变体，通常由 HEADER、BODY、FOOTER、BUTTONS、CAROUSEL、LTO 等素材组成 |
| 素材 | `message_material` | 真正的内容素材，当前主要存储在 MongoDB 中 |

相关对象还包括：

- `message_material_combination_card`：轮播组合与卡片的关联。
- `message_material_group_lane`：素材模板与泳道的配置关系。
- `message_template`：由素材组合生成或关联的消息模板。
- `message_template_waba`：模板在 WABA 维度的状态。
- `material_combination_send_statistic`：组合维度发送统计。
- `ai_material_suggestion`：AI 素材建议。
- `ai_backup_material_update_log`：AI 备份素材组更新日志。

### 1.2 当前架构的主要优势

当前体系已经具备较好的业务基础：

- 支持 RANDOM / MANUAL 组合模式。
- 支持 HEADER、BODY、FOOTER、BUTTONS、CAROUSEL、LTO 等组件。
- 支持轮播卡片与组合绑定。
- 支持泳道配置和模板数量校验。
- 支持 AI 素材建议与 AI 备份素材组。
- 支持动态备份素材组。
- 支持素材稳定性评级。
- 支持组合维度发送、送达、已读统计。
- 支持 RAG 历史文案搜索和异步图片生成。
- 支持标签、分类、素材选择记录等运营能力。

### 1.3 当前架构的主要问题

#### 固定槽位列导致扩展成本高

`message_material_combination` 直接存：

- `header_material_id`
- `body_material_id`
- `footer_material_id`
- `buttons_material_id`
- `carousel_body_material_id`
- `limited_time_offer_material_id`

每增加一种组件类型，都要改表、DTO、校验、状态同步、AI 备份复制、统计、模板生成逻辑。

#### 已经出现组件遗漏

当前代码中存在多处分组件判断不一致：

- `canCreateTemplate` 校验了 HEADER、BODY、FOOTER、BUTTONS、LTO，但没有校验 `carouselBodyMaterialId`。
- AI 备份 `allCombinationMaterialsActive` 和 `isCombinationUsingMaterial` 只检查 HEADER、BODY、FOOTER、BUTTONS，漏了轮播和 LTO。
- 组合素材状态计算缺少 LTO。
- 不同服务对“组合使用哪些素材”的理解不一致。

这说明固定槽位模型已经开始产生维护风险。

#### MySQL + Mongo 双写一致性弱

当前创建和更新素材组时，既有 MySQL 写入，也有 Mongo 写入。代码中已明确说明 `@Transactional` 只能回滚 MySQL，Mongo 插入、状态变更、终态删除无法随 MySQL 事务回滚。

可能产生：

- 孤儿素材。
- MySQL 组合已写入但 Mongo 素材不完整。
- Mongo 素材已删除但组合仍引用。
- 审核失败后素材状态不可逆。
- AI 备份和主素材状态不一致。

#### 编辑直接影响线上任务

当前任务、组合、模板和素材组之间是直接引用关系。素材组编辑可能影响正在使用该素材组的任务。虽然代码中已经做了“保留组合 ID、避免复活停用组合、修复组合与模板关系”等处理，但长期看仍需要版本和发布机制。

#### 查询存在 N+1 和大 IN 风险

典型问题包括：

- 组合分页时，每条组合都会查 group、Mongo 素材、卡片、泳道模板数。
- 素材组分页时，每个 group 都会查 lane，并调用 laneTemplateCount。
- 多处 MySQL `IN` 直接使用大列表，没有统一分批。
- 本地 Guava 缓存没有显式失效机制，存在陈旧数据风险。

## 2. 素材模板建模优化方向

### 2.1 从固定槽位列升级为组合明细模型

建议引入规范化组合明细表：

```text
message_material_combination_item
- id
- material_combination_id
- component_type        HEADER/BODY/FOOTER/BUTTONS/CAROUSEL_BODY/LTO/...
- sub_type
- material_id
- item_group_key        同一组合内区分多个 body、多个 card group
- sort_order
- required
- ext_json              变量映射、按钮索引、兼容性约束等
- create_time
- update_time
```

`message_material_combination` 保留组合头信息：

```text
message_material_combination
- id
- material_group_id
- combination_key
- material_template_type
- status
- material_status
- source_type
- primary_combination_id
- create_time
- update_time
```

现有固定列可以在一段时间内作为投影列保留，用于兼容发送链路，但业务逻辑应逐步统一从 item 集合读取。

收益：

- 新组件不需要反复扩列。
- 状态检查、暂停、AI 备份同步、模板生成统一遍历 item。
- 轮播卡片、LTO、未来新增按钮类型和媒体类型更容易扩展。
- 可增加 `combination_key` 唯一键，避免重复生成组合。

建议采用“双写 + 灰度迁移”，而不是一次性大重构。

### 2.2 素材内容与使用状态解耦

当前素材内容和状态都在 MongoDB `message_material` 中，且 `DELETED` 是终态。

建议拆成：

```text
material_asset          素材定义
material_asset_version  素材版本
material_usage          素材在某个组/组合/任务/泳道中的使用
material_reference      素材引用关系
```

这样可以支持：

- 一个素材被多个素材模板复用。
- 同一素材在不同泳道或组合有不同状态。
- 修改素材时通过新版本发布，不影响历史模板。
- 支持差异对比、回滚和实验归因。
- 暂停使用不等于删除定义。

### 2.3 增加素材模板版本与发布机制

当前任务直接关联素材组，素材组编辑直接影响线上组合和模板。

建议增加：

```text
message_material_group_version
- group_id
- version_no
- status                DRAFT/PUBLISHED/OFFLINE
- published_by
- published_at
- snapshot_hash
- create_time
- update_time
```

任务、模板、实验都绑定：

```text
material_group_version_id
```

收益：

- 编辑中的素材组不会影响正在发送的任务。
- 支持发布、回滚、灰度和审计。
- 模板创建可以稳定绑定某个组合版本。
- 可以避免模板与组合漂移。
- 可以和 AI 备份、稳定性统计形成闭环。

### 2.4 统一时间字段和主键规范

当前存在多种时间字段和类型：

- `ctime/utime`
- `create_time/update_time`
- `LocalDateTime`
- epoch millis

新表建议统一：

- `id` 使用 `bigint unsigned auto_increment`。
- `create_time bigint not null default 0`。
- `update_time bigint not null default 0`。
- `create_time` 增加索引。
- 所有 NOT NULL 字段必须有默认值。
- 状态字段使用明确枚举。
- 唯一键和组合索引覆盖核心查询。

### 2.5 增加引用关系和影响分析

建议增加：

```text
material_reference
- id
- source_material_id
- source_material_version_id
- target_type          GROUP/COMBINATION/TEMPLATE/TASK/LANE/EXPERIMENT
- target_id
- reference_mode       LATEST/FIXED_VERSION
- create_time
- update_time
```

可以回答：

- 这个素材被哪些组合引用？
- 这个组合被哪些模板引用？
- 修改素材会影响哪些任务？
- 哪些任务固定旧版本，哪些跟随最新版本？

### 2.6 素材资产、目录和权限

参考内容管理平台和营销云：

```text
material_asset
material_asset_version
material_folder
material_tag
material_acl
material_change_log
material_reference
```

这比单纯 `message_material_group + tags` 更适合长期运营。

### 2.7 动态片段规则化

建议把动态内容从 Java 的 if-else 中抽离出来：

```text
material_fragment_rule
- id
- fragment_key
- material_group_id
- slot_type            HEADER/BODY/BUTTONS/CAROUSEL_BODY/...
- priority
- condition_json
- target_material_id
- target_material_version_id
- fallback_material_id
- status
- valid_from
- valid_to
- create_time
- update_time
```

示例规则：

```json
{
  "all": [
    {"field": "language", "operator": "eq", "value": "id"},
    {"field": "templateType", "operator": "eq", "value": "MARKETING"},
    {"field": "userSegment", "operator": "in", "value": ["new_user", "dormant"]}
  ]
}
```

渲染时按 priority 找到第一个命中的 fragment，再解析到具体素材版本。

### 2.8 渲染上下文与渲染快照

建议增加统一渲染上下文：

```text
render_context
- task_id
- material_group_id
- material_group_version_id
- lane_code
- language
- template_type
- user_segment
- experiment_group
- catalog_data
```

模板渲染后产出：

```text
rendered_template_snapshot
```

不要让发送链路每次重新解释素材组合和动态规则。

## 3. 功能扩展方向

### 3.1 组合生成规则化与按需展开

当前 RANDOM 模式是 header × body × footer × buttons 的笛卡尔积，再加轮播和 LTO 扩展。

建议：

- 用组合规则描述可组合维度、必选维度、互斥条件。
- 大组合集先生成 logical combination，实际创建 WABA 模板时按泳道和预计发送量懒加载展开。
- MANUAL 模式从全量替换升级为 diff/delta API。
- 保存前提供 dry-run 预览。
- 返回新增、更新、失效组合以及影响模板数。
- 增加组合上限、变量数量、按钮结构、卡片数量、header 媒体类型、语言字符等兼容性校验。

### 3.2 权重、流量和实验迁移到素材域

当前自定义权重在 `TaskSenderChannelConfig.customCombinationWeight` 中，动态备份还要将主组合 ID 映射到备份组合 ID。

建议增加素材组/组合维度的：

- 默认权重。
- 泳道覆盖权重。
- 任务覆盖权重。
- 实验分组和 holdout。
- 曝光、发送、送达、已读、点击、转化、退订等指标。
- 统计显著性和自动降权。

进一步支持：

- MAB / bandit 自动流量分配。
- Control / holdout。
- Guardrail metric。
- 自动停止劣质变体。
- 优质组合自动放量。

### 3.3 AI 能力闭环

当前 AI 能力包括：

- AI 素材建议。
- AI 备份素材组。
- RAG 历史文案搜索。
- 异步图片生成。

建议扩展：

- AI 支持 HEADER、BODY、BUTTON、CAROUSEL、LTO 多槽位生成。
- 生成结果按组合维度保存候选，而不是直接覆盖备份素材。
- 增加去重、语义相似度、合规校验、品牌语气校验。
- 把模板审核结果、送达率、已读率反哺 RAG。
- AI 备份组支持版本快照和回滚。
- Redis 中的异步图片任务结果持久化，增加任务表、重试、幂等和审计。

目标闭环：

```text
生成 -> 审核 -> 发布 -> 实验 -> 指标回流 -> 再生成
```

### 3.4 多语言、多地区、多品牌扩展

当前素材组有 language 字段，但多语言、多地区、多品牌长期看会出现大量复制。

建议支持：

- 一个素材组绑定多个语言变体。
- 一个素材定义按 locale 生成版本。
- 品牌、地区、合规规则作为维度。
- 任务绑定逻辑素材组，运行时选择语言和地区变体。
- 跨地区复用公共素材，只覆盖差异片段。

### 3.5 运营能力扩展

建议增加：

- 素材组复制。
- 组合导入导出。
- 批量创建。
- 模板 diff。
- 保存前预览。
- 影响分析。
- 泳道容量占用预估。
- 任务上线前容量预留。
- 素材和组合审批流。

### 3.6 路由、泳道和容量治理

当前已有泳道容量校验，但长期建议升级为：

- 泳道容量账本。
- 创建任务时预留模板额度。
- 审批通过后正式占用。
- 任务结束或失效后释放。
- 避免多个任务并发创建时超卖。
- 支持优先级和抢占。

## 4. 当前代码中的性能与正确性优化

这些是短期收益最高、风险较低的方向。

### 4.1 批量查询替代 N+1

组合分页时，每条组合会执行：

- 查 group。
- 最多 6 次查 Mongo 素材。
- 查卡片。
- 查泳道模板数。

一页 20 条可能产生上百次查询。

建议改为：

- 批量查 group。
- 批量 `queryByIds` 查 Mongo 素材。
- 批量查 combination card。
- 批量计算 lane template count。
- 批量查统计。

素材组分页也存在类似问题，每个 group 查 lane 并调用模板统计，应批量加载。

### 4.2 MySQL IN 必须分批

对以下场景统一封装批次查询：

- sourceLane 查询出的 materialGroupIds 再 IN。
- combinationIds 集合查询。
- messageTemplateId 列表查询。
- WABA template id 查询。
- tag 对应 materialIds 查询。

建议每批 500 或 1000，视 SQL 长度和索引情况确定。

Mongo 已有部分 `queryByIds` 做了 1000 一批，但标签路径和部分查询仍需补齐。

### 4.3 修复组件遗漏

短期先修复：

- `canCreateTemplate` 增加 carousel body 校验。
- AI 备份状态同步增加 carousel body、LTO。
- 组合素材状态计算增加 LTO。
- `allCombinationMaterialsActive` 和 `isCombinationUsingMaterial` 统一组件集合。
- 清理不可达代码和重复判断。

长期通过 `combination_item` 统一遍历，避免继续遗漏。

### 4.4 缓存统一失效

当前存在：

- `materialForTypeCache`
- `templateTypeStatsCache`
- `groupAllTemplatesCache`
- group cache

这些本地缓存部分没有显式失效，更新素材、组合、模板后可能短时间返回旧数据。

建议：

- 改成 Redis 或 Spring Cache。
- 更新时主动失效。
- 使用 group version 作为 cache key。
- 关键缓存支持手动清理。
- 大批量刷新使用 job，避免请求链路抖动。

### 4.5 增加索引和唯一约束

建议至少考虑：

- `message_material_combination(material_group_id, combination_key)` 唯一。
- `message_material_group_lane(material_group_id, source_lane)` 唯一。
- `message_material_combination_card(material_combination_id, sort_order)`。
- `material_combination_send_statistic(send_dt, material_combination_id)`。  
- Mongo `message_material(material_group_id, type, sub_type, status)`。
- Mongo `message_material(source_material_id, type)`。

### 4.6 处理 MySQL + Mongo 双写一致性

建议引入：

- Outbox。
- Saga。
- Compensation。
- Idempotency key。
- Operation log。
- 定时补偿任务。
- 长流程工作流引擎。

短期至少：

- 每次素材组创建/更新生成 `operation_id`。
- MySQL 记录操作状态。
- Mongo 写入后回写确认。
- 失败时补偿或标记待修复。
- 避免静默产生孤儿素材。

### 4.7 统一 message_material_template 与 message_template 关系

当前 `message_material_template` 看起来存在遗留或双轨痕迹，而主生成链路更多使用 `message_template.material_group_id` 和 `message_template.material_combination_id`。

建议明确：

- 是否继续保留 `message_material_template`。
- 如果保留，明确它和 `message_template` 的唯一事实来源。
- 如果废弃，制定迁移和停写计划。
- 避免模板计数、泳道计数、修复逻辑各自读不同来源。

## 5. 业内成熟实现参考

### 5.1 推荐参考的产品

| 产品 | 最值得借鉴的点 | 对应到素材模板体系 |
|---|---|---|
| Meta WhatsApp Business Platform | 官方 template components 数组、语言、分类、按钮、媒体、WABA 状态同步 | `message_template`、`message_template_waba`、组件适配 |
| Braze | Content Blocks、Catalogs、Canvas、Variant、Currents 数据回流 | 素材块复用、组合候选、编排、指标回流 |
| Salesforce Marketing Cloud | Content Builder、Shared Content、Dynamic Content Block、Journey Builder | 素材库、共享素材、动态片段、任务编排 |
| Adobe Journey Optimizer | Content Template、Fragment、Offer Decisioning、Experimentation | 模板、片段、组合、决策、实验一体化 |
| Iterable / Klaviyo / Customer.io | Snippets、Catalog、Universal Content、模板复用与变量 | 可复用素材、变量绑定、模板片段 |
| Contentful / Sanity | Content Type、Reference、Localization、Draft/Published、Environment | 素材组版本、素材引用、语言变体、发布流程 |
| GrowthBook / LaunchDarkly / Optimizely | 稳定分流、实验版本、holdout、guardrail、exposure | 组合权重、AB 实验、素材自动降权 |
| Temporal / Cadence | Saga、长事务、重试、补偿、幂等 | MySQL + Mongo 双写一致性 |
| Netflix / Airbnb 实验平台 | 实验治理、指标口径、长期效应、可复现性 | 素材和组合自动优化闭环 |

如果只能选三个对标：

1. Meta WhatsApp Template API：参考 WhatsApp 域模型。
2. Braze + Salesforce Marketing Cloud：参考内容块、共享素材、动态片段和组合编排。
3. Adobe Journey Optimizer + GrowthBook：参考决策、权重、实验和自动优化。

### 5.2 最值得借鉴的建模思想

#### Meta：组件数组而不是固定字段

Meta 的 WhatsApp 模板天然是 components 数组，每个 component 有 type、format、parameters、buttons、cards 等。

对应建议：

```text
message_material_combination
message_material_combination_item
```

把 Meta component schema 作为外部协议，把内部组合 item 作为领域模型。外部协议变化只影响适配层，不影响素材组和组合核心模型。

参考：

- Meta WhatsApp Message Templates：https://developers.facebook.com/docs/whatsapp/business-management-api/message-templates/
- Meta WhatsApp Cloud API Components：https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-message-templates

#### Adobe Journey Optimizer：Template + Fragment + Decisioning

Adobe 的分层：

```text
Template
  -> Fragment
  -> Offer/Decision
  -> Experiment
  -> Channel Delivery
```

对应到当前体系：

```text
素材模板
  -> 素材组合
  -> 决策规则
  -> 权重/实验
  -> WABA 模板和任务
```

参考：

## 6. Braze / Salesforce 细化参考

这一部分重点细化“内容块、共享内容、动态片段”。

### 6.1 核心分层

成熟做法是把下面四件事拆开：

```text
共享内容 Content Block
动态片段 Dynamic Content / Fragment
运行时变量 Personalization
组合关系 Composition
```

当前系统容易把它们混在：

- `message_material`
- `message_material_combination`
- `laneConfig`
- `TaskSenderChannelConfig`

### 6.2 四个概念的区别

#### Shared Content：共享内容块

特点：

- 可复用。
- 不依赖具体用户。
- 常用于 footer、免责声明、品牌签名、固定 CTA、图片、按钮文案。
- 被多个模板引用，而不是复制。
- 修改共享块时，需要明确是“引用最新版”还是“固定某个版本”。

对应到当前系统：

- 一个 FOOTER 素材。
- 一个固定按钮文案。
- 一个固定 BODY 模板片段。
- 一个品牌签名。

#### Dynamic Content / Fragment：动态片段

特点：

- 在渲染时根据上下文选择。
- 依赖用户属性、语言、国家、渠道、任务、泳道、实验分组、时间等。
- 通常有优先级、命中规则、fallback。
- 不是变量替换，而是“选择哪一个内容”。

对应到当前系统：

- 印尼语用户走印尼语文案。
- MARKETING 走营销文案，UTILITY 走功能性文案。
- 新用户走新客文案，老用户走沉默召回文案。
- 主素材组不可用时走 AI backup group。
- A 任务走组合 1，B 任务走组合 2。

#### Personalization：变量替换

特点：

- 内容已经选定，只替换占位符。
- 例如 `{{name}}`、`{{amount}}`、`{{expiry_time}}`。
- 变量数量和类型由组件结构约束。

对应到当前系统：

- BODY 里的 `{{1}}`、`{{2}}`。
- 按钮 URL 参数。
- 卡片 header media。
- LTO 金额、有效期。

#### Composition：组合

特点：

- 把多个内容块、动态片段、变量绑定组装成一个可发送模板。
- 组合是结构，不应该承担所有动态决策逻辑。

对应到当前系统：

- HEADER + BODY + FOOTER + BUTTONS。
- CAROUSEL_BODY + CARD_LIST。
- BODY + LTO。

### 6.3 Braze 的实现方式

#### Content Blocks

Braze 的 Content Blocks 是可复用内容单元，可以插入到邮件、消息和其他渠道内容中。

借鉴点：

- 内容块独立管理，不绑定某一个 Campaign。
- 内容块可以被多个模板引用。
- 内容块可以是 HTML、文本、Liquid、图片、按钮等。
- 内容块支持嵌套或组合，但需要控制嵌套深度。
- 修改内容块时，需要考虑对引用它的模板影响。

建议模型：

```text
material_definition        素材定义
material_version           素材版本
material_reference         引用关系
material_block             可复用内容块
```

进一步：

```text
material_asset
- id
- material_key
- type                 HEADER/BODY/FOOTER/BUTTONS/CAROUSEL_BODY/LTO
- sub_type
- status
- source_type
- create_time
- update_time

material_asset_version
- id
- material_asset_id
- version_no
- content_json
- content_hash
- status               DRAFT/PUBLISHED/ARCHIVED
- create_time
- update_time
```

#### Catalogs

Braze Catalogs 用来存业务数据，比如商品、门店、优惠、推荐内容。它和内容模板分开。

借鉴点：

- 文案素材和业务数据不要混在一起。
- LTO、商品、优惠、价格、库存适合放 Catalog 类模型。
- 模板只引用数据 key，不复制业务数据。
- 渲染时根据任务上下文查 Catalog。

对应 LTO：

```text
message_material_group_lto
- material_group_id
- lto_key
- title
- amount
- currency
- start_time
- end_time
- payload_json
```

不要让 LTO 所有业务语义都塞进 Mongo 素材的 element JSON。

#### Liquid / Personalization

Braze 使用 Liquid 做变量替换、条件逻辑和动态内容。

借鉴点：

- 变量替换是渲染期行为。
- 条件逻辑有明确上下文。
- 复杂逻辑不要散落在 Java 校验代码里。
- 模板本身应该可预览、可测试。

建议提供统一 render context：

```text
render_context
- task_id
- material_group_id
- lane_code
- language
- template_type
- user_segment
- experiment_group
- catalog_data
```

模板渲染后产出 `rendered_template_snapshot`。

#### Canvas / Experiment Paths

Braze Canvas 支持 Journey 编排、分支、实验路径。

借鉴点：

- 组合是内容结构，Canvas 是流量结构。
- 实验分组不应该放在素材内容里。
- 任务、泳道、实验、素材组应该是不同层级。

对应：

```text
素材模板 group              内容集合
素材组合 combination        可发送变体
任务 task                   投放场景
泳道 lane                   通道/容量/资源
实验 experiment             流量分配
```

### 6.4 Salesforce Marketing Cloud 的实现方式

#### Content Builder

Content Builder 是资产中心，典型资产包括：

- Image
- Text
- Content Block
- HTML Email
- Template
- Code Snippet
- Shared Content

借鉴点：

- 素材不是业务表的附属品，而是独立资产。
- 资产有文件夹、权限、标签、共享范围。
- 资产可以被多个消息引用。
- 资产变更需要影响分析。
- 资产和模板是不同对象。

对应模型：

```text
material_asset          素材资产
material_folder         素材目录
material_tag            素材标签
material_acl            素材权限
material_reference      引用关系
material_change_log     变更审计
```

#### Shared Content

Salesforce 的 Shared Content 强调跨业务单元复用。

借鉴点：

- 公共 footer、品牌元素、合规文案可以跨素材组复用。
- 共享内容有权限边界。
- 引用共享内容的模板需要有依赖图。
- 修改共享内容前需要知道影响多少模板和任务。

建议表：

```text
material_reference
- id
- source_material_id
- source_material_version_id
- target_type          GROUP/COMBINATION/TEMPLATE/TASK
- target_id
- reference_mode      LATEST/FIXED_VERSION
- create_time
- update_time
```

#### Dynamic Content Block

Salesforce 的 Dynamic Content Block 本质是“规则命中的内容块”。

借鉴点：

- 动态内容是一个独立的规则对象。
- 规则按优先级匹配。
- 命中后选择一个内容块。
- 未命中时有 fallback。
- 规则可以基于用户属性、数据扩展、语言、地区等。

建议表：

```text
material_fragment_rule
- id
- fragment_key
- material_group_id
- slot_type            BODY/HEADER/BUTTONS/...
- priority
- condition_json
- target_material_id
- target_material_version_id
- fallback_material_id
- status
- valid_from
- valid_to
- create_time
- update_time
```

#### AMPscript / SSJS

Salesforce 用 AMPscript / SSJS 做个性化、查询和条件渲染。

借鉴点：

- 个性化逻辑需要沙箱、预览和测试。
- 不要允许任意脚本进入发送热路径。
- 复杂逻辑应该预计算或缓存。

对当前系统来说，不建议引入通用脚本引擎。更合适的是：

- 用 JSON DSL 表达条件。
- 用白名单 operator。
- 用上下文对象注入变量。
- 在保存和发布时静态校验。
- 渲染结果快照化。

#### Journey Builder

Journey Builder 负责流程和分支，不负责内容本身。

借鉴点：

- 内容、旅程、决策、实验分四层。
- 任务不是素材组的一部分。
- `relatedTasks` 这种 JSON 字段长期会成为反模式。
- 应该建立任务与素材组版本的正式引用关系。

建议表：

```text
message_material_group_usage
- material_group_id
- material_group_version_id
- usage_type           TASK/LANE/EXPERIMENT/TEMPLATE
- target_id
- status
- create_time
- update_time
```

然后 `relatedTasks` 只作为缓存或展示字段，不再作为事实来源。

### 6.5 Braze 和 Salesforce 合并借鉴

| 能力 | Braze | Salesforce | 建议在当前系统的落地 |
|---|---|---|---|
| 可复用内容块 | Content Blocks | Content Block / Shared Content | `material_asset + version` |
| 内容资产治理 | 相对轻量 | 强目录、权限、共享 | `folder + tag + acl + reference` |
| 动态内容 | Liquid / Canvas | Dynamic Content Block | `fragment_rule + priority + fallback` |
| 个性化变量 | Liquid | AMPscript / SSJS | `render_context + variable_schema` |
| 组合编排 | Canvas | Journey Builder | `combination + item` |
| 实验分流 | Canvas Experiment | Journey / Einstein | `experiment + variant + assignment` |
| 数据目录 | Catalogs | Data Extensions | `catalog_data` 或 LTO/商品数据表 |
| 发布治理 | Campaign/Canvas 级别 | Content Builder 资产级别 | `group_version + asset_version` |
| 指标回流 | Currents | Einstein / Datorama | `material_metric` 统一归因 |

### 6.6 最值得直接抄的四点

1. **Content Block / Shared Content 模型**  
   素材必须是可复用资产，不是素材组的附属品。

2. **Dynamic Content Block 模型**  
   动态内容必须是“规则命中 + 优先级 + fallback”，不是散落的 if-else。

3. **Content Builder 治理模型**  
   素材需要目录、权限、版本、引用、影响分析、变更审计。

4. **Canvas / Journey 分层模型**  
   内容、组合、任务、泳道、实验、决策必须分层，不能全塞进任务配置。

## 7. 当前收益与长期收益

收益可以分成两类：

- 确定性收益：稳定性、性能、研发效率、治理能力，做完就能看到。
- 弹性收益：转化率、AI 效率、运营效率、模板复用率，需要配套流程和产品能力才能释放。

不建议把“架构升级”直接等同于“转化率一定提升”。它更多是先把地基和闭环建起来，让增长优化产生复利。

### 7.1 当前收益

#### 减少线上错误和回归成本

当前固定槽位列导致每加一个组件，都要改很多地方，而且已经出现遗漏。

改成 `combination_item` 或统一组件访问层后：

- 新组件只改模型和少量适配。
- 状态检查、暂停、AI 备份、模板生成统一遍历 item。
- 降低“新增功能后旧逻辑漏改”的回归风险。
- 测试范围更小，单测更容易覆盖。

衡量指标：

- 新增组件类型的改动文件数。
- 素材组合相关线上缺陷数。
- 回归测试覆盖率和失败率。
- 发布后回滚次数。

#### 性能立即改善

当前组合分页、素材组分页存在明显 N+1 风险。

批量查询、缓存失效和 IN 分批的当前收益：

- 接口 P95 / P99 延迟下降。
- MySQL 慢查询和 Mongo QPS 下降。
- 大素材组、大组合集下不容易超时。
- 减少分页查询打爆 DB / Mongo 的概率。
- 避免 IN 列表过大导致 SQL 变慢或报错。

衡量指标：

- 单次接口 SQL 数量。
- Mongo 查询次数。
- P95 / P99 延迟。
- 慢查询数量。
- 超时率和错误率。

#### 降低线上变更风险

当前素材组编辑会直接影响组合、状态、模板和任务。增加版本和发布后：

- 编辑中的草稿不会影响线上任务。
- 任务可以绑定已发布版本。
- 出问题时可以回滚版本。
- 可以对比发布前后差异。
- 可以做灰度发布。

当前收益：

- 误操作影响范围变小。
- 线上问题可快速定位到具体版本和操作人。
- 不需要靠 repair 脚本修数据。
- 不会因为编辑素材组导致在线组合和模板漂移。

衡量指标：

- 平均回滚时间。
- 因素材编辑导致的线上事故数。
- repair / 补偿任务执行次数。
- 数据不一致记录数。

#### 运营和审计能力增强

引入素材资产、引用关系、版本和操作日志后：

- 能查一个素材被哪些组合、模板、任务引用。
- 暂停或删除素材前能做影响分析。
- 可以记录谁在什么时间改了什么、为什么改。
- 支持审批、权限和合规审计。

当前收益：

- 运营操作更可控。
- 风险、合规、审核成本下降。
- 删除或暂停前不再靠人工确认。
- 审计不再依赖零散日志。

#### 研发效率提升

当前模型下，很多知识散落在多个 Service、DTO 和 mapper 逻辑中。

统一组合 item、引用关系和渲染上下文后：

- 领域边界更清晰。
- 新增渠道、组件、组合模式时改动更小。
- 产品、运营、研发对同一套术语更容易对齐。
- 代码 review 和排障成本下降。

### 7.2 长期收益

#### 素材复用和内容供应链复利

长期看，素材会从“某个 group 下的私有数据”变成“可复用内容资产”。

收益包括：

- 一个 footer、品牌签名、CTA、合规文案可跨模板复用。
- 一个 BODY 可被多个任务、泳道、实验引用。
- 多语言、多地区、多品牌不需要复制整套素材组。
- 修改公共内容时只需要改一次。
- 可以建立素材目录、标签、权限和生命周期。

长期指标：

- 素材复用率。
- 重复素材数量。
- 多语言素材复制成本。
- 新建素材组到上线的时间。
- 一次修改影响的模板数量。

#### 实验和增长优化形成复利

当前已经有组合统计和自定义权重，但长期更成熟的是实验平台化：

- 组合、素材、片段都可以进入实验。
- 支持 holdout、guardrail、显著性检验。
- 支持按用户、任务、泳道、地区稳定分流。
- 支持自动降权、MAB、bandit。
- 指标从发送、送达、已读扩展到点击、转化、退订、投诉。

长期收益：

- 优质素材更快放量。
- 劣质素材更快止损。
- 实验周期缩短。
- 同一批流量产出更高。
- 内容优化从人工判断变成数据驱动。

长期指标：

- 每月有效实验数。
- 实验从创建到结论的天数。
- 胜出变体放量时间。
- read / click / conversion lift。
- 投诉率和退订率下降。

#### AI 能力闭环

当前 AI 建议、AI 备份、RAG 已经有基础。长期收益来自闭环：

```text
生成 -> 审核 -> 发布 -> 实验 -> 指标回流 -> 再生成
```

收益：

- AI 建议更符合历史优质模板。
- 自动学习哪些文案、按钮、图片、组合效果更好。
- 减少人工写文案和配组合的时间。
- AI 备份可以从 BODY 替换扩展到多槽位、多组合、多版本。
- 可以自动生成候选实验，而不是只生成内容。

长期指标：

- AI 建议采纳率。
- AI 建议应用到发布的转化率。
- AI 生成素材的胜出率。
- AI 节省的运营工时。
- AI 素材上线后的业务指标提升。

#### 风险、合规和治理长期收益

随着模板、语言、地区、品牌变多，治理成本会指数上升。

长期收益：

- 素材和模板有版本、审批、权限和审计。
- 可以控制哪些内容可跨品牌、跨地区使用。
- 可以限制敏感内容、合规文案、退订说明。
- 可以快速冻结某个素材、组合或实验。
- 可以回答“谁改了、什么时候改的、影响了哪些任务”。

长期指标：

- 审计覆盖率。
- 未审批发布数量。
- 合规问题数量和响应时间。
- 风险内容影响任务数。

#### 横向扩展能力

长期看，系统不会只支持 WhatsApp 一种渠道，也不会只支持现在的组件类型。

更好的模型可以支持：

- 新组件类型：新按钮、新媒体、新卡片结构。
- 新渠道：SMS、Email、RCS、Push。
- 新供应商：Meta、GPI、YCloud、未来其他供应商。
- 新业务：营销、通知、认证、运营活动。
- 新区域：多语言、多时区、多合规规则。

长期收益：

- 新渠道接入成本降低。
- 新供应商替换成本降低。
- 业务扩展不需要重写素材模型。
- 平台化能力可以服务更多业务线。

#### 成本下降

这里的成本不只是机器成本，还包括：

- 研发改造成本。
- 运营配置成本。
- 测试回归成本。
- 线上事故和修复成本。
- 重复模板治理成本。
- 人工实验和调优成本。

长期收益：

- 更少的重复素材和重复模板。
- 更少的人工复制和粘贴。
- 更少的线上事故。
- 更少的无效 WABA 模板申请和治理。
- 更高的自动化实验和优化比例。

### 7.3 按角色看收益

| 角色 | 当前收益 | 长期收益 |
|---|---|---|
| 研发 | 减少遗漏、降低 N+1、提升编译和测试可维护性 | 平台化、扩展新渠道和组件、降低系统耦合 |
| 运营 | 素材复用、影响分析、上线更安全 | 低代码编排、自动发布、批量运营 |
| 增长 | 指标更完整、实验更可控 | 自动优化、复利增长、提高转化 |
| 风控/合规 | 操作可追溯、变更可审计 | 审批、权限、版本回滚、合规规则体系 |

| 管理层 | 降低事故和无效成本 | 提高内容产能、提升 ROI、支撑多业务扩展 |

### 7.4 一句话总结

当前收益主要是：少出 bug、接口更快、编辑更安全、审计更清楚、研发改动更小。

长期收益主要是：素材可复用、组合可版本化、流量可实验、AI 可闭环、渠道可扩展、治理可控，最终形成内容供应链和增长优化的复利。

最大的长期收益不是省几次查询，而是让“素材生产、组合发布、实验优化、AI 生成”变成可管理、可复用、可度量的平台能力。

## 9. 目标模型建议

建议目标模型如下：

```text
message_material_group                 素材模板，管理入口
message_material_group_version         素材模板版本
message_material_asset                 素材定义
message_material_asset_version         素材版本
message_material_reference             素材引用关系
message_material_combination           组合头
message_material_combination_item      组合组件
message_material_combination_card      轮播卡片关系
message_material_fragment_rule         动态片段规则
message_material_render_snapshot       渲染快照
message_material_experiment            实验
message_material_experiment_variant    实验变体
message_material_assignment            分流结果
message_material_metric                指标
message_material_group_usage           素材组使用关系
message_material_change_log            变更审计
```

核心原则：

- 素材定义和素材使用分离。
- 组合由 item 组成，不由固定列组成。
- 草稿和发布版本分离。
- 任务绑定发布版本，不直接绑定可编辑对象。
- 发送路径保留快照或投影，保证性能。
- 权重、实验、指标独立建模。
- MySQL 和 Mongo 跨库写入必须有补偿和幂等。
- 动态内容必须规则化、优先级化、有 fallback。
- 所有新表遵循：NOT NULL 有默认值、包含 create_time / update_time、create_time 加索引。

## 10. 衡量指标建议

### 工程指标

- 单次接口 SQL 数量。
- 单次接口 Mongo 查询次数。
- 接口 P95 / P99 延迟。
- 慢查询数量。
- 超时率和错误率。
- 新增组件类型改动文件数。
- 回归测试覆盖率和失败率。
- 发布后回滚次数。
- 数据不一致记录数。
- repair / 补偿任务执行次数。
- 缓存命中率和陈旧数据问题数。

### 运营指标

- 素材复用率。
- 重复素材数量。
- 新建素材组到上线的时间。
- 一次修改影响的模板数量。
- 运营手动操作次数。
- 批量创建和导入使用率。
- 素材和组合审批通过率。
- 素材暂停/删除前的影响分析覆盖率。

### 增长指标

- 每月有效实验数。
- 实验从创建到结论的天数。
- 胜出变体放量时间。
- request / sent / delivered / read / click / conversion。
- 投诉率和退订率。
- read / click / conversion lift。
- AI 生成素材的胜出率。
- AI 建议采纳率和应用转化率。

### 风险治理指标

- 审计覆盖率。
- 未审批发布数量。
- 合规问题数量和响应时间。
- 风险内容影响任务数。
- 平均回滚时间。
- 因素材编辑导致的线上事故数。

## 总结

当前系统已经具备较好的业务功能基础，包括多组合模式、轮播、LTO、AI 备份、稳定性评级和组合统计。下一步最值得做的不是继续堆字段和 if-else，而是：

```text
素材资产化
组合明细化
片段规则化
发布版本化
渲染快照化
实验数据化
跨库一致性治理
```

短期优先做性能、正确性和缓存治理；中期做组合 item、素材复用和版本发布；长期做动态片段、实验平台、AI 闭环和多渠道扩展。

这样既能保留 WhatsApp 结构化组件约束，又能吸收 Meta、Braze、Salesforce、Adobe、Contentful、GrowthBook、Temporal 等成熟实现的优点。
