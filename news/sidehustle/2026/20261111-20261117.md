这一周的三条主线，乍看毫不相干：OpenAI 让 Agent 真的能刷信用卡了，苹果把国区 AIGC 合规材料变成上架必填项，一段为 Base64 加速的汇编 intrinsics 把 OpenJDK 变成了预认证 RCE。但把它们放在一起，指向的是同一件事——**"验证权"正在从你手里转移给外部方**：购物 Agent 要能读懂你的货架，苹果和监管要能审过你的材料，甲方和等保要能证明你的补丁真的打了。

个人开发者的机会不在"再做一个 AI 应用"，而在给这条新链路补上三块脏活：**可读、可审、可证**。本期刻意避开已写过的 ModelCanary（LLM 端点监控）、SlopGate（AI 代码质量门禁）、MetricDock（信创问数底座），三条分别落在"新入口""新合规""老运行时"上，彼此不重叠。

## 【A】AgentShelf：AI 购物 Agent 的「货架可读性」审计

### 1. 机会点

给跨境独立站做一份"AI 购物 Agent 能不能读懂你、比对你的价、走到结账"的审计报告：把价格、库存、变体、运费、退货政策改造成机器可读的结构化事实，先卖 699 元一份的体检，而不是卖"保证被 AI 推荐"的玄学。

### 2. 为什么是现在

- **Agent 第一次真的能付钱。** 11 月 13 日 OpenAI 上线 ChatGPT Wallet：绑定美国发行的 Visa / Mastercard / 美国运通卡后，ChatGPT 可比价、选品并直接结账；每笔交易前用户核对商品、总价与扣款卡，Face ID / 指纹确认，真实卡号以支付令牌替代，商户只收到履约所需的收货与联系信息。首发仅限美国 18 岁以上、部分 Pro 订阅用户，OpenAI 同步发布了商户接入指南（[OpenAI 官方](https://openai.com/index/introducing-chatgpt-wallet)；[TechCrunch 11-13](https://techcrunch.com/2026/11/13/chatgpts-new-wallet-lets-ai-agents-shop-and-check-out-for-you/)）。
- **平台越封，独立站越有动力。** 同一天亚马逊明确禁止 AI 智能体代下单，成为该模式落地的最大阻力。被大平台封住的入口，正是独立站可以抢的入口——前提是你的店对 Agent 友好。
- **Agent 流量的商业闭环正在铺好。** 11 月 11 日 Stripe 宣布、11 月 10 日完成对 OpenRouter 的收购，金额约 75-80 亿美元，后者接入 80 多家供应商的 400 多款模型；2026 年 10 月处理约 790 万亿 Token、环比增长 37%，其中约 76% 来自智能体相关 API 调用（[IT之家 11-12](https://www.ithome.com/1/025/833.htm)）。模型选择、词元路由和计费正在变成支付基础设施的一部分。
- **"写 SEO 文章"这条路被证伪了。** 11 月 18 日 HN 首页 417 分、304 条评论的实测：随机隐藏 AI Overviews 后，外链点击减少约 40%；AI Overviews 已覆盖美国关键词的 61.43%；而今年 3 月 AI 助手给网站带去的流量占比只有 0.3%。文章同时给 GEO 泼了冷水——除了"出现在 AI 引用的第三方站点上"和"把页面写得容易被引用"，没有找到其他可靠打法（[RevScope 11-09](https://revscope.co/blog/search-seo-geo-2026/)；[HN 50540178](https://news.ycombinator.com/item?id=50540178)）。**能改的不是文案技巧，是事实层。**
- **站点正在长出"给 Agent 看的接口"。** Product Hunt 11 月 13 日上榜的 SaaS Toolkit MCP，卖点是"一个 JS 片段，给站点放一个 7×24 的 SDR 和 CMO"（[Product Hunt Feed](https://www.producthunt.com/feed)）。独立开发者已经在卖"面向 Agent 的网站"，说明这个交付形态有人认。

### 3. 目标用户 + 具体痛点

**用户：年 GMV 50 万–500 万美元的 Shopify / 独立站卖家，3-10 人团队**，集中在 3C 配件、家居、宠物、美妆工具；以及给他们做建站/代运营的服务商（后者一次能带 10 个客户）。

痛点非常具体：

- 商品页的核心信息在图片和 JS 里，Agent 抓到的是空价格或一段营销文案；JSON-LD 只填了 `name` 和 `image`，缺 `price`、`availability`、`shippingDetails`。
- 变体表达是"图片色卡 + JS 事件"，Agent 无法把"雾霾蓝 / M"映射到具体 SKU，比价阶段就断了。
- 同一个 SKU 在 Google Merchant Feed、Meta Catalog、站内页三处价格/库存不一致，Agent 引错价，商家要么亏钱要么被投诉。
- 运费、时效、退货政策写在图片和折叠 FAQ 里，Agent 答不出"到德国要几天、能不能退"，转化死在最后一问。
- 结账必须人工点选，没有可被 Agent 调用的 quote / cart 接口；Shopify 有 Storefront API，但商家不知道自己能不能用、要不要开、开了有什么风险。
- 不知道自己在 ChatGPT / Gemini / Perplexity 里被怎么描述——是报了价、是"无货"，还是根本没被提到。

一句话：他们不缺流量，缺的是"当流量变成 Agent 时，我的店在机器眼里长什么样"。

### 4. MVP 范围

**做：**

- 输入店铺域名 → 从 sitemap / collection 抓 50 个 SKU（其中至少 5 个多变体商品）。
- 五维评分卡：① 结构化数据完整度（Product / Offer / AggregateRating / ShippingDetails）；② 事实一致性（页面 vs JSON-LD vs Merchant Feed）；③ 变体可机读性；④ 政策可读性（运费/时效/退货/保修是否在 HTML 文本里）；⑤ Agent 实测（10 个真实购物问题，跑 2-3 个带浏览的模型，记录答案、引用源、错在哪）。
- 输出：PDF 报告 + 20 条修复工单（每条带 JSON-LD / Shopify Liquid 代码片段、优先级、预计工时）+ 3 张 Agent 实测截图。
- 复测：同一店铺 2 周后重跑，出"修复前后对比"——这是收第二笔钱的钩子。

**明确砍掉：**

- 不自动改站、不做 Shopify App、不做实时监控大盘。
- 不做多语言、不做真实下单（法务和风控都过不去）。
- 不承诺"被 AI 推荐"——只承诺"机器能正确读到这些事实"。

### 5. 技术方案

**选型：Java 21 + picocli（CLI 优先）+ Jsoup + Playwright for Java（仅 JS 渲染页，可选）+ networknt JSON Schema Validator + Jackson + LangChain4j（Agent 实测与报告措辞）+ Thymeleaf → OpenPDF + SQLite。**

一个刻意的取舍：**A 档不上 Spring Boot。** 这是一次性批处理，CLI 启动 200ms、单 jar 分发、零运维；等"月度复测订阅"真的有人买，再用 Spring Boot + 定时任务包一层。8 年 Java 的经验在这里的正确用法是"少写框架"，不是"多写分层"。

**关键模块：**

- `crawler`：礼貌抓取（1 req/s、尊重 robots），sitemap 优先，失败降级到 collection 页；记录抓取时间，报告里必须带。
- `extractor`：JSON-LD / microdata / OpenGraph 三路抽取，合并成统一的 `ProductFact`；冲突时保留全部来源，不做"聪明"的合并。
- `consistency`：页面价 vs 结构化价 vs feed 价，容忍币种、税费、四舍五入差异；库存三态（in stock / out of stock / preorder）。
- `variant-model`：把 option 组合映射到 variant SKU，检查每个组合是否都有价、有货、有图——这一步最能出"哇"的效果。
- `agent-probe`：固定 10 问（"X 和 Y 哪个更适合敏感肌""到德国要几天""能不能退"），跑 2-3 个模型，记录引用 URL 与事实错误。
- `report`：评分卡 + 工单 + 对比页，Thymeleaf 模板 + OpenPDF。

**可复用：** Jsoup、Playwright Java、LangChain4j、OpenPDF、json-schema-validator、SQLite JDBC；Google 的 Rich Results Test 和 Merchant Center 诊断可以作为交叉验证，但不要抓它们的页面当数据源。

### 6. 变现方式

| 档位 | 价格 | 内容 |
|---|---|---|
| 单店审计 | ¥699 / $99 | 50 SKU、五维评分、20 条工单、30 分钟讲解 |
| 三店打包 | ¥1,800 | 同品牌多站 / 多语言站 |
| 月度复测 | ¥299/月 | 每月重跑 + 变更 diff + 新工单 |
| 服务商白标 | ¥2,999/月 | 10 份/月，贴服务商 logo |

渠道：跨境卖家微信群 / 知识星球、Shopify 建站与代运营服务商（分包，返 20-30%）、Upwork / Fiverr 搜 "product feed audit / AI shopping readiness"、LinkedIn 冷信；样报发到 r/shopify、r/ecommerce（先看版规，别硬广）。

### 7. 投入估算

- 首个可卖版本：2 个周末，12-16 小时（CLI + 报告模板 + 10 问脚本）。
- 上线后：3-5 小时/周（跑单、写报告、复测）。
- 现金成本：<¥100/月（模型 API + 域名），服务器 0（本地跑）。

### 8. 风险与壁垒

- **品类太早（最大风险）**：Wallet 只在美国、只对 Pro 开放，Agent 带来的成交可能 12 个月内都很小。对策：卖"多渠道机器可读性"（Google / Meta / TikTok Shop + AI），不要只押 ChatGPT。
- **平台收编**：Shopify 可能原生补齐结构化字段，Amazon / Google 可能定义 Agent 商品标准。壁垒不在代码，在评分口径 + 跨平台对比案例 + 能直接照着改的工单。
- **客户只认成交不认曝光**：报告必须给"修复后 2 周复测"和"哪条工单最可能影响报价/加购"的排序，否则就是一次性买卖。
- **责任边界**：不承诺被 AI 推荐；报告写明"基于 X 月 X 日、X 模型的实测"，模型换版就重测。

### 9. 第一步行动

本周末：选一个细分类目（建议宠物用品），从 sitemap 抓 20 家 Shopify 店，**先不写代码**，用浏览器 + 结构化数据测试工具 + 3 个 Agent 提问，手工跑完五维检查，产出 1 份样报。把样报发给 5 个卖家，话术只有一句："我测了你的店在 ChatGPT 里被怎么描述，发现 3 个价格/库存对不上的地方，报告免费给你，要不要？" 记录回复率，以及"能不能帮我改"的比例——后者超过 30%，才值得写代码。

## 【B】LaunchGuard：国区 App Store「AIGC 上架合规包」

### 1. 机会点

帮 1-5 人的 iOS 团队在 2027-01-31 前把国区 AIGC 上架的两项必填材料备齐：先判定"你到底要办哪个备案 / 要不要安全评估"，再生成可提交、可编辑的材料包，最后做一遍提交前自检——按 App 收 299 元自助、1,999 元陪跑。

### 2. 为什么是现在

- **入口被焊死了。** 11 月 16 日，开发者反馈 App Store Connect 后台新增「人工智能生成或合成内容（AIGC）服务声明与备案信息」与「已完成安全评估的证明」两项中国大陆分发必填项。含 AIGC 服务的 App 需提交备案及安全评估报告副本；若使用第三方技术或模型，还须提供授权或盖章合作协议与算法备案号。新 App 需立即提交，现有 App 须在 2027 年 1 月 31 日前完成（[少数派派早报 11-18](https://sspai.com/post/119210)）。
- **社区的困惑是实时的、具体的。** 同一天 V2EX 独立开发者节点出现《Apple 开发者新规，目前有评估通过的吗？》，楼主的口径是"只要你的 App 会调用大模型 API 来生成回复，基本都包含在这次要求里"，并贴出 App Store Connect 的中国大陆合规信息帮助页（[V2EX 1258053](https://www.v2ex.com/t/1258053)；[Apple 帮助页](https://developer.apple.com/help/app-store-connect/manage-compliance-information/view-china-mainland-compliance-information)）。评论区的高赞情绪是"和做游戏一样，最难的是获得版号""备案的麻烦程度比整个 App Store 上架还高"——这就是付费理由。
- **监管在同步收紧，不是一次性表单。** 11 月 11 日广东新增 3 款生成式 AI 备案、累计 230 款，并要求在显著位置或产品详情页展示备案编号、按《人工智能生成合成内容标识办法》为生成内容加标识（[日报 11-13 #8](https://www.sohu.com/a/1100596612_122066678)）。
- **标识已经进入司法责任分配。** 11 月 11 日北京互联网法院披露：平台把用户原创文字误判为"AI 生成未标识"，隐藏内容并禁言，被判违约，须恢复内容、删除违规处理记录，并被建议建立阶梯式处置与误判救济机制（[IT之家 11-11](https://www.ithome.com/1/025/592.htm)）。标识不是"上架时勾一下"，是运营期的持续义务。
- **授权链条正在成为平台标配。** 11 月 9 日红果短剧上线 AI 剧虚拟形象确权，要求创作者前置提交真人授权、上游 IP 授权或著作权登记材料，审核通过后形成确权记录（[IT之家 11-11](https://www.ithome.com/1/025/569.htm)）。这和苹果要的"第三方模型授权/盖章合作协议"是同一套逻辑。

这是一道截止日期题，不是判断题。而大代办机构看不上"一个 App"的小单，正好留给个人开发者。

### 3. 目标用户 + 具体痛点

**用户：个人开发者 / 1-5 人 iOS 团队**，App 里有 AI 对话、AI 写作、AI 生图、AI 翻译、角色扮演、AI 头像；月流水 0-5 万元；绝大多数没有法务，也没做过任何备案。

痛点是"不知道"和"不敢问"：

- 分不清三件事：**算法备案**（互联网信息服务算法备案系统）、**生成式 AI 服务备案**（大模型上线备案）、**安全评估**（具有舆论属性或社会动员能力的互联网信息服务）。不知道自己属于哪一种，还是都不属于。
- 主体对不上：开发者账号是个人、App 是海外公司、收款又是另一个主体——备案主体和开发者账号不一致，怎么解释、能不能过。
- 调 OpenAI / Claude 这类境外 API 到底能不能过？用国内第三方模型要的"授权或盖章合作协议"长什么样，"算法备案号"去哪里要。
- 安全评估报告谁写、多少页、要不要盖章、要不要渗透测试；网上 2023 年的模板还能不能用。
- 内容标识怎么落：显式标识（生成图片角标、文本提示）+ 隐式标识（元数据），iOS 端加在哪一层、会不会反而被判"诱导性标识"。
- 被拒后拒信只说"材料不完整"，不知道补哪一项，一来一回两周，眼看赶不上 1 月 31 日。
- 存量 App 拖到 12 月才发现要补，临时抱佛脚。

一句话：他们要的不是"法律意见"，是"一张告诉我先办哪个、交什么、怎么填的图，和一套能直接改的模板"。

### 4. MVP 范围

**做：**

- 判定问卷（12 题）：App 功能类型、是否面向公众、是否含 UGC、模型来源（自研 / 国内第三方 API / 境外 API / 端侧）、是否涉及未成年人或医疗金融等敏感场景、主体类型。
- 判定树输出：一张"你要办什么"的路径图（官方入口、所需材料、预计周期、可否豁免）+ 风险提示。例如：个人主体通常无法完成大模型备案，正确路线是"使用已备案模型 + 补齐授权链 + 做好内容标识"，而不是硬冲备案。
- 材料包生成（Word 优先、PDF 定稿，必须可编辑）：算法备案表字段草稿、安全评估报告骨架（安全管理制度、应急处置、日志留存、未成年人保护、投诉举报）、第三方模型授权条款清单、内容标识方案（含 iOS 实现建议）、隐私政策增补条款。
- 提交前自检清单（20 项）：描述/截图是否宣称 AI 能力、是否展示备案号、是否有"AI 生成"标识、是否有举报入口、是否有未成年人模式、是否收集了不必要的人脸/声纹。
- 拒审申诉信模板库，按拒审理由分类。

**明确砍掉：**

- 不代办跑腿、不出法律意见、不自动提交到网信办或苹果。
- 不做 Android 各应用商店（后续再说）、不做渗透测试/等保。
- 不做"包过"承诺——既涉嫌虚假宣传，也毁口碑。

### 5. 技术方案

**选型：Java 21 + Spring Boot 3.3 + PostgreSQL + Flyway + Thymeleaf/HTMX + docx4j（生成可编辑 Word）+ OpenPDF（定稿 PDF）+ LangChain4j（问卷追问、材料初稿、拒信用语解析）+ YAML 规则表。**

核心不是 AI，是**规则版本化**：政策每月都在动，代码不能跟着改。

**关键模块：**

- `policy-version`：每条规则带生效日期、来源链接、适用地区；政策变了只改 YAML，报告首页自动印"本报告基于 2026-11-18 口径"。这一条决定你能不能在政策变动时活下来。
- `decision-tree`：YAML 定义节点与边，输出路径 + 材料清单 + 周期；命中"个人主体 + 境外 API"这类组合时，直接给替代路线而不是报错。
- `doc-composer`：模板 + 变量 + 段落库；同一份材料按"首次提交 / 被拒补充 / 年度复审"出三个版本。
- `evidence-pack`：客户上传的截图、授权函、备案号、隐私政策存成"证据包"，一键导出 zip，附材料清单和盖章位置标注。
- `review-console`：人工复核工作台（目标 30 分钟一单），标注"必须改 / 建议改"，生成批注版给客户。

## 【C】PatchProof：Java 运行时暴露面与「补丁证据链」

### 1. 机会点

以 Java4Shell 为切口，做一套"Java 运行时资产台账 + 可利用性判定 + 处置证据"工具：一次采集把 JDK 版本、CPU 指令集、容器镜像、网络暴露串起来，直接回答"我们哪些系统受影响、能不能真的被打到、今天怎么处置、怎么向甲方证明"。

### 2. 为什么是现在

- **本周 HN 头条就是给 Java 工程师的。** 11 月 17 日披露的 Java4Shell（CVE-2026-114938，CVSS 4.0 评分 9.2）是 OpenJDK Base64 解码器 intrinsic 的堆越界写，触发串只要 64 个 `A` 加一个 `=`（较早的 OpenJDK 17 构建是 128 个）。默认配置下，Keycloak、Jira、Confluence、Artifactory、Jenkins、PingFederate 可预认证 RCE；Kafka、Solr、Elasticsearch、Gerrit、Spinnaker 认证后可 RCE；Spring Boot 示例应用也中；客户端连恶意 TLS 服务器同样可能中招（[Calif Research](https://calif.io/java4shell/)；[HN 961 分 / 243 评论](https://news.ycombinator.com/item?id=50538240)）。
- **"版本受影响"和"你真的能被打"是两件事。** 受影响范围是 OpenJDK 17.0.6 及以上，Corretto / Temurin / Microsoft Build / Zulu / Liberica / SapMachine / Red Hat OpenJDK / Oracle JDK / GraalVM 全系；但利用还需要 x86-64 + AVX-512 VBMI（Ice Lake 之后的 Xeon、Zen 4 之后的 EPYC），ARM64 不受影响。Oracle 列出的受影响版本包括 8u511b33-perf、17.0.21.0.3、21.0.13.0.3、25.0.5.0.3、27.0.1.0.3（同上）。
- **补丁已发，窗口只有几周。** OpenJDK 与 Oracle 于 11 月 17 日 13:00 PT 发布补丁；临时缓解是 `-XX:-UseBASE64Intrinsics` 或 `-XX:UseAVX=2`，且只对 x86-64 有效——ARM 上加了 `UseAVX` 参数 JVM 直接起不来。未来 2-4 周是"排查 + 处置"的高峰，之后转入常规补丁管理（同上）。
- **供应链信任在同步崩塌。** 11 月 18 日 HN 335 分的《Microsoft's ONNX Runtime has disappeared from GitHub》提醒所有人：仓库会消失、会被接管、会下架，光靠版本号匹配解决不了"这个包还在不在、还是不是原来那个人维护的"（[HN 50539610](https://news.ycombinator.com/item?id=50539610)）。
- **监管把"可证明的安全控制"变成硬要求。** 11 月 16 日加州总检察长起诉 OpenAI，称其至少 80 次智能体失控（[日报 11-17 #3](https://www.ithome.com/1/028/028.htm)）；11 月 12 日五家前沿 AI 公司被集体起诉，原告要求被告证明技术处于人类控制（[日报 11-13 #4](https://www.ithome.com/1/026/466.htm)）；11 月 10 日澳大利亚公布强制事故上报与"未能预防"刑责的监管框架（日报 11-12 #5）。企业采购、等保、甲方验收都在从"你说你修了"转向"拿证据来"。
- **现有工具只做版本匹配。** Trivy / Grype / Dependency-Track 能告诉你"这个 jar 对应哪个 CVE"，回答不了"这台机器有没有 AVX-512、这个容器有没有暴露 Base64 入口、这个 Jenkins 是不是预认证可达"。

### 3. 目标用户 + 具体痛点

**用户：20-200 人的研发团队 / 外包公司 / 信创集成商**，跑 Jenkins、Confluence、Jira、Kafka、Elasticsearch、Keycloak；或者给甲方交付 Java 系统的乙方（需要出报告的那一方）。

- 资产台账里只有"Spring Boot 2.7 + JDK 8"，但容器基础镜像里到底是哪个 vendor 的 JDK、补丁级别多少，没人说得清。
- 300 个容器、200 台 VM，安全团队发一张 Excel 要 48 小时填完，填的还是"疑似"。
- 不知道自己的 CPU 有没有 AVX-512 VBMI；云上实例类型换了一轮又一轮，`/proc/cpuinfo` 没人看。
- 就算版本中招，也要判断 Base64 入口是否外部可达：Jenkins remoting、Confluence REST、Keycloak token endpoint，哪些走预认证。
- 打补丁要停 JVM，Jenkins / Confluence 的升级窗口排到下个月；临时参数能撑，但没人敢在生产加 `-XX:-UseBASE64Intrinsics`，怕性能掉、怕背锅。
- 甲方和等保要"处置证据"：谁、什么时候、依据哪个版本、改了哪个参数、回归了什么。

一句话：他们不缺一个 CVE 列表，缺的是"能在 4 小时内签字的那张纸"。

### 4. MVP 范围

**做：**

- 采集：agentless（SSH）读 `java -version`、`$JAVA_HOME/release`、`/proc/cpuinfo` 的 flags、监听端口；容器侧直接解析镜像层里的 JDK（不依赖 docker daemon），支持 K8s 镜像清单导入。
- 判定：三态输出（受影响 / 不受影响 / 需人工确认），依据 = 版本区间 × CPU flag × 产品指纹 × 网络暴露；每条结论都带"判定依据"原文，可审计。
- 处置：生成 K8s Deployment / systemd 的启动参数 patch、升级路径（哪个 vendor 的哪个版本）、回归测试清单（登录、文件上传、TLS 客户端、JWT）。
- 证据：JSON + PDF 报告（资产、判定、处置状态、时间戳、执行人），能直接给甲方。
- 复测：处置后重跑，出"关闭率"。

**明确砍掉：**

- 不做完整 SBOM 平台、不做代码级污点分析、不做自动热补丁、不做 RASP。
- 不做多租户计费（先单机 / 私有化），不做移动端。
- 不在报告里放任何 exploit 代码——只做防御性判定。

### 5. 技术方案

**选型：Java 21 + picocli（采集器 CLI，单 jar 分发）+ Spring Boot 3.3（控制台/API）+ PostgreSQL + Flyway + fabric8 Kubernetes Client + Apache MINA SSHD（agentless）+ tar/zip（镜像层解析）+ JSON 规则表 + React 或 htmx + OpenPDF + Docker Compose / 离线安装包。**

**关键模块：**

- `collector`：虚拟线程并发 SSH，只读命令白名单，输出标准化 `AssetFact`（vendor、version、cpu flags、ports、product fingerprint）。
- `image-inspector`：拉 manifest → 层 tar → 找 `.../release`、`lib/modules`、`java` 二进制；算 JDK vendor/version，不启动容器。
- `rule-engine`：JSON 规则（affected_versions / cpu_flags / product_fingerprints / exposure），每条带 CVE 编号、来源、发布日期；支持"厂商未修但可缓解"的状态。
- `exposure-graph`：端口 + 路径 + 产品指纹 → 预认证 / 认证后 / 不可达；输出按"可利用性"排序，而不是按 CVSS 排序——这是和免费工具最大的差别。
- `remediation`：模板化 patch（K8s env / `JAVA_TOOL_OPTIONS`、systemd、Dockerfile），每条附副作用说明（例如 `-XX:UseAVX=2` 会关掉 AVX-512，Base64 与部分加解密可能变慢，需要压测）。
- `evidence`：签名报告（哈希 + 时间戳），可导出给等保 / 甲方。

**可复用：** fabric8、MINA SSHD、OSV API / NVD feed、Dependency-Track 的数据模型（不要重造 CVE 库）、Trivy 的镜像层解析思路；规则格式直接对齐 OSV schema，省掉一轮设计。

## 本周机会小结 + 建议优先做哪一个

三个方向的共同点：**本周的钱，都藏在"别人要验证你"这件事里。** A 是购物 Agent 要验证你的货架，B 是苹果和监管要验证你的材料，C 是甲方和等保要验证你的补丁。它们都不是"再造一个 AI 应用"，而是给新链路补上可读、可审、可证的基础设施——脏活，也正因如此，大厂看不上、个人开发者能吃到。

- **A（AgentShelf）验证最快、成本最低**，两个周末就能拿出样报；但品类最早，Agent 成交规模可能 12 个月内都很小。适合当实验，不适合当主线。
- **B（LaunchGuard）时间窗口最硬、付费理由最直接、启动成本最低**，是本月最可能收到钱的；缺点是政策依赖强，必须有合规顾问兜底，且不能承诺"包过"。
- **C（PatchProof）最匹配 8 年 Java 的能力复利**，天花板最高、客户付费能力最强；但销售周期长，需要 3-6 个月养规则库和案例，不适合作为第一个动作。

**建议：先做 B，A 当周末实验，C 用开源 CLI 先埋钉子。**

具体节奏：

1. **第 1 周**：B 的判定问卷 + 一页路径图发出去，目标 30 份问卷；A 手工做 1 份样报，发 5 个卖家；C 的 `j4s-check` 开源，跑 10 个公开镜像。
2. **第 2-4 周**：B 手工交付前 3 单（模板 + 复核），验证 ¥299 / ¥1,999 的转化；A 只在有人问"能不能帮我改"时才继续投入；C 收 50 份环境样本，写第二篇实测。
3. **第 5-8 周**：B 若月单 ≥5，做自助版判定树；C 若"300 个容器"的对话 ≥3，做控制台；A 若 10 份报告 0 付费，直接停。
4. **第 9-12 周**：用三个数字决定加码——B 的月收入、C 的付费客户数、A 的复购率。哪个先到阈值，哪个就是主线；都没到，说明问题定义错了，回去改访谈，而不是加功能。
