# 工作日报 / 周报 / 月报 · 自动化运行说明

> **本任务当前使用的模型：`deepseek-v4.1-flash`**（provider 为 `opay-gateway`，仅本任务固定使用，不影响 App 默认模型）
>
> 最后更新：2026-10-09
> 本文档说明这套自动化的运行逻辑、配置修改方式、以及停止/恢复方法。

---

## 1. 这套自动化做什么

| 模式 | 触发时间 | 覆盖窗口 | 产物 |
|---|---|---|---|
| **日报** `daily` | 工作日（周一~周五）**19:00** | 上次日报结束 → 现在（增量） | `summary/daily/<年月日>.md` |
| **周报** `weekly` | 每周五 **18:00** | 上次周报结束 → 现在 | `summary/weekly/<年>-W<周数>.md` |
| **月报** `monthly` | 每月 1 日 **10:30** | 上次月报结束 → 现在 | `summary/monthly/<年月>.md` |

**产物命名规则**：日报/周报按「窗口覆盖到的最后一天」取名（`end` 是开区间，故减 1 秒）；
月报按「窗口起始月」取名（月报在上月 1 号之后跑，覆盖的是上一个自然月）。

> ⚠️ **关于周报 18:00 的一个已知取舍**：周报在周五 18:00 跑，而当天日报在 19:00 跑，
> 所以**周五 18:00–19:00 这一小时的工作不会出现在当周周报里**，而是被算进下周周报的窗口
> （因为周报窗口是「上周五 18:00 → 本周五 18:00」）。内容不会丢，只是归属到下一周。
> 若希望周五当天的工作完整落在当周周报，把周报改到 19:30 之后即可（见 5.1 节）。

**数据来源（全部只读）**

| 来源 | 位置 | 能取到什么 |
|---|---|---|
| Codex 会话明细 | `~/.codex/sessions/**/rollout-*.jsonl` | 提问原文、AI 结论、执行命令、文件改动 |
| Codex 线程元信息 | `~/.codex/state_5.sqlite` | 标题、工作目录、分支、token 用量 |
| **DSH 会话明细** | `~/.dsh/sessions/*/*/session.v4.jsonl.zstd` | 提问原文（已过滤 harness 注入）、执行命令、写入的文件、`deliverables` 交付物 |
| Trae SOLO CN | `~/Library/Application Support/TRAE SOLO CN/` | ⚠️ 仅会话元数据（会话 ID / 工作区 / 模型 / 时间 / 状态 / 文件变更计数） |
| 代码提交 | 本地 git 仓库（`~/code-temp`、`~/IdeaProjects`） | 窗口内提交（按 author 过滤，只统计本人） |

> ⚠️ **Trae 会话正文不可读**：Trae 的会话库 `ModularData/ai-agent/database.db` 使用 SQLCipher 加密
> （模块 `libai_agent.dylib` 内含 `sqlcipher_export`），密钥在云端/运行时，本地无法解密。
> 因此 Trae 端只能写元数据，写不了对话内容。

**DSH 采集的三个坑**（都已处理，改这块代码前先读）：

1. **是 zstd 压缩的 JSONL**。需要外部 `zstd`；launchd 的 `PATH` 里没有 Homebrew，
   所以 `_zstd_bin()` 按 `which → /opt/homebrew/bin → /usr/local/bin → /usr/bin` 逐个兜底，
   找不到就只降级为「无 DSH 数据」，不会中断采集。
2. **`user/message` 里绝大多数不是真人输入**。DSH 把时间上下文、运行时上下文、技能目录、
   后台任务完成通知、压缩检查点、模型切换等都记成 `user/message`，靠 `data.source.kind` 区分：
   **只有 `kind == "user"` 才是真人输入**（实测 238 条里只有 72 条）。
   不过滤会把 `<system-reminder>`、`Time sampled while...`、`background job bash-N` 灌进报告。
3. **续聊/分叉会话会整段重放父会话历史**。子会话的 `createdAt` 恰好等于父会话最早事件的时刻，
   照单全收会重复计数。因此只统计 `time >= createdAt` 的事件（父会话文件里已有一份），
   另外再按 `user/message.id` / `tool/call.callId` 做一次全局去重兜底。

> **自动化自跑的会话会被排除**：执行器在提示词第一行写 `<!-- DSH_AUTOMATION_RUN:... -->`，
> 采集器见到这个标记就跳过该会话——否则「生成日报」这件事本身会每天出现在日报里。
> 加标记之前的早期运行靠提示词前缀（`你是「`、`执行每日 AI 行业热点新闻速览`）识别。
> 被跳过的会话记录在 `evidence.dsh.skipped_automation_sessions[]`，可核对。

## 2. 底层运行逻辑（完整链路）

```
launchd（按各自时间触发）
  └─ /usr/bin/python3 scripts/work-report/run.py --mode daily|weekly|monthly
       ├─ 读水位线 .dsh-work-report-logs/state.json → 算出增量窗口 [start, end)
       ├─ 看护子进程：超时则杀进程组，退出码 124，并给产物加“-执行超时”后缀
       ├─ 切换到工作目录 /Users/opay-20260271/code-temp/ai-md
       └─ 启动 DSH 无头模式：
            dsh --profile headless \
                --patch ~/.dsh/profiles/desktop/cordis.patch.yml \
                --patch ~/code-temp/ai-md/whatsapp_crm_docs/scripts/work-report/model.patch.yml \
                "<任务提示词>"
              ├─ 第 1 步：读相关报告（上一份同类报告 + 窗口内日报/周报，由执行器算好路径）
              ├─ 第 2 步：跑只读采集器
              │     scripts/work-report/collect.py --start .. --end .. -o .dsh-work-report-logs/evidence-*.json
              ├─ 第 3 步：读 evidence.json（codex / trae / git 三段）
              ├─ 第 4 步：按固定模板写出报告到 summary/<subdir>/<名字>.md（含「承接与延续」对账章节）
              └─ 第 5 步：自检（不把 Guardian review 子会话当工作项、不把他人提交算产出、不编造、不原样复述上一份报告）
  └─ 成功(exit=0)后推进水位线；下次从新的水位线继续
```

### 六个关键设计点

1. **为什么写入不需要审批。**
   DSH 的 `workspace-write` 沙箱没有"按目录加白名单"的能力，规则是：**会话的工作目录（cwd）就是写入边界**。
   所以本任务把 cwd 设为 `/Users/opay-20260271/code-temp/ai-md`，产物落在它下面的
   `whatsapp_crm_docs/summary/` 里，天然在边界内 → 永久免审批，放行范围只有这一棵树。

2. **增量窗口由执行器算，不交给模型。**
   水位线存在 `state.json`，只在**执行成功**后才推进。所以某天没跑、或跑失败了，
   下次会**自动把漏掉的时间段补进来**，不会丢内容，也不会重复统计。

   同时有一层**下限钳制**：本次窗口的起点至少会被拉到「当前周期的起点」
   （日报=当天 00:00，周报=本周一，月报=本月 1 日）。作用是——
   同一天里手动重跑，窗口只会变宽不会变窄，**不会把已经写好的当天报告覆盖成"只有下午"的残缺版**。
   例如水位线是 `10-09 19:00`、当天 20:30 再跑一次，窗口仍是 `10-09 00:00 → 10-09 20:30`。

3. **只统计本人提交。**
   报告里的"代码提交"一节按 `git author = licun.zha` 过滤，同事的提交不计入产出
   （采集器会把全部提交都抓下来，由提示词约束过滤，方便需要时回溯）。

4. **超时会被"看得见"。**
   超时被杀时不会留报错，只有日志；所以执行器在杀进程后会把产物改名加 `-执行超时` 后缀
   （若本次没写出文件，则建一个同名提示文件）。产物目录里一眼就能看出"这天没跑完"。

5. **跨报告关联：日报之间、以及周/月报与日报之间是打通的。**
   因为日报是"连续时间轴上的切片"，相邻两份天然会共享同一件事，所以每份报告生成前，
   执行器会**自动算出该读哪些历史报告**并把路径写进提示词：

   | 模式 | 「上一份同类报告」 | 「窗口内的历史日报/周报」 |
   |---|---|---|
   | 日报 | 最近 **2** 份日报 | — |
   | 周报 | 最近 **1** 份周报 | 窗口内**全部日报**（最多 7 份） |
   | 月报 | 最近 **1** 份月报 | 窗口内**全部周报**（最多 5 份）+ **全部日报**（最多 31 份） |

   基于这些引用，报告里有两个硬要求：
   - **承接标记**：明细里承接上一份报告的工作，小标题后标「（承接 MM-DD）」；
   - **对账章节**：日报的「七、承接与延续」、周报的「七、承接与延续」、月报的「八、承接与延续」，
     要**逐条**给上一份报告「待跟进」项的当前状态（`已闭环 / 进行中 / 无变化`）+ 依据，
     并且**不许原样复述**上一份报告已写完的结论，只写新增的变化。

   **周报/月报和日报的关系**：不是"拿日报拼起来"，而是**以日报为主线事实来源、用原始采集结果做校验**。
   周报/月报同样会重新跑一遍只读采集器，一方面用于核对数字、补日报的遗漏，
   另一方面当天日报缺失或互相冲突时以它裁决。主题必须**跨天/跨周合并成一条**，禁止流水账。

   > 为什么不让周报/月报纯粹基于日报？日报一旦哪天没跑或有偏差，纯拼接会把误差放大到周/月级别；
   > 而两者都读、并要求冲突时说明以哪个为准，既保住了连续性也保住了准确性。

   日报会取**最近 3 份**日报：最后一份用于「承接与延续」逐条对账，
   更早的两份只读它们的「总结」和「待跟进」两节，供「思考」识别反复出现的问题。

6. **「总结」是概括，「思考」是推断，两者分工明确。**
   - **总结**（正文靠前）回答「今天到底推进了什么」，四个小节：结果盘点 / 投入分布 / 进展与空转 / 与预期偏差。
     它是**结论**，不是明细的复述——明细是证据，总结是收口。
     「空转」一项要求如实写（调研、被打断、返工、在等别人），否则这一节没有价值。
   - **思考**（正文靠后）分「复盘（给自己）」和「建议（给方向）」两个小节，
     必须**跨报告找模式**（例如"同一件手工验证最近三份日报里出现了三次"），
     每条都要标注依据（日报文件名 / 提交号 / 命令 / 证据字段）。
   - 思考部分固定以「以下为 AI 依据采集数据推断，可能不准确，供参考」开头。
     没有依据的猜测一律不写——**宁可少写两条，也不要输出听起来合理但无根据的建议**。

## 3. 文件清单

> **脚本按需求分目录**：`whatsapp_crm_docs/scripts/<需求>/`，一个需求一个子目录，
> 目录内自带该需求的执行器、模型补丁和辅助文件。属于 git 仓库 `whatsapp_crm_docs`，方便跟文档一起版本管理。
>
> ```
> whatsapp_crm_docs/scripts/
> ├── work-report/          ← 需求：工作日报 / 周报 / 月报
> │   ├── run.py               执行器（配置 + 提示词 + 超时看护）
> │   ├── collect.py           只读采集器（Codex / DSH / Trae / git）
> │   └── model.patch.yml      本任务专用的模型覆盖层
> └── ai-news/              ← 需求：每日 AI 行业新闻
>     ├── run.py               执行器
>     └── model.patch.yml      本任务专用的模型覆盖层
> ```
>
> 执行器内的同目录资源一律用 `os.path.dirname(__file__)` 推算（`SCRIPT_DIR`），
> **所以整个需求目录可以整体挪动或改名，不必改代码**；只有 `WORKDIR` 是写死的，
> 因为它是「沙箱写入边界」这一语义配置，不是相对位置。
> 日志与水位线仍在 `ai-md/.dsh-work-report-logs/`（新闻任务在 `ai-md/.dsh-news-logs/`）。
>
> 下表中 `scripts/...` 指 `~/code-temp/ai-md/whatsapp_crm_docs/scripts/...`，
> `.dsh-work-report-logs/...` 指 `~/code-temp/ai-md/.dsh-work-report-logs/...`。

| 路径 | 作用 | 什么时候需要动它 |
|---|---|---|
| `~/Library/LaunchAgents/com.opays.dsh.daily-work-report.plist` | 日报触发定义 | 改**日报时间**时 |
| `~/Library/LaunchAgents/com.opays.dsh.weekly-work-report.plist` | 周报触发定义 | 改**周报时间**时 |
| `~/Library/LaunchAgents/com.opays.dsh.monthly-work-report.plist` | 月报触发定义 | 改**月报时间**时 |
| `scripts/work-report/run.py` | 执行器：所有可调配置（超时、提示词、水位线、作者、自动化标记）+ 超时看护 | 改**超时 / 提示词 / 作者**时 |
| `scripts/work-report/collect.py` | 只读采集器（Codex / **DSH** / Trae / git） | 需要新增数据源时 |
| `scripts/work-report/model.patch.yml` | 模型层：只钉本任务使用的模型（当前 `deepseek-v4.1-flash`） | 改**任务所用模型**时 |
| `scripts/ai-news/`（`run.py` + `model.patch.yml`） | 另一套：「每日 AI 新闻」自动化 | 改新闻任务时 |
| `summary/重新执行工作日报.command` | 手动重跑（Finder 双击，默认日报） | 超时/失败后重跑 |
| `news/重新执行新闻任务.command` | 手动重跑新闻任务 | 超时/失败后重跑 |
| `.dsh-work-report-logs/state.json` | **水位线**（三种模式各自的 last_*_end） | 需要手动调整统计起点时 |
| `.dsh-work-report-logs/run.log` | 每次运行的开始/结束/退出码（首选排查入口） | 排查失败 |
| `.dsh-work-report-logs/dsh-output.log` | 无头 Agent 的完整输出 | 排查内容质量 |
| `.dsh-work-report-logs/evidence-*.json` | 本次采集到的原始证据（含 `codex` / `dsh` / `trae` / `git` 四段） | 想核对报告是否失真时 |
| `.dsh-work-report-logs/out.log`、`err.log` | launchd 捕获的 stdout / stderr | 排查脚本级错误 |
| `summary/daily/` `summary/weekly/` `summary/monthly/` | 交付产物 | — |

## 5. 如何修改配置

### 5.1 改触发时间 ⏱

编辑对应的 plist（`StartCalendarInterval`），改完**必须重新加载**（plist 不像脚本那样自动重读）：

```bash
L=com.opays.dsh.daily-work-report        # 换成 weekly / monthly
P=~/Library/LaunchAgents/$L.plist
plutil -lint "$P"                                   # 先校验语法
launchctl bootout   gui/$(id -u)/$L 2>/dev/null || true
launchctl bootstrap gui/$(id -u) "$P"
launchctl print gui/$(id -u)/$L | grep -iE 'state|runs'
```

- `Weekday`：1=周一 … 5=周五，0 或 7=周日
- `Day`：几号

### 5.2 改超时时间

编辑 `scripts/work-report/run.py`，找到 CONFIG 段的：

```python
TIMEOUT_SECONDS = int(os.environ.get("DSH_WR_TIMEOUT", "1500"))   # 25 分钟
```

改成想要的秒数。**保存即生效，无需重载 launchd**。临时测试不改文件：

```bash
DSH_WR_TIMEOUT=120 /usr/bin/python3 /Users/opay-20260271/code-temp/ai-md/whatsapp_crm_docs/scripts/work-report/run.py --mode daily
```

### 5.3 改统计口径（作者 / 仓库 / 起始水位线）

都在 `scripts/work-report/run.py` 的 CONFIG 段：

```python
AUTHOR = "licun.zha"          # 只统计这个 git author 的提交
REPO_ROOTS = [...]            # 在 collect.py 里，扫描哪些目录下的 git 仓库
INITIAL_START = {...}         # 首次运行（无水位线时）的起始时间
```

### 5.4 改任务使用的模型 ⭐

与新闻任务同一套两层 patch 机制：基础层 `~/.dsh/profiles/desktop/cordis.patch.yml` +
模型层 `scripts/work-report/model.patch.yml`。改模型只需编辑模型层最后一行的 `model:`，
**保存即生效**。核对实际生效的模型：

```bash
D=/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh
"$D" --profile headless \
     --patch ~/.dsh/profiles/desktop/cordis.patch.yml \
     --patch /Users/opay-20260271/code-temp/ai-md/whatsapp_crm_docs/scripts/work-report/model.patch.yml \
     --dump-config | grep -A6 'id: agent-default-model' | grep -E 'provider:|model:'
```

### 5.5 想临时重跑某个历史区间

执行器支持显式指定窗口（**不会**动水位线）：

```bash
/usr/bin/python3 /Users/opay-20260271/code-temp/ai-md/whatsapp_crm_docs/scripts/work-report/run.py --mode daily \
    --start '2026-10-08 00:00:00' --end '2026-10-09 00:00:00'
```

只看窗口和提示词、不真正跑（`--dry-run`）：

```bash
/usr/bin/python3 /Users/opay-20260271/code-temp/ai-md/whatsapp_crm_docs/scripts/work-report/run.py --mode daily --dry-run
```

## 6. 如何停止 / 暂停 / 恢复

| 需求 | 命令 |
|---|---|
| **临时停止**（本次开机期间） | `launchctl bootout gui/$(id -u)/com.opays.dsh.daily-work-report`（weekly / monthly 同理） |
| **持续停用**（跨重启保持） | 先 `launchctl disable gui/$(id -u)/<label>`，再 `bootout` |
| **恢复运行** | `launchctl enable gui/$(id -u)/<label>` 然后 `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist` |
| **彻底卸载** | `bootout` 后删除 plist |
| **只跳过某一天** | 当天先 `bootout`，过后再 `bootstrap` |

只看状态、不做变更：`launchctl list | grep dsh`

## 7. 退出码与故障排查

| 退出码 | 含义 | 处理 |
|---|---|---|
| `0` | 成功（产物已写出 + 水位线已推进） | — |
| `124` | **超时被杀** | 产物被标记为 `-执行超时`，双击 `.command` 手动重跑 |
| `2` | 模型跑完了但**产物文件没写出来** | 看 `dsh-output.log` 尾部 |
| 其他非 0 | 运行失败 | 同上 |

**常见问题**

- `MISSING_CREDENTIAL` / `no API key for provider route`：模型凭据失效，检查 `~/.dsh/.credentials.yaml`；
  若提示 `deepseek-official`，说明 `--patch` 没生效。
- 重启后任务不跑：App 被移动/改名会导致 `DSH_CLI` 路径失效，更新执行器里的 `DSH_CLI`。
- `err.log` 里的 `codesign_util.cc: task_name_for_pid failure (5)`：Electron 无害警告，可忽略。
- **采集器报 `sqlite3.OperationalError: unable to open database file`**：这是已修复过的坑，成因是——
  Codex 的 `state_5.sqlite` 是 **WAL 模式**，用只读 URI（`file:...?mode=ro`）打开时，
  如果随库复制的 `-wal` / `-shm` 不存在（Codex 已 checkpoint 并关闭时就是这种情况），
  SQLite 需要自己创建共享内存文件，于是直接失败。
  **正确做法**：sqlite 库先复制到临时目录，再在**副本**上以普通模式打开
  （写入只落在临时副本里，原始文件自始至终没被打开过）。`collect.py` 的 `_open_ro_copy()` 已按此实现，
  并带 `immutable=1` 退路；`_thread_meta()` 失败时只降级为「无元信息」，不会拖垮整次采集。
- **睡眠/关机期间错过**：`StartCalendarInterval` 会在唤醒后补跑**最近一次**，不会逐日补齐。
  但由于是**增量窗口**，补跑的那次会把漏掉的全部内容覆盖进来，不会丢内容。
- **报告内容可疑**：直接看 `.dsh-work-report-logs/evidence-*.json`，那是报告的唯一事实来源。
- **报告里出现"今天又生成了一份日报"这类流水**：说明提示词里的「排除自动化自身日常产物」那条
  没被遵守，去 `build_prompt()` 的「铁律」段加强措辞即可，无需改代码。

## 8. 与「每日 AI 新闻」任务的关系

两套任务**完全独立**，互不影响：

| | 每日 AI 新闻 | 工作日报/周报/月报 |
|---|---|---|
| Label 前缀 | `com.opays.dsh.daily-ai-news` | `com.opays.dsh.{daily,weekly,monthly}-work-report` |
| 执行器 | `scripts/ai-news/run.py` | `scripts/work-report/run.py` |
| 模型层 | `scripts/ai-news/model.patch.yml` | `scripts/work-report/model.patch.yml` |
| 产物 | `whatsapp_crm_docs/news/<年月>/` | `whatsapp_crm_docs/summary/<daily\|weekly\|monthly>/` |
| 日志 | `.dsh-news-logs/` | `.dsh-work-report-logs/` |

两者共用同一个基础层 patch 与同一个工作目录（`ai-md`），所以写入都免审批。
