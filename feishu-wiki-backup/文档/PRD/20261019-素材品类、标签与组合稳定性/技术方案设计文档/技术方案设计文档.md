# 技术方案设计文档

## 1. 目标与统一口径

1. 指定白名单用户在“素材分类管理”页面维护可用于素材的分类（例如 repay_within_one_day、repay_within_two_days），作为新素材必选的“素材品类”。
2. 标签使用现有 tag.category_id -> category.id 关系。运营选择的标签必须与素材品类同分类；AI 跨品类标签作为候选保留，不参与正式标签筛选和效果统计。
3. 组合中仅允许一个真实品类；历史未分类素材可以与任意一个真实品类组合。
4. 素材创建时允许运营选择/新建同分类标签，创建后素材品类和运营标签不可改。
5. 素材模板列表和素材详情按需查看组合；新增组合维度稳定性评级 S > A > B > C > D。

## 2. 现状与数据模型选择

当前 `category` 有 `id/name/sort/status/ctime/utime`，`tag` 同时存 `category_id` 和冗余 `category_name`。人工建标签时后端按 `category_id` 找分类并填入名称；当前 AI 提取仅返回分类名称，后端按名称查询或创建 `category`。本方案要求 AI 额外返回 `categoryCode`，并由后端校验后落库。

因此：

- 复用 `category` 表：分类定义只维护一份，品类下自然有标签集合。
- 不能用 `tag.category_name` 作为品类主键：它是可修改的展示文本，且一个分类可以没有标签；不能依赖标签是否存在来判断品类是否存在。
- 不能让所有 AI 分类都进入品类下拉：AI 可能产生临时/不可控分类名称，素材品类还承担组合约束，必须显式准入。

目标关系：

```text
category (统一分类定义)
    ├─ code = repay_within_one_day, category_type = BUSINESS_MATERIAL
    ├─ Mongo 素材.material_category_code = repay_within_one_day
    └─ tag.category_id = category.id
         └─ tag_relation: 素材 ID -> tag ID

组合.material_category_code = 成员素材品类收口结果
```

分类是标签与素材品类的共同上层，但标签仍是可选的细分描述，不参加组合品类计算。

## 3. 核心业务规则

### 3.1 分类的两个用途

`category` 增加 `code`（稳定标识）、`source_type`（最初产生来源）和 `category_type`（业务类型）。来源与类型相互独立，不使用来源判断是否能选作素材品类。

- category_type=BUSINESS_MATERIAL：可作为新素材品类，且其下标签可供该品类素材选择。
- category_type=TAG_ONLY：只用于标签字典与 AI 候选；不能直接作为新素材品类。

| 情形 | 分类来源 `source_type` | 分类类型 `category_type` | 运营可在其下建标签 |
|---|---|---|---|
| 管理员发布 repay_within_one_day | 1（管理员维护） | `BUSINESS_MATERIAL` | 是 |
| AI 新提取“内容结构” | 0（AI 生成） | `TAG_ONLY` | 是（启用后） |
| 管理员认可已有 AI 分类 | 仍为 0（来源不改） | 审核后在管理页调整为 `BUSINESS_MATERIAL` | 是 |
| 已停用分类 | 保留原来源 | 保留原类型，但不可选 | 不可新建标签，历史可回显 |

统一来源码：`0=AI生成、1=管理员维护/编码规则、2=运营`。分类目前不开放普通运营创建，`2` 对分类仅预留。AI 分类默认是 `TAG_ONLY`；授权管理员在管理页将其调整为 `BUSINESS_MATERIAL` 时，保留原 `category.id/code/source_type`，不伪造最初来源，并记录操作人、时间及变更前后值。

### 3.2 素材品类与标签

- 新素材只能单选一个 status=1 且 category_type=BUSINESS_MATERIAL 的分类；提交其 category.code，创建后不可修改。
- 运营已选标签必须 status=1、type=MATERIAL，并满足 tag.category_id = 选中素材品类的 category.id；不能跨分类选择，也不能通过接口绕过校验。AI 标签另按 3.4 节区分正式生效与候选。
- 标签可以不选；同分类下没有标签也能创建素材。
- 页面创建标签只需填写名称（英文，64字符以内），分类由当前素材品类锁定，运营无需再选另一个分类；后端从品类 code 解析 category.id 并复核。
- 若运营切换尚未保存的新素材品类，前端清空已选标签并提示；后端仍校验每个 tagId 的分类。
- 既有素材的品类和运营标签在编辑素材模板时只读；新增素材遵守新规则。

### 3.3 未分类与组合

历史素材缺少品类字段，读取时解释为 `UNCATEGORIZED`。这是系统占位 code，**不创建 ****`category`**** 行，不出现在新建下拉中**。

| 组合成员 | 组合品类 | 处理 |
|---|---|---|
| 全部未分类 | `UNCATEGORIZED` | 允许 |
| 未分类 + repay_within_one_day | `repay_within_one_day` | 允许 |
| repay_within_one_day + repay_within_one_day | `repay_within_one_day` | 允许 |
| repay_within_one_day + repay_within_two_days | 无 | 禁止 |

组合只从**成员素材自身品类**计算，不从标签名称或标签分类反推。历史未分类素材在 repay_within_one_day 组合里仍是未分类素材，并不会被写成 repay_within_one_day。素材品类创建后不可改，组合品类保存为生成时快照。

### 3.4 AI 标签的正式与候选状态

当前 AI 按模型返回的 `categoryName/tagName` 创建或复用分类、标签，再绑定到素材。本方案将响应增加 `categoryCode`；AI 返回的分类**即使与运营选择的素材品类不同，也写入 ****`tag_relation`**，但区分两种生效状态：

- 素材品类为 repay_within_one_day、AI 标签也属于 repay_within_one_day：写 source_type=0, binding_status=1 (EFFECTIVE)。可进入正式标签筛选和后续效果统计。
- 素材品类为 repay_within_one_day、AI 标签属于另一分类：写 source_type=0, binding_status=0 (CANDIDATE)。可在素材详情的“AI 候选”区查看和供分析 Job 使用，但不参加正式标签筛选、效果统计，也不改变素材/组合品类。
- 历史 UNCATEGORIZED 素材：为兼容现有流程，AI 标签可写成 EFFECTIVE，但不可据标签反推或修改素材、组合品类；报告中单列“历史未分类”，不计入已分类素材的一致率。
- 同一标签同时被运营和 AI 命中时，可保留两条不同来源关系；运营关系始终 EFFECTIVE，AI 关系按上述规则判断。
- 分类之后经开发评审被调整为 BUSINESS_MATERIAL，不会自动把既有候选关系转正；候选状态代表提取当时与该素材品类的比较结果，下一次成功提取才重新计算当前状态。差异分析保留提取时的分类 code 和批次。

AI 重新提取只替换目标素材的 AI 来源标签关系，保留运营和编码规则来源关系；历史关系按已核实的 AI 来源口径处理，上线前发现非 AI 例外须先修正其来源。每次成功提取保留现有 `tag_extract_log` 的请求/响应，并使新 AI 关系指向对应批次。**候选关系保留最近一次成功判断，历史判断由提取日志追溯**；无效响应或调用失败不能清空上一批 AI 判断。

### 3.5 AI标签 与运营差异分析 Job

定时 Job 按最近一次成功提取批次比较素材品类、运营来源的有效标签、AI 来源的有效/候选标签，并归纳：同分类同标签、同分类不同标签、跨分类候选、AI 新增分类、历史未分类五种情况。统计关系条数、受影响素材数及有限样例 ID；同一素材可有多条来源不同或重复的关系，关系条数不等于素材数，不删除或合并原始关系。按日期汇总后供运营和白名单管理员评审。分析结果**只提供证据和建议**，不能直接按数量阈值自动转为正式可选分类；管理员结合业务定义、现有品类重叠程度、样例内容和连续观察结果，在管理页决定是否将分类类型改为 `BUSINESS_MATERIAL`。不自动修改历史素材品类，也不自动把候选关系转为正式；原始 AI 判断由 `tag_extract_log` 追溯。

## 4. 数据模型与迁移设计

#### 4.1 字段总览

| 库 | 对象 | 新增字段 | 类型/默认值 | 含义与写入方 |
|---|---|---|---|---|
| MySQL | `category` | `code` | `varchar(64) NOT NULL DEFAULT ''` | 稳定分类编码；旧行补齐后建唯一索引，管理页按 code 查询 |
| MySQL | `category` | `source_type` | `tinyint NOT NULL DEFAULT 0` | 来源：0 AI，1 管理员维护，2 运营（当前禁止）；按存量均由 AI 创建的口径处理 |
| MySQL | `category` | `category_type` | `varchar(32) NOT NULL DEFAULT 'TAG_ONLY'` | `BUSINESS_MATERIAL` 可作素材品类；`TAG_ONLY` 只作标签分类；仅白名单用户可调整 |
| Mongo | `message_material` | `material_category_code` | String | 新素材创建时写 `category.code`，历史缺失读作 `UNCATEGORIZED` |
| MySQL | `message_material_combination` | `material_category_code` | `varchar(64) NOT NULL DEFAULT 'UNCATEGORIZED'` | 保存组合品类快照；历史组合保持占位 |
| MySQL | `tag` | `source_type` | `tinyint NOT NULL DEFAULT 0` | 标签定义来源，0 AI，1 管理员维护，2 运营；`category_id` 仍为所属分类，`category_name` 只供展示 |
| MySQL | `tag_relation` | `source_type` | `tinyint NOT NULL DEFAULT 0` | 该条绑定来源；0 AI、1 编码规则、2 运营 |
| MySQL | `tag_relation` | `binding_status` | `tinyint NOT NULL DEFAULT 1` | 0 候选 CANDIDATE、1 正式 EFFECTIVE；只有跨品类 AI 关联写 0 |
| MySQL | `tag_relation` | `extract_log_id` | `bigint NOT NULL DEFAULT 0` | AI 提取批次 `tag_extract_log.id`；历史数据和非 AI 关系为 0 |
| MySQL | `material_category_tag_diff_stat` | 见下方新表 DDL | 新表 | 保存差异分析 Job 的按日汇总和样本 |

**来源、类型、状态分开存**：`source_type` 只说明来源，`category_type` 表示分类用途，`binding_status` 表示关联是否正式生效；三者不可混用。新写入应显式写入来源。本文按“现存 `category`、`tag`、`tag_relation` 记录均由 AI 创建”这一已确认业务口径，以默认 0 兼容历史；上线前仍须在实际库核实是否存在例外，发现例外需单独标记或修正，不能静默覆盖。

#### 4.2 DDL

所有新增 NOT NULL 列都有默认值；来源字段默认 0 是基于历史数据均由 AI 生成的业务口径。创建分类、标签和关联时，服务端仍须按实际操作者显式写入 0/1/2。

```SQL
ALTER TABLE `category`
  ADD COLUMN `code` varchar(64) NOT NULL DEFAULT '' COMMENT 'Stable category code',
  ADD COLUMN `source_type` tinyint(4) NOT NULL DEFAULT '0' COMMENT '0=AI, 1=admin, 2=operations',
  ADD COLUMN `category_type` varchar(32) NOT NULL DEFAULT 'TAG_ONLY' COMMENT 'BUSINESS_MATERIAL or TAG_ONLY';

ALTER TABLE `message_material_combination`
  ADD COLUMN `material_category_code` varchar(64) NOT NULL DEFAULT 'UNCATEGORIZED' COMMENT 'Resolved member material category';

ALTER TABLE `tag`
  ADD COLUMN `source_type` tinyint(4) NOT NULL DEFAULT '0' COMMENT 'Tag definition source: 0=AI, 1=admin, 2=operations';

ALTER TABLE `tag_relation`
  ADD COLUMN `source_type` tinyint(4) NOT NULL DEFAULT '0' COMMENT 'Tag binding source: 0=AI, 1=code, 2=operations',
  ADD COLUMN `binding_status` tinyint(4) NOT NULL DEFAULT '1' COMMENT '0=candidate, 1=effective',
  ADD COLUMN `extract_log_id` bigint(20) NOT NULL DEFAULT '0' COMMENT 'AI extract log ID; 0 for other sources';

CREATE TABLE `material_category_tag_diff_stat` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT 'Primary key',
  `stat_date` varchar(10) NOT NULL DEFAULT '' COMMENT 'Analysis date yyyy-MM-dd',
  `material_category_code` varchar(64) NOT NULL DEFAULT 'UNCATEGORIZED' COMMENT 'Material category',
  `ai_category_code` varchar(64) NOT NULL DEFAULT '' COMMENT 'Category suggested by AI',
  `diff_type` varchar(32) NOT NULL DEFAULT '' COMMENT 'SAME_TAG, SAME_CATEGORY, CROSS_CATEGORY, AI_NEW_CATEGORY, LEGACY_UNCATEGORIZED',
  `material_count` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Affected material count in this dimension',
  `relation_count` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Raw tag relation count in this dimension',
  `sample_material_ids` text COMMENT 'Bounded JSON array of sample Mongo IDs',
  `create_time` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Creation time',
  `update_time` bigint(20) NOT NULL DEFAULT '0' COMMENT 'Update time',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_stat_category_diff` (`stat_date`,`material_category_code`,`ai_category_code`,`diff_type`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Daily material category vs AI tag difference statistics';
```

`material_category_tag_diff_stat` 为可重算的每日汇总，不是标签关系的事实来源。`relation_count` 统计参与该维度比较的原始关联行数，**不合并同一素材/标签的多条记录**；`material_count` 统计该维度涉及的素材数，只用来表示覆盖面，不会删除或改写 `tag_relation` 的任何行。样本 ID 数量有上限；同一素材可命中多个 AI 分类，**不同维度的计数不能直接相加**。具体判断回查 `extract_log_id` 和提取日志。后续正式标签效果分析若从关系表关联发送数据，须防止一条发送记录被多条同标签关系放大；这只是统计查询口径，不是存储去重。

**哪些 AI 分类可以成为正式可选品类**：该表只提供参考证据，不设自动转正阈值。管理页按 AI 分类展示候选素材量、出现日期/趋势、关联标签和样例素材；运营判断是否有明确业务含义、是否与已有品类重复，并提供名称和用途；白名单管理员审核后在“素材分类管理”页将该 `category` 的 `category_type` 调整为 `BUSINESS_MATERIAL`。转正仅改变以后能否被新建素材选择，不回填历史素材、不自动将候选关系转为正式、也不改 `source_type=0` 的原始来源。

#### 4.3 索引

```SQL
ALTER TABLE `tag`
  ADD KEY `idx_category_type_source_type_status` (`category_id`,`type`,`source_type`,`status`);

ALTER TABLE `tag_relation`
  ADD KEY `idx_entity_status` (`entity_type`,`entity_id`,`binding_status`),
  ADD KEY `idx_extract_log_id` (`extract_log_id`);

-- 考虑是否需要添加，组合表数据量级万以内
ALTER TABLE `message_material_combination`
  ADD KEY `idx_material_category_code` (`material_category_code`);
```

`tag_relation` **不增加按素材/标签/来源的唯一索引**，允许同一素材、同一标签保存多条来源相同或不同的关联；后台读取保留这些行。索引仅用于查找，不承担去重。组合按成员素材 ID 查询还需核对六个固定槽位的现有索引并按执行计划决定是否补齐，轮播卡片通过 `message_material_combination_card` 查询。标签按 `category_id/name/type` 查询时复用或增补索引。批量 MySQL `IN` 单批不超过 500。

#### 4.5 上线前数据处理顺序（不是历史业务数据迁移）

这里的“迁移”仅指**升级表结构、给历史 ****`category`**** 行补上新加的 code、发布兼容逻辑**，不是移动 MySQL/Mongo 数据，也不是给所有历史素材重新打品类：

1. 核查实际库结构及历史数据来源，确认既有 category/tag/tag_relation 主要由 AI 生成；若发现例外，记录对应 ID 并单独修正来源。备份变更涉及的表。
2. 给 category 增加 code/type/source 字段；旧分类的 category_type 默认 TAG_ONLY，不会自动进入素材品类下拉。对旧分类逐行按 ID 生成稳定 code（例如 AI_LEGACY_{id}，仅用于存量兼容，不代表 AI 新分类命名规则），核查所有 code 非空且唯一，再建立 code 唯一索引；不能先建唯一索引，因为新增列默认空字符串会重复。
3. 给 tag、tag_relation 增加来源与关联状态等字段：历史来源默认 AI(0)，关联状态默认正式(1)，提取批次为 0；保留原有标签和关联，不做历史标签去重，也不默认清理历史 AI 关系。启用 AI 重新提取前，核对真实库中是否有非 AI 历史例外并修正来源，确认旧关系读取正常、替换操作仅针对目标素材的 AI 来源行。
4. 给组合表加品类快照列，历史组合默认 UNCATEGORIZED；Mongo 历史素材不写回，读取缺少品类的文档时解释为 UNCATEGORIZED。
5. 白名单管理员在“素材分类管理”页对运营给出的品类（例如 repay_within_one_day）新建记录，或明确选中同名旧分类后调整其 code/type。分类 code 一旦被素材或组合引用不得直接改；改名只改展示名称并同步 tag.category_name。验证新建、人工/随机组合及标签筛选后开放页面。

**AI 分类 code 生成与复用**：当前 `MaterialAITagServiceImpl.OUTPUT_FORMAT` 只要求 `categoryName/tagName`，`TagExtractResultDTO.TagInfo` 无 `categoryCode`，`MaterialCategoryServiceImpl.getOrCreate(name)` 仅按名称写入。需要同步调整提示词、响应 DTO、解析校验和分类保存服务。提示词向 AI 提供已有分类的 `code/name`，要求输出 `categoryName` 和翻译自名称的英文语义化 `categoryCode`，采用 `lower_snake_case`，例如“1 天内还款” -> `repay_within_one_day`，“获客拉新” -> `user_acquisition`；新分类不使用随机 `AI_` + UUID 作为正常编码。单条标签结果示例：

```JSON
{"categoryName":"获客拉新","categoryCode":"user_acquisition","tagName":"拉新内容","confidence":0.95}
```

后端逐条处理：

1. 分类名称命中数据库已有记录：始终复用数据库的 id/code，AI 提议 code 不一致也不得修改持久化 code，可记录偏差供排查。
2. 名称不存在：校验 AI code 非空、长度 1～64、满足 ^[a-z][a-z0-9_]*$、非 UNCATEGORIZED 等保留值；复核语义与名称一致，并确认该 code 未被其他分类占用后，插入 name/code/source_type=0/category_type=TAG_ONLY。
3. code 格式无效、缺失、与已有不同名称冲突或语义不符：不随机补码、不静默复用或改写已有分类；记录该条 AI 结果失败并安排重试或人工审核，该条结果暂不创建分类、标签或关联，其余合法结果继续处理。
4. AI 并发产生相同名称或 code：依靠数据库 code 唯一约束和名称冲突检查，冲突后复查；确为同一分类才复用，否则按第 3 点处理。

分类创建后 code 是稳定身份。管理员调整名称或将 AI 分类转为 `BUSINESS_MATERIAL` 时保留原 `code/source_type`；存量的 `AI_LEGACY_{id}` 是一次性兼容，不要求 AI 为历史行重新翻译。

分类 code 与 `tag.category_id` 的完整性、同名分类/同分类同名标签的查找复用、AI 并发建分类保护均须在服务端落实；不因要求保留多条标签关联而对 `tag_relation` 做去重。分类名称仅供展示，不代替稳定 code；同名冲突停止人工写操作并提示处理。MySQL 大批量 `IN` 每批不超过 500，批量同步采用分页。

已被新素材绑定的 `tag.category_id` 不得直接调整到另一分类，否则旧素材的标签会跨品类。现有标签管理接口的单条更新、批量转分类均须增加“被已分类素材使用时禁止改分类”的后端校验；运营创建后不能修改标签关系本身。现有 `tag.category_name` 只作展示，分类改名时分批同步，不影响 code/ID 关联。停用分类或标签只影响新选择，旧关系保持可回显。

#### 4.6 标签关系多来源存储与提取批次

同一素材、同一 `tag_id` 即使被 AI 和运营同时选中，`tag_relation` 也保存**多条独立记录**，分别标记 `source_type=0` 和 `source_type=2`。不以 `(entity_type, entity_id, tag_id, source_type)` 建唯一约束，不删除、不合并重复关系；原始关联查询保留每一行。`binding_status` 只说明 AI 判断是否为正式/候选，不参与唯一判断。每次 AI 成功重新提取时，先生成提取日志 ID，再在同一 MySQL 事务中仅替换目标素材上上一批 AI 来源的正式/候选行并写入 `extract_log_id`，保留运营及其他来源的全部行；调用失败或结果无效不清理旧判断。重复 MQ 消费以提取批次/消息处理状态控制重复执行，不通过标签唯一索引“去重”。标签在 UI 上可按来源分组展示，但不改变数据库中的多条关系。

## 5. 素材分类管理页面与权限

### 5.1 页面位置与功能

前端 `master` 分支已有 **AI打标** 父菜单，路由为 `/material-ai-manage`，现有子页包括“标签管理”“素材管理”“规则管理”。一期在该父菜单下新增 **素材分类管理** 子页（建议路由 `/material-ai-manage/material-category`），不是新建顶层菜单，也不通过分类维护 Job 执行增删改查。若某个账号当前看不到“AI打标”，应检查实际部署分支、菜单/角色权限及路由过滤；代码存在不等于所有账号都可见。

页面功能：按 code、名称、类型、来源、状态分页查询；展示分类下标签数量和 AI 差异分析的候选量/样例；白名单用户可新增、修改名称/排序/类型/状态、停用以及将已有 AI 分类调整为素材品类。已有分类 `id/code/source_type` 不因调整用途而改变；普通登录用户可读取列表及详情，但看不到写按钮。

新增分类时白名单管理员填写稳定 code（如 `repay_within_one_day`）和名称（如“1 天内还款”），选择 `BUSINESS_MATERIAL` 或 `TAG_ONLY`，服务端记录 `source_type=1`；AI 自动生成的分类仍由提取链路创建，默认 `source_type=0/category_type=TAG_ONLY`。分类 code 一经素材或组合引用不可直接修改；若修改分类名称，需同步冗余的 `tag.category_name`。

停用为 `status=0`，不物理删除已被标签/素材引用的分类；停用后不能新建素材或新选标签，历史记录继续回显。

### 5.2 Apollo 独立写操作白名单

新增**独立的 Apollo 配置 key**（建议 `material.category.manage.write.whitelist`，值为逗号分隔的 SSO 用户名），**不复用 ****`admin.whitelist`**，后者用于后台登录/角色默认权限。白名单为空、未配置或解析失败时写操作一律拒绝；按去空格后的完整用户名精确匹配，不使用 `contains` 子串匹配。

- 写接口：现有 /admin/api/material/ai/category/create、/batchCreate、/update、/delete 以及新增状态/类型调整接口，全部在服务端统一校验 AuthUtil.getCurrentUserName()。delete 改为逻辑停用，不再物理删除。其他可能写 category 的管理员接口也必须收敛到相同校验服务；AI 自动创建属于系统内部链路，不通过该管理白名单。
- 读接口：/page、/queryById、/listAll、素材品类下拉和差异分析查询不受此写白名单限制，但仍遵守现有后台登录和数据访问校验。“读取不限”不表示匿名开放。
- 前端可通过只读权限信息隐藏写按钮，但后端授权是最终准入；白名单热更新后下一次写请求立即使用最新配置。所有写请求记录操作人、操作内容及结果；权限失败返回明确的 403。

同名/同 code 冲突拒绝写入；AI 同名并发建分类由服务端复用检查和数据库约束保护。历史 AI 分类若需转为业务品类，由白名单管理员结合差异分析表及样例审核后在本页调整类型，**不自动转正**。

### 6.3 接口

| 接口/对象 | 变化 |
|---|---|
| `GET /admin/api/material/category/list` | 查询 `category.status=1 AND category_type=BUSINESS_MATERIAL`，返回 `id/code/name/sort/sourceType`，作为素材品类下拉来源 |
| `POST /admin/api/material/ai/category/page`、`GET /queryById`、`GET /listAll` | 分类管理与标签选择的读取，登录用户可调用；分页支持 code/名称/来源/类型/状态筛选 |
| `POST /admin/api/material/ai/category/create`、`/batchCreate`、`/update`、`/delete` | 分类管理写入；服务端校验独立 Apollo 用户白名单；`/delete` 为逻辑停用，不做物理删除 |
| 当前用户分类写权限查询 | 返回是否在独立 Apollo 写白名单中，只用于前端按钮展示；不可代替每个写接口的校验 |
| `GET /admin/api/material/ai/tag/listByCategoryId` | 根据已选分类 ID 查启用素材标签；若分页/搜索需要扩展则增加对应查询参数 |
| `POST /admin/api/material/ai/tag/create` | 从素材页面创建时提交名称、当前品类 code 和 categoryId；后端核对两者指向同一启用且允许用于素材的分类，固定来源 `2`；已有独立标签管理入口继续遵循原分类权限 |
| 素材模板创建/更新请求 | 每条新素材提交 `materialCategoryCode`、`tagIds`；已有素材不接受变更 |
| 素材详情的标签响应 | 正式关联返回 `binding_status=1` 的每条关系（保留 ID、标签、来源），不按 tagId 去重；只读 AI 候选关联返回 `source_type=0 AND binding_status=0` 的每条关系，含分类与 `extractLogId` |
| `POST /admin/api/material/combination/page` | 增加素材 ID/品类筛选，复用现有组合列表；素材 ID 查询覆盖所有实际成员槽位 |
| `POST /admin/api/material/combination/stability/batch` | 批量返回组合维度当前/历史 Utility 占比和评级 |
| 分类差异分析查询接口 | 按日期、素材品类、AI 分类及差异类型分页读取 `material_category_tag_diff_stat`；所有登录用户可读，不受分类写白名单限制 |

标签创建接口不能仅依赖前端把分类锁定：从素材页面新建时必须同时提交当前 `materialCategoryCode`，后端将它解析为 `category.id` 并与请求的 categoryId 比较。素材模板保存时还需重新校验 tagIds 均属于该素材的分类。若提前创建标签但最终取消素材模板，标签字典可保留、不会产生孤儿绑定。

素材模板请求中每条**新素材**携带字段：

```JSON
{
  "tempKey": "body-1",
  "materialCategoryCode": "repay_within_one_day",
  "tagIds": [101, 102],
  "element": {"text": "示例文案"}
}
```

请求中的 `tagIds` 是运营指定的标签，不包括之后异步生成的 AI 标签。既有素材仍提交其 ID 以便保持原有编辑/组合逻辑；若提交品类或标签字段，后端必须与持久化值比较并拒绝变更（允许未改变的回显字段），不能信任前端禁用状态。后端先批量解析分类和标签再写 Mongo，避免逐素材查 MySQL；`IN` 列表单批不超过 500。

## 7. 后端流程与异常边界

1. 创建/更新前：验证模板字段、分类 code 有效且可作为素材品类、tagIds 均有效且属于该分类；对已有素材品类/标签的更改报错。
2. 对随机、人工组合做写库前预校验：按实际参与的组件池/人工行判断，仅允许同一真实分类与未分类混用；普通、轮播、LTO 路径都要覆盖，不能将互不参与同一组合的素材误判为冲突。前端检查只用于提示，后端必须复核。
3. Mongo 新素材保存生成 ObjectId，建立 clientMaterialKey -> ObjectId 映射，再写运营 tag_relation.source_type=2。
4. 组合生成/保存统一收集成员素材，批量读取品类，校验后写 material_category_code。后续若引入组合明细模型，成员遍历可扩展，不依赖标签反推。
5. AI 提取在提交后异步执行；同分类标签写正式关联，跨分类标签写候选关联并关联本次成功提取日志，不阻断素材模板创建；重提只替换 AI 来源的旧正式/候选关联，保留运营、编码规则和历史未知来源关系。
6. MySQL 与 Mongo 非同一事务：入库前完成可预判校验；写入失败记录已生成 Mongo ID 并执行补偿。MQ 重试必须幂等。

**轮播卡片边界**：当前 `message_card` 是独立对象，`message_material_combination_card` 连接组合与卡片，它并非 Mongo `message_material`。一期“新素材必选品类”适用于 Mongo 素材（包括轮播 BODY），不暗示已有卡片也具备分类。若运营要求卡片参与品类兼容性校验，需在卡片实体上新增分类并独立设计迁移，不能把卡片当作已分类素材默默放行。

## 8. 组合稳定性与效果分析

组合稳定性复用素材模板当前计算口径：

```text
message_template.material_combination_id
    -> message_template_waba.category
    -> 当前/历史 UTILITY 占比
    -> 现有稳定性规则
    -> S/A/B/C/D（S 最高）
```

不使用 request/sent/delivered/read 作为稳定性评级依据。组合级 Redis 缓存和批量接口供列表使用；刷新 Job 分批计算，避免大量 `IN` 和逐行查库。当前/历史“可用模板”的过滤条件要与素材模板维度保持一致，并覆盖普通及 AI 备用素材模板。

后续效果分析需按“组合品类 + 素材类型 + 正式生效的同分类标签”分析发送、送达、已读、点击、注册、申请授信、放款等指标；**候选标签只进入分类差异分析，不进入效果聚合**。现有质效大盘归因窗口 `T0/T3/T7` 可作为参考，但一期不新增效果看板。标签仍绑定素材，不复制到组合；将来按标签汇总要保留多标签重复计数提示、最小样本量和观察性结论边界。

| AI 提取 | 已有分类复用数据库 code，新分类需返回语义化 code 并通过格式、语义、冲突校验；同分类写正式关系、跨分类写候选关系；重提仅替换目标素材 AI 关系，保留运营关系及重复记录 |
| 差异 Job | 每日按五种差异类型统计和有限样例，重跑覆盖同一统计日期及维度，不自动修改分类或素材 |
| 分类管理页及权限 | 登录用户可查询；只有 Apollo 独立白名单用户可新增、编辑、停用及审核 AI 分类；绕过前端直接调用写接口返回 403；原有写接口也受保护 |
| 关联数据 | 同一素材、同一标签由 AI 和运营选中时保留多条 `tag_relation`；不建立去重唯一键；差异汇总区分关系条数与素材数 |
| 组合入口 | 素材模板展开与素材浮层均懒加载、分页，列和操作沿用素材组合页 |
| 稳定性 | 组合评级使用当前/历史 Utility 占比，等级包含 S；批量查询不产生逐行查询 |
| 非事务写入 | Mongo 已写而 MySQL 失败时可追踪和补偿，不留下不可见标签绑定 |

## 10. 实施范围与上线验收

### 10.1 后端与数据

- MySQL：category 增加稳定 code、来源和分类类型；tag 增加定义来源，tag_relation 增加绑定来源、正式/候选状态与提取批次；素材组合增加品类快照；新增按日分类差异统计表。实施前核查真实表结构和现有索引，新列遵守 NOT NULL 必须有默认值的规范。
- Mongo：素材保存不可变的分类 code；历史缺字段在读取层统一解释为 UNCATEGORIZED。
- 素材分类管理：复用现有分类查询/维护服务，提供查询、新增、更新、逻辑停用及 AI 分类类型审核；所有管理写接口用 Apollo 独立用户白名单逐请求校验，读取不受该白名单限制。
- 保存服务：校验新素材品类和同分类标签，形成 clientMaterialKey -> 素材 ObjectId 映射，写入运营标签关系。
- 组合服务：随机和人工模式前置校验；普通、LTO、轮播、编辑新增及 AI 备用素材组合保存前统一核对并填充品类。
- 标签服务：AI 输出和响应 DTO 增加 categoryCode；已有分类复用数据库 code，新分类校验 AI 提议的语义化 code，冲突结果不入库；AI 提取只替换目标素材的 AI 来源关系，保留跨分类候选及其他来源的多条关联；正式与候选分接口或明确分组返回。
- 差异分析服务与 Job：按最新成功 AI 提取批次计算每日差异，写可重算的汇总记录，提供只读分页查询。
- 稳定性服务与 Job：按组合维度批量统计当前/历史 UTILITY 占比，计算 S/A/B/C/D 并刷新缓存。
- 查询服务：按素材模板、具体素材筛选并分页返回组合；批量返回组合稳定性。

### 10.2 前端

- 素材模板新建/编辑/查看弹窗增加品类、同分类标签选择、新建标签和只读状态；已有素材只读展示 AI 候选（与正式标签分区）；组合配置即时提示冲突。
- “AI打标”下新增“素材分类管理”子页；登录用户可查看，白名单用户才显示新增/编辑/停用/调整类型操作；管理页展示差异分析证据供人工审核。
- 素材模板列表按需展开其组合；素材卡片按需打开关联组合浮层。
- 将独立素材组合页面的列、详情与操作抽成可复用模块，在列表展开区和浮层保持一致；新增品类和稳定性信息，查看模式隐藏写操作。
- 普通、LTO、轮播和人工组合的素材选择、预览及移动端/窄窗口布局均需验证，不因为新增字段改变现有操作流程。

### 10.3 上线顺序

1. 核查历史分类/标签主要由 AI 产生且记录例外；备份后新增字段，来源默认 AI(0)；先为旧分类回填唯一 code，再建 code 唯一索引，确认不清理历史标签关联。
2. 上线新旧素材兼容的后端读取与保存、AI 分类 code 生成、分类写白名单、组合品类校验及稳定性服务；确保已有素材模板仍可查看和使用。
3. 将“素材分类管理”挂到现有“AI打标”目录，白名单管理员在页面发布可选品类；验证新增、编辑、人工和随机组合，再开放前端素材入口。
4. 启用组合评级刷新和分类差异分析 Job，观察失败率、候选/正式标签数量、Mongo/MySQL 补偿和缓存命中。

### 10.4 验收条件

- 运营只能在启用的 BUSINESS_MATERIAL 分类中为新素材选择单一品类，且仅能选择该分类的启用标签。
- 人工及随机组合在多真实品类冲突时不能保存；未分类历史素材仍能与一个真实品类组合。
- 素材模板列表和具体素材浮层均能分页查看相应组合，所展示的原有功能与素材组合页面一致。
- 组合稳定性使用 UTILITY 占比计算，包含最高 S 级；AI 跨品类判断保留为可查看、可分析的候选，但不影响素材品类、正式标签及效果统计；AI 重提不删除运营或编码规则标签。
- 存量数据可正常查看，历史关联不被误删；同标签不同来源可保留多条记录；失败写入可追踪并补偿。
