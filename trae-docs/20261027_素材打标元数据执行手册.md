## 二、执行前必读

1. **顺序不可打乱。** STEP1 的 `ADD COLUMN` 必须先于 STEP2 回填 `code`；`uk_category_code` 唯一索引必须先等 STEP2 回填完成（否则空字符串会撞唯一键）。
2. **影响面。** 旧 19 个分类 `status=0` 后，`MaterialCategoryServiceImpl.listAll()` 只返回新 14 个品类，AI 打标的 `categoryList` 会整段换掉；存量 2621 条标签和历史 `tag_relation` 不受影响。
3. **无代码回滚开关。** 提示词与规则一改就全量影响后续打标，STEP7 发布前请先做离线回放（见第九节）。
4. **不要在业务高峰执行。** STEP1 的 `ALTER TABLE tag` 会短暂锁表；`tag` 当前 2621 行，影响可控，仍建议低峰。
5. **脚本不含 `tag.group_code`**，该字段已明确不新增。

## 五、逐步操作

### STEP0 前置检查（只读，先留存输出）

```sql
SHOW COLUMNS FROM `category` LIKE 'code';                 -- 期望 0 行
SELECT COUNT(*) FROM `category`;                          -- 期望 19
SELECT COUNT(*) FROM `tag` WHERE `type` = 'MATERIAL';     -- 期望 2621
SELECT COUNT(*) FROM `category` WHERE `code` IN ('user_acquisition', ...); -- 期望 0
```

任一结果与期望不符，先停下来确认是否已有他人执行过。

### STEP1 表结构迁移

```sql
ALTER TABLE `category`
  ADD COLUMN `code` varchar(64) NOT NULL DEFAULT '' AFTER `name`,
  ADD COLUMN `category_type` varchar(32) NOT NULL DEFAULT 'TAG_ONLY' AFTER `code`,
  ADD COLUMN `source_type` tinyint(4) NOT NULL DEFAULT '0' AFTER `category_type`;

-- 只加字段，不加 idx_category_id（线上已存在）
ALTER TABLE `tag`
  ADD COLUMN `source_type` tinyint(4) NOT NULL DEFAULT '0' AFTER `type`;

ALTER TABLE `tag_relation`
  ADD COLUMN `source_type` tinyint(4) NOT NULL DEFAULT '0' AFTER `tag_id`,
  ADD COLUMN `binding_status` tinyint(4) NOT NULL DEFAULT '1' AFTER `source_type`,
  ADD COLUMN `extract_log_id` bigint(20) NOT NULL DEFAULT '0' AFTER `binding_status`,
  ADD KEY `idx_entity_source` (`entity_type`,`entity_id`,`source_type`),
  ADD KEY `idx_extract_log_id` (`extract_log_id`);

ALTER TABLE `message_material_combination`
  ADD COLUMN `material_category_code` varchar(64) NOT NULL DEFAULT '' AFTER `material_template_type`,
  ADD KEY `idx_material_category_code` (`material_category_code`);
```

验收：`SHOW COLUMNS` 四张表对应字段全部存在。

### STEP2 停用旧 19 个「写作技法」分类

```sql
UPDATE `category`
SET `code` = CONCAT('ai_legacy_', `id`),
    `category_type` = 'TAG_ONLY',
    `status` = 0,
    `utime` = ROUND(UNIX_TIMESTAMP(NOW(3)) * 1000)
WHERE `id` < 900001
  AND `code` <> CONCAT('ai_legacy_', `id`);
```

- `code` 用小写 `ai_legacy_{id}`，因为分类 `code` 有校验正则 `[a-z][a-z0-9]*(?:_[a-z0-9]+)*`，大写 `AI_LEGACY_` 会在页面保存时报错。
- 停用而非删除：`listAll()` 只查 `status=1`，停用即退出提示词，历史关联完整保留。

**硬性验收：**

```sql
SELECT COUNT(*) FROM `category` WHERE `code` = '' OR `code` IS NULL;  -- 必须为 0
```

不为 0 就**不要**进 STEP4。

### STEP3 插入 14 个品类

固定 id 段 900001–900013 + 900016，避开现有 1–17、1000001、1000002。清单与排序见附录 A。

验收：14 行，`category_type='BUSINESS_MATERIAL'`，`status=1`。

> `repay_1_day`（1天内还款）与 `repay_2_day`（2天内还款）**不落库**：它们只出现在需求文档术语表的示例里，素材正文全量分析中没有 T-1 / T-2 的独立主题（对应的是 `DUE_REMINDER` / `DUNNING_OVERDUE` / `DUNNING_UNPAID`）。900014 / 900015 两个 id 保留不复用，后续业务确认要拆分时再补。

### STEP4 唯一索引与差异统计表

```sql
ALTER TABLE `category` ADD UNIQUE KEY `uk_category_code` (`code`);
CREATE TABLE IF NOT EXISTS `material_category_tag_diff_stat` (...);  -- 见脚本原文
```

`material_category_tag_diff_stat` 支撑后续每日「运营品类 / 标签 vs AI 抽取」差异分析 Job，按 `(stat_date, material_category_code, ai_category_code, diff_type)` 唯一，可重跑。

### STEP5 灌 202 条标签

执行方式：建临时表 `tmp_tag_seed` → 一次性 `INSERT ... VALUES` → `DELETE` 目标 id 段旧数据 → `INSERT ... SELECT JOIN category ON code` → 校验 → `DROP TABLE`。

四个关键点：

| 点 | 原因 |
| --- | --- |
| `tag.name` 写入 `<dim>:<value>` 英文名（如 `tenor:7d`） | 库里只有 `(category_id, name)`，维度不是字段；不带前缀的 `7d`、`collection` 无法自解释 |
| `category_name` 取 `c.name`，不写中文常量 | `TagServiceImpl.getByNameAndCategoryName()` 按**名称**匹配标签所属分类，写错就关联不上 |
| `type='MATERIAL'`、`source_type=1`（ADMIN） | 人工配置的标签来源是管理员，不是 AI |
| INSERT 前先 `DELETE FROM tag WHERE category_id BETWEEN 900001 AND 900016` | 保证可重跑；`tag_relation` 未引用这些新标签，删除无副作用 |

命名规则与「维度 / 7天」的含义见第十节，逐条明细见附录 B。

**验收（7 条，全部通过才继续）：**

```sql
-- 1) 总数 202
SELECT COUNT(*) FROM `tag` WHERE `category_id` BETWEEN 900001 AND 900016;
-- 2) 分品类数量，期望 19/20/15/14/19/16/16/13/15/12/10/8/11/14
SELECT `category_id`, COUNT(*) FROM `tag` WHERE `category_id` BETWEEN 900001 AND 900016 GROUP BY 1 ORDER BY 1;
-- 3) 每品类 level=1 数量，期望 3/3/3/3/4/3/3/3/3/4/3/2/3/4（合计 44）
SELECT `category_id`, SUM(`ai_demo_level`='1') FROM `tag` WHERE `category_id` BETWEEN 900001 AND 900016 GROUP BY 1 ORDER BY 1;
-- 4) 同品类重名 0 行
SELECT `category_id`,`name`,COUNT(*) FROM `tag` WHERE `category_id` BETWEEN 900001 AND 900016 GROUP BY 1,2 HAVING COUNT(*)>1;
-- 5) category_name 不一致 0
SELECT COUNT(*) FROM `tag` t JOIN `category` c ON c.id=t.category_id
WHERE t.category_id BETWEEN 900001 AND 900016 AND t.category_name <> c.name;
-- 6) 标签名不符合 <dim>:<value> 规范 0
SELECT COUNT(*) FROM `tag` WHERE `category_id` BETWEEN 900001 AND 900016
  AND `name` NOT REGEXP '^(topic|form|offer|risk|tenor|urgency|audience):[a-z0-9][a-z0-9.-]*$';
-- 7) 临时表 dim 与名称前缀不一致 0（脚本内已校验，重跑时复核）
SELECT COUNT(*) FROM `tmp_tag_seed` WHERE LOWER(SUBSTRING_INDEX(`name`, ':', 1)) <> LOWER(`dim`);
```

`ai_demo_level` 语义：1=强示例（few-shot 首选）、2=弱示例、3=边界易混（必须在规则里给区分说明）。只有非空值会被序列化进 `categoryList`。

### STEP6 灌 16 条 tag_rule

- 2 条全局：`category_id=6`（沿用生产惯例）、`scope='全局适用'`、文本写明「只执行【品类名】与素材品类一致的那条品类规则」。
- 14 条品类：`category_id` 指向各自品类、`scope='品类专属'`、每条以【品类名】开头自证身份。

**为什么必须这样写**：`TagRuleServiceImpl.listAllValidRules()` 只按 `status=1` 和 `sort` 排序，**不按品类过滤**，16 条规则会全部拼进每一条 prompt。不做自选约束，模型会拿到 14 个品类的规则互相干扰。

验收：`SELECT COUNT(*) FROM tag_rule WHERE status=1;` 期望 16。
建议同时停用旧规则：`UPDATE tag_rule SET status=0 WHERE id=1;`（其分类已被 STEP2 停用，规则文本也已过时）。

### STEP7 Apollo 提示词（非 SQL）

- Key：`material.ai.tag.system.prompt`
- 现状：**空字符串**，所以 prompt 第一段是空白。
- 动作：粘贴脚本 STEP7 注释块中的英文文本 → 发布 → 用一条已有素材验证 `buildPrompt()` 输出。
- 注意：不要改动代码里的 `OUTPUT_FORMAT`，新文本只作为前置 system 段落。

## 十、维度与命名口径（必读）

### 10.1 为什么标签名里必须带「维度」

`tag` 表只存 `(category_id, name)`，**没有维度字段**（`tag.group_code` 已明确不加）。所以维度只能内嵌进名字：

```
库里能看到的                       没有的东西
category_id = 900001   → 获客拉新
name        = tenor:7d            ← 维度只能是名字前缀
                                   （不存在 dim 列）
```

如果名字只写 `7天`，脱离上下文没人知道它指代什么；写成 `tenor:7d` 就自解释：维度=期限档位，取值=7 天。

因此本次入库口径统一为 `tag.name = <dim>:<value>`：

- `dim` 固定 7 个（见 10.2），必须小写；
- `value` 小写英文 kebab-case（`signup-incomplete`、`0.01pct-daily-rate`）；
- 中文名只存在于本文档，作为运营沟通与页面展示的词典，不入库。

### 10.2 七个维度（中英对照）

| dim | 中文维度名 | 含义 | 判定依据 | 示例 |
| --- | --- | --- | --- | --- |
| `topic` | 内容主题 | 这条素材想推动的业务动作 | 看正文主线意图，不看语气 | `topic:signup-incomplete` |
| `form` | 文案形态 | 叙述口吻与体裁 | 看语气、结构、是否伪装通知 | `form:collection` |
| `offer` | 权益要素 | 给出的具体权益 | 出现明确数字、券、减免 | `offer:30d-interest-free` |
| `risk` | 合规风险 | 疑似违规的夸大表述 | 出现绝对化措辞、时效承诺 | `risk:instant-arrival-promise` |
| `tenor` | 期限档位 | 正文出现的天数档位 | 出现 7/20/30/60 hari 等天数 | `tenor:7d` |
| `urgency` | 紧迫度 | 催促强度 | 看时间压力类措辞 | `urgency:urging` |
| `audience` | 目标人群 | 文案面向谁 | 看人称与身份词 | `audience:new-user` |

> 维度是**设计期分组视角**，不落库；落库的只有「品类 + 带前缀的标签名」。

### 10.3 「7天」「20天」到底指什么

`tenor` 只记录**正文里出现的天数档位**，不替业务解释含义：

- **免息类品类**（`user_acquisition`、`free_benefit`、`limit_*` 等）：天数通常来自「30 天免息」，所以 `tenor:30d` 与 `offer:30d-interest-free` 会同时出现。前者用于「按天数档位筛选」，后者用于「标注权益类型」，是同一条事实的两个视角。
- **还款类品类**（`repay_due`、`repay_overdue`）：天数来自借款产品期限（如 `pinjam 7 hari`、`tenor 30 hari`）。`tenor:7d` 表示这条素材推的是 7 天期产品，**不是**「7 天内还款」。
- 需求文档术语表里的 `repay_1_day`（1天内还款）/ `repay_2_day`（2天内还款）已确认不落库（见附录 A 说明），因此没有 T-1 / T-2 的「账期节点」标签，账期语义由 `repay_due`、`repay_overdue` 两个品类表达。

### 10.4 「user_acquisition 品类 + tenor 标签」怎么读

新版 `user_acquisition` 只挂 `tenor:30d`（无 7d/20d），因为它只承接 30 天免息类文案。一条记录的读法：

```
category_id = 900001 (user_acquisition)  → 素材属于「获客拉新」
tag.name    = tenor:30d                  → 正文出现 30 天档位（这里是 30 天免息期）
tag.name    = offer:30d-interest-free    → 权益是「30 天免息」
```

### 10.5 同名标签跨品类

- **合计 202 条**，与[附录 A](#附录-a14-个品类)「标签数」列一致；逐品类 count 应为 `19/20/15/14/19/16/16/13/15/12/10/8/11/14`。

- **命名全部符合正则** `^(topic|form|offer|risk|tenor|urgency|audience):[a-z0-9][a-z0-9.-]*$`（允许 `0.01pct-daily-rate` 这类带小数点的取值），脚本 STEP5 已内置校验，期望 0 条不符。
- **中英一一对应**：每行英文名与中文名的维度段、取值段一一对应（`tenor:7d` ↔ `期限档位:7天档位`）；中文名不入库，仅作展示与沟通口径。

- `sort` 在每个品类内从 1 连续递增，与上表 `#` 列完全一致。
