## 一、结论先行

| # | 结论 | 依据 |
| --- | --- | --- |
| 1 | **品类（BUSINESS_MATERIAL）不能只当组合校验标签，它同时是 AI 正式标签的归属容器** | 需求 1.4「新建标签时分类锁定为当前素材品类」、需求 1.6「同分类才转正」 |

## 四、L1 素材品类清单（建议 16 个）

设计原则有两条，互相拉扯，取平衡点：

- **品类要够细**：不同品类素材不能混组（需求 1.3）。`repay_1_day` 的话术放进 `repay_2_day` 组合里是资损/投诉风险，必须分开。
- **品类要够粗**：品类越细，可组合素材越少，随机组合生成率越低。已验证品类组合数过少会直接卡住模板创建。

## 五、L2/L3 关键取舍：为什么不做 7 个语义分类

需求 1.6 的规则是：

> 与素材品类同分类的 AI 标签作为正式标签；跨分类 AI 标签作为候选保留，不进入正式标签筛选和效果统计。

而素材只能有**一个**品类（需求 1.2 单选）。于是：

| 方案 | 结构 | 正式标签 | 语义维度可聚合 | 结论 |
| --- | --- | --- | --- | --- |
| A 品类即归属 | 16 品类，每个品类下挂同一套标签池的子集 | ✅ 正常转正 | ✅ 靠标签名 + `tag.group_code` | **推荐** |
| B 语义分类并列 | 16 品类（无标签）+ 7 个 TAG_ONLY 语义分类 | ❌ 全部跨分类 → 全是候选 | ✅ 天然按分类分 | 只能做分析，正式标签为空 |
| C 语义分类替代品类 | 7 个语义分类同时当品类 | ❌ 组合校验语义错乱（`limit_offer` 和 `free_benefit` 可混组） | ✅ | 不推荐 |

**采用 A**，并补一个小字段：

```sql
ALTER TABLE `tag`
  ADD COLUMN `group_code` varchar(32) NOT NULL DEFAULT '' COMMENT 'Semantic group: TOPIC/FORM/OFFER/RISK/TENOR/URGENCY/AUDIENCE';
```

`group_code` 的作用只有三个，都很轻：前端按维度分组展示标签、报表按维度聚合、`tag_rule` 按维度下发规则。**如果不想动表结构**，退化方案是标签名统一以维度中文前缀打头（`主题-额度招揽` / `形态-伪装系统通知`），前端按 `-` 前缀分组——能用，但 UI 上会难看，且改名成本高。建议加字段。

## 七、L4 抽取规则与系统提示词

### 7.1 tag_rule：2 条全局 + 16 条品类

`tag_rule.scope` 字段已有「全局适用」，用两层规则：

**全局规则（2 条，scope=GLOBAL）**

```json
[
  {
    "ruleName": "输出约束",
    "categoryName": "全部",
    "isRequired Build Tag": "true",
    "rule": "只输出 categoryList 中存在的 categoryCode；tagName 优先取同分类既有标签名；confidence 低于 0.7 的标签不输出；单个分类下最多 2 个标签；无法判断时不输出，不要兜底。"
  },
  {
    "ruleName": "正式/候选口径",
    "categoryName": "全部",
    "isRequired Build Tag": "true",
    "rule": "标签必须归属素材当前品类对应的分类；不得输出其他品类下的分类编码，避免产生候选标签。"
  }
]
```

**品类规则模板（16 条，每个品类一条，category_id 指向该品类）**

以 `limit_offer` 为例：

```json
{
  "ruleName": "额度招揽品类打标规则",
  "categoryName": "额度招揽",
  "isRequired Build Tag": "true",
  "rule": "必选 1 个 TOPIC（额度招揽 / 大额额度+免息组合招揽）；必选 1 个 FORM；若正文出现明确额度数字，打「额度上限渲染」；若出现「detik/menit」等时效承诺，打「极速到账承诺」；若出现免息天数，打对应 TENOR。区分说明：「竞品对比」只在正文出现「kompetitor / 别人 / 别被忽悠」等对比对象时才打，单纯说自家额度大不算。"
}
```

每个品类的 `rule` 只需替换「必选 TOPIC 集合」和「易混标签的区分说明」，结构一致。

### 7.2 Apollo `material.ai.tag.system.prompt`

当前该配置**实测为空**，所以 prompt 第一段是空白。建议内容（英文，与 OUTPUT_FORMAT 保持一致）：

```text
You are a tagging engine for WhatsApp marketing templates of an Indonesian
multi-finance lender. You receive: (1) categoryList with allowed categories and
example tags, (2) MaterialContent with materialId/type/content, (3) tag Rule.

Rules:
1. Only use categoryCode values present in categoryList. Never invent a category.
2. Prefer tagName values that already exist under that category. Follow the
   naming style of the examples. New tag names are allowed only when no existing
   tag describes the content; keep them short (2-12 Chinese characters) and
   noun-phrase style.
3. Follow tag Rule strictly, including required dimensions and the maximum tag
   count per category.
4. Tag what the text SAYS, not what it implies. For HEADER image descriptions,
   tag the visual subject and style, not marketing intent.
5. Emit at most 6 tags per material. If nothing applies, return an empty tags
   array. Never emit placeholder tags such as "其他" or "未知".
6. confidence must reflect evidence strength: 0.9+ only when an explicit phrase
   supports the tag.
```

## 九、实施顺序

| 阶段 | 动作 | 验收标准 |
| --- | --- | --- |
| P0 | 执行 [2026-10-21-material-category-tag.sql](../../whatsapp_crm/doc/sql/2026-10-21-material-category-tag.sql) | 三类字段存在，`tag.group_code`（若采纳）已加 |
| P1 | 灌 16 个品类 + 19 个旧分类补 code 并 `status=0` | `listAll()` 只返回 16 个品类 |
| P2 | 灌标签池（约 262 条）+ `ai_demo_level` + `group_code` | 每个品类下 `level=1` 标签 3–5 个 |
| P3 | 灌 2 条全局 + 16 条品类 `tag_rule`；配 Apollo 提示词 | `buildRules()` 输出非空，`buildCategoryList()` 示例非空 |
| P4 | **离线回放** 1219 条 distinct 正文 | 主主题命中率 ≥ 85%（与规则引擎基线对齐）；新增标签占输出标签 ≤ 15% |
| P5 | 上线 AI 打标，观察 7 天差异分析 Job | 候选标签占比 ≤ 20%；日新增标签数收敛 |

离线回放是必须的：`tag_rule` 和提示词改一次就会全量影响存量素材，线上没有回滚开关。
